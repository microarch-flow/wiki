# 从逻辑门到芯片顶层:AI 算力单元为何长成这样

> 来源:Dwarkesh Patel × Reiner Pope(MatX CEO,前 Google TPU 架构师)黑板讲座第二期,2026-05。
> 本文不是逐字稿复述,而是按"计算 / 通信比(compute-to-communication ratio)"这条单一主线重组的架构师笔记。

---

## 0. 全文母题:一切都在最大化"有用计算 / 数据搬运"

这期讲座表面上是"自底向上搭一颗芯片",真正的内核是**同一个 trade-off 在不同抽象层级上反复出现**:

> 芯片面积里,真正做乘加的逻辑很少;绝大部分面积花在把数据从一个地方搬到另一个地方(选数、存储、同步、布线)。每一层的设计动作,本质都是在抬高"有用计算 vs 数据搬运"的比例。

这条主线会在下面六个层级各出现一次:

| 层级 | 计算项 | 通信 / 开销项 | 抬比例的手段 |
|---|---|---|---|
| 比特精度 | p×q(乘法器面积) | —— | 降位宽(二次缩放) |
| datapath | p×q(MAC) | 3·n·p(三个 mux) | —— 这是问题,不是解 |
| systolic array | x·y(阵列做的 MAC) | x(进出向量) | 权重就地驻留 + 复用 |
| pipeline | 每周期做的事 | pipeline register 面积 | 切到"够用就好",别过切 |
| FPGA vs ASIC | 真实门 | LUT/mux 可配置开销 | 流片固化(10× 收益) |
| 顶层布局 | systolic array 大小 | vector↔matrix 跨边界布线 | 粗粒度摊薄 RF 成本 |

记住这张表,下面每一节都是它的一行展开。

## 02. Datapath 基础:从逻辑门搭出一个 MAC

### 02.1 为什么 multiply-accumulate 是 AI 芯片的天然原语

**因为** 矩阵乘的本质是三重循环:

```
for i:
  for k:
    for j:
      out[i,k] += in[i,j] * w[j,k]   # 每一步都是一次 MAC
```

**所以** 每一个最内层迭代恰好是一次"乘了再累加"——MAC 不是被选出来的,它是矩阵乘自己长出来的原语。

**第二个理由是精度不对称**:乘法用低精度,累加用高精度。

- **因为** 累加沿 j 维重复 j 次,每次都引入舍入误差,误差会沿求和链累积;而乘法链上只有一次乘法,几乎不累积误差。
- **所以** 选择"4-bit × 4-bit 乘法 + 8-bit 累加"是有物理依据的非对称设计,不是随手定的位宽。

> ⚠️ 常见误解:以为"累加要高精度"只是因为结果数值更大。更本质的原因是**误差沿求和链累积**——这是两个独立的理由,数值范围只是其一。

### 02.2 手工推导:一个 4×4 MAC 要花多少门

把 `1001 × ????  + (8-bit accumulator)` 用长乘法摊开:

```
        1 0 0 1            ← 被乘数
      × ? ? ? ?            ← 乘数(逐位)
      ---------
        1 0 0 1            ← 部分积 0(乘数第 0 位 = 1)
      0 0 0 0              ← 部分积 1(乘数第 1 位 = 0)
    1 0 0 1                ← 部分积 2
  0 0 0 0                  ← 部分积 3
+ a a a a a a a a          ← 顺手把 accumulator 一起加进来
  -----------------
        (一个 8-bit 五路求和)
```

**两类门**就够了:

1. **AND 门生成部分积**:每个部分积比特 = (被乘数某位) AND (乘数某位)。p 位 × q 位的乘法需要 **p×q 个 AND 门**(本例 16 个)。
2. **Full adder(3→2 compressor)做求和**:注意它**不是**软件里的 32-bit 加法器——它把同一比特位上的 **3 个 1-bit 数**压成 **2 bit 输出**(sum + carry)。本质是"数一列里有几个 1,用二进制表达"。

求和时沿列反复用 full adder,每次吃掉一列里的 3 个数、吐出 2 个数,直到每列只剩 1 个数。这套压缩方式叫 **Dadda multiplier**,是面积高效乘法器的标准做法。

### 02.3 一个很漂亮的代数闭合

数一下用了几个 full adder。**每用一次 full adder 净消掉 1 个比特**(3 进 2 出),所以:

```
full adder 数量 = 起始比特数 − 输出比特数
              = (p×q + (p+q)) − (p+q)
              = p×q
```

部分积 p×q 个比特,加上 accumulator 的 p+q 个比特;最后输出 p+q 个比特。一减,**accumulator 项完全抵消**,full adder 数恰好 = p×q。这也是选 MAC(而非纯乘法)作为原语的第二个理由——它给出这么干净的 p×q 代数。

### 02.4 收束点:面积随位宽**二次**缩放

这是整节最该记住的一句话:

> 乘法器面积 ∝ p×q ∝ (位宽)²

**所以**:

- 位宽减半 → 面积理论上降到 1/4,而不是 1/2。
- 这是**低精度算术对神经网络如此有效的单一最根本原因**——比你直觉以为的还要划算一倍。

**Real hardware 锚点**:Nvidia 在 B100/B200 之前一直按"位宽减半 → FLOP 翻倍"标 spec(线性假设)。但因二次缩放,这个比例其实偏保守。从 **B300** 起 Nvidia 改口,标 FP4 比 FP8 快 **3×**(理论极限其实是 4×)。

> 补充:FP4/FP8 的电路**并不完全 fungible**(不能自由互换)。"FP4 算力 = 2× FP8"这种整齐比例,一部分来自给各精度分配的 die area,一部分来自数据搬运的便利——两个 4-bit 数能塞进一个 8-bit 的存储槽,片上总线宽度天然对齐。浮点还多一个 exponent 项,使计算比上面的整数例子更复杂。

### 02.5 datapath 的真问题:mux 与数据搬运成本

现在把 MAC 塞进一个 CUDA core / CPU core 看看代价。结构:一个 register file(比如 8 entry)+ 一个 MAC 单元,从 RF 读 3 个输入、写回 1 个。

"选第 3 号寄存器"这个软件里看似免费的动作,硬件上是一个 **mux(多路选择器)**:

```
n 个输入 ─┬─ AND(掩码:要的那行 AND 1,其余 AND 0)
          │
          └─ OR(把 n 行收拢成 1 行)
```

**一个 n 输入、p 位的 mux 成本**:n×p 个 AND + (n−1)×p 个 OR ≈ **n×p 个门量级**。

MAC 有 3 个输入 → 3 个 mux。算总账(n=8, q=4):

```
数据搬运:3 × n × p = 3 × 8 × p = 24p 个门
真正计算:p × q     =     4 × p =  4p 个门
```

> **七八成的面积花在了软件完全不可见的数据搬运上**,真正做乘加的逻辑只占零头。

**因为** RF 越大,mux 越贵(线性 ∝ n),而且这成本在每次访问都付;**所以** "无脑加大 register file 换灵活性"会被数据搬运成本反噬。这正是 Volta 之前 GPU(以及 CPU)CUDA core 的状态,也是 Tensor Core / systolic array 出现的直接动机。

> ⚠️ 常见误解:把"选一个寄存器"当成零成本操作。它是一个 n×p 量级的组合电路,是全栈数据搬运成本的第一层。

## 03. Systolic Array:把循环上提一层,扭转计算/通信比

### 03.1 核心思路

datapath 阶段我们把"一次 MAC"固化进了硬件。**systolic array 的思路是再往上提两层循环,把整个矩阵-向量乘固化进硬件。**

**因为** 更大粒度的固定功能逻辑,可以让进出口的"税"摊得更薄:
- compute 涨 x×y(阵列里每个 PE 都做 MAC)
- 但通信只需涨 x(只有进出的向量跨边界)
- → 净赚一个 y 倍的 advantage 项

### 03.2 权重就地驻留 + 复用(weight-stationary)

矩阵-向量乘 = 每列与向量做点积。映射到 2×2 阵列:

```
        in: 3   7          ← 输入向量从顶部灌入,向下流
            │   │
        ┌───▼───▼───┐
   w00→ │  PE   PE  │      ← 权重 0,1 就地存在 PE 的 register 里
        │  ·    ·   │
   w10→ │  PE   PE  │      ← 权重 2,3 就地驻留
        └───┬───┬───┘
            ▼   ▼
        out(沿列累加,从底部出)
```

**关键技巧**:在 AI 场景里,**权重矩阵长时间不变**。**所以** 把它就地存在阵列的 register 里反复复用,跨边界的只有输入/输出向量(x 量级),权重不需要每周期从昂贵的 RF 重新搬进来。

> 这正是矩阵乘的"额外一维"被利用的地方:你做大量乘法才出一个点积值,所以可以在出一个值之前,把大量乘法塞进去——计算/通信比天然有利。

### 03.3 权重怎么装进去:trickle-feed

既然权重就地驻留,它**最初**怎么进去?答案:不在乎慢,只在乎窄。

- **因为** 权重只在切换模型时载入一次,优化目标是**带宽(= 面积 = 跨边界布线数)**,而不是延迟。
- **所以** 用 daisy-chain 慢速 trickle:每周期只往顶行灌一行,其余行整体下移一格,连续 y 个周期灌满。跨边界布线压在 x 量级,而非 x×y。

```
cycle 0:  顶行 ← w_row0
cycle 1:  顶行 ← w_row1,  原顶行 ↓ 下移
cycle 2:  顶行 ← w_row2,  其余 ↓ 下移
...                                      ← 布线只需 x 宽
```

> Dwarkesh 的总结很精准:**载入只发生一次,所以优化带宽而非延迟;用更少的窄通道慢慢灌,因为这值要在里面待很久。**

### 03.4 sizing trade-off:阵列多大、RF 多大

**Real hardware 锚点**:老 TPU 是 **128×128** 的这种阵列,是已知最高效的矩阵乘电路。

最核心的 sizing 决策是一对耦合变量:**systolic array 多大 vs register file 多大**。

- 大 RF → 更灵活、application-level 性能更高,但吃掉本可给阵列的面积。
- 常用方法:给数据搬运设一个**面积预算**(比如"RF 占 10%,阵列占 90%"),再据此定 RF 大小。

> ⚠️ 注意:阵列越大,RF 成本摊得越薄(同一份 RF 喂更多 PE)。这个"大阵列摊薄 RF"的论点,会在 §07 GPU vs TPU 顶层布局里再次出现。

## 04. 时钟与流水:同步的代价

### 04.1 为什么要全局时钟同步

一颗芯片 ~1000 亿晶体管,极度并行。**因为** 大规模并行必须解决"不同单元何时握手"的问题;软件用 mutex(一个线程抢锁、通知另一个)这种昂贵手段,芯片用不起。

**所以** 芯片每 ~1ns 让全部电路暂停一瞬、整体同步到下一拍——这就是时钟周期。整片芯片近乎 lockstep 推进。机制上由 register 介导:逻辑云的输出在时钟沿那一刻被打入 register。

时钟周期由**最长关键路径的逻辑延迟**决定:想跑 2 GHz,任何一条逻辑路径都必须在 0.5ns 内稳定。

> ⚠️ 工程现实:并非"赌一个概率能不能算完"。标准做法是 margin 到提前 ~25% 周期完成,多个标准差之外,实际视为永远满足时序。只有 clock domain crossing 这类边缘情况才真的要算概率。这也解释了**同一工艺节点的两颗芯片可以有不同时钟频率**——取决于关键路径优化得多干净。

### 04.2 pipeline register insertion:切逻辑换频率

最朴素的提频手段:把一团逻辑云从中间切两半,中间插一个 register。

```
[─────── 长逻辑云 ───────]  →  [─半─]─reg─[─半─]
         1× 时钟                      2× 时钟,代价:多一个 register
```

**因为** 每半段延迟减半;**所以** 时钟可翻倍,吞吐翻倍,代价是面积(多出来的 register)。这是**纯粹的时钟速度 ↔ 面积** trade-off。在芯片里大量插这种 register 是设计工作的一大部分,手工 + 自动混合完成。

### 04.3 最硬的约束:带反馈环的逻辑

上面是"流水线"这种简单情形。真正的硬骨头是**自反馈逻辑**——比如 running sum:每周期把新数加到自己身上。

```
        ┌──────────────┐
   in ──▶(+)──▶ reg ────┤
         ▲              │
         └──────────────┘   ← 输出回灌输入
```

**因为** 如果这个 `+` 太慢,你不能简单地往中间插 pipeline register——那会改变语义:本该是"所有输入的累加和",插了 register 后变成**两条独立的累加和(偶数拍一条、奇数拍一条)**。

**所以** "有环的逻辑"(任何芯片某处都有)是**设定时钟周期的最硬约束**,不能用插 register 的廉价手段绕过。(注:`+` 本身不是原子的——它内部也是一堆 full adder,可以在内部切;但跨越反馈边界切就会坏掉语义。)

### 04.4 过犹不及:频率高 ≠ 吞吐高

把一个 register + 一个 AND 门组成极小环路,能跑到 5-6 GHz。但看面积:AND 门是 1 个门当量,register 大约 8 个门当量。**几乎所有面积都花在同步(register)上,而非逻辑。**

> **吞吐 = (每周期做的事 / 面积效率) × (每秒周期数)**

把频率推到极致 = 牺牲面积效率 = **吞吐反而下降**。你得到的是低延迟 + 低吞吐。

> 这与上一期聊的 batch size 是同一个张力:batch 小则单用户首 token 快(低延迟),但每小时总 token 数低(低吞吐)。频率推太高 = 减少了可榨取的并行度。

## 05. FPGA vs ASIC:可配置性的 10× 代价

### 05.1 商业账先行

| | 第一颗成本 | 单位能效/成本 | 适用场景 |
|---|---|---|---|
| FPGA | ~$10k | 差一个数量级 | 确定性低延迟 + workload 频繁改(如每月) |
| ASIC | ~$3000 万(一次 tape-out) | 好一个数量级 | workload 稳定、量大 |

FPGA 能表达的,ASIC 都能表达。FPGA 的存在理由是:**想要确定性延迟 + 高并行,但又频繁改 workload,不愿每次都付流片费。**

### 05.2 FPGA 三大件,以及"muxes all the way down"

- **register**:存储
- **LUT(lookup table)**:可配置门
- **大量 mux**:在"现场(field,指部署在数据中心后)"配置布线——每个单元前都挂一个 mux,从邻近电路里选输入。配置 FPGA = 配置所有这些 mux 的选择 + LUT 的真值表。

**LUT 的本质就是一个 mux**:4 输入 → 1 输出,共有 2^(2^4)... 不,共有 16 种"4→1 bit"的输入组合,真值表 16 个 entry,用 4 个输入位去 mux 选出对应那一行输出。所以一个 LUT = 一个 n=16, p=1 的 mux + 一个把 soup 里选 4 位喂进来的前级 mux。Pope 原话:**"muxes all the way down。"**

> **Real hardware 锚点**:LUT 典型 4 输入——是个 sweet spot。输入太少则需要更多 LUT 串联(又是一个 compute/communication trade-off)。长距离连接由厂商(如 AMD)固定布线,只在局部邻域给你灵活性。

### 05.3 10× 开销从哪来

一个四路 AND(`AND(AND(a,b), AND(c,d))`):

- ASIC 直接实现:**3 个 AND 门**。
- LUT 实现:16-entry 真值表的 mux ≈ **32 个门**。

**因为** 真值表是"穷举每种输入组合"的冗余表达,而直接写门是对同一函数的简洁表达;**所以** 可配置性的代价就是这 ~10× 的门数膨胀(以及对应的 polysilicon 和布线面积)。这就是"FPGA 比 ASIC 贵一个数量级"的微观出处。

## 06. Cache vs Scratchpad:确定性延迟的设计分歧

### 06.1 CPU 非确定性延迟的最大来源:cache

```
CPU die ──[cache]── DDR        每次访存先查 cache,命中则快两个数量级
```

- **因为** cache 比 DDR 快约两个数量级,没有 cache 几乎所有程序慢 100×——cache 对 CPU 跑出合理速度是**绝对必要**的。
- **但** 命中与否取决于环境(其他程序、近期访问历史、cache 替换的随机数)——**所以** cache 是 CPU 运行时间非确定性的最大来源。

### 06.2 Scratchpad:把决策搬到软件

TPU / Groq 的不同哲学:不让硬件偷偷决定数据从 cache 还是 DDR 来,而是**做成两条不同的指令**。

```
TPU die ──[scratchpad]── HBM
          ↑ 一种指令读 scratchpad
                          ↑ 另一种指令读 HBM(软件显式决定)
```

**因为** 数据来源由软件指令显式指定,没有硬件层面的随机命中;**所以** 获得**确定性延迟**。

> **Real hardware 锚点**:Groq 公开宣传过确定性延迟,TPU 核内也有。这正是"Groq 全静态、编译器决定数据放置"的硬件根因——确定性其实是更简单的**起点**,是 CPU 后来主动加入 cache 等机制把它弄成非确定性的。可做确定性 CPU,但市场不青睐,所以没人做了。

> 🔗 衔接 RAM wiki:这条与你 RAM wiki 的 `06-memory-controller` 和 `09-ai-chip-memory-architecture` 直接咬合——scratchpad 模型把"数据放置决策"从 MC 的硬件仲裁前移到了编译期,这是 archax 建模存储层次时必须区分的两种语义(隐式 cache vs 显式 scratchpad)。

## 07. CPU vs GPU core:面积都花哪了

### 07.1 为什么 CPU core 大得多

CPU 仍算 von Neumann:~100 核 × ~16 路向量 ≈ 1000 路并行。但单核大,大头在哪?

- cache + register file:占大量面积,但 GPU 也有对应物,**不是关键区别**。
- ALU 本身:很小。
- **真正的区别:branch predictor**。CPU 里一大块面积专门预测"下一个分支在哪、跳到哪"。GPU **没有**对应物。

**砍掉分支预测 + 收紧 register file,是 GPU 相对 CPU 的主要收益来源。**

### 07.2 branch predictor 在解决什么

```
取指 → 判 boolean → 更新 PC → 从指令存储取目标   ≈ 5ns(= 200 MHz)
但我想跑 1~2 GHz
```

**因为** 处理一条分支指令到知道"该跳哪"要 ~5ns,而想跑的时钟快得多;**所以** 必须在分支结果出来前先跑后续指令(可能跑错,跑错就回滚跳到正确目标)。branch predictor 的职责就是**提前 ~5 个周期预测分支走向**,在还没到那条指令时就开始对的路径。

> AI 加速器(TPU/GPU)workload 分支极少,**所以** 砍掉这块面积几乎无损——这是"为 AI 专门化"省面积的典型案例。

## 08. 脑 vs 芯片:为什么时钟这么快

脑的特征:非结构化稀疏、存算一体、时钟极慢。但 Pope 指出存算一体这点其实芯片也有(systolic array 里权重就地驻留 = 某种存算一体)。真正值得讲的是**时钟速度与能耗**。

**因为** 芯片时钟快是为了高吞吐——GPU 跑 batch 1000,而"我"只有一个,脑不需要 batch 1000。

**那把 GPU 从 GHz 降到 MHz 会不会像脑一样省能?** 不会有 1000× 能效优势:

- 芯片能耗主体是**动态(开关)功耗**:一个 bit 存在电容上,置 1 充电、置 0 放电到地,这个充放电循环耗能。
- 降频 1000× → 翻转次数少 1000× → 能耗少约 1000×,但这只是**近线性**减少,不是数量级的能效**密度**跃升。电路只是"算一次到稳定,然后长时间空转",空转几乎不耗能(漏电忽略)。

> 结论:脑的低功耗不是单纯"慢时钟"能复刻的——慢时钟省的是总能量(因为翻转少),不是每次运算的能效。

## 09. 顶层布局:GPU 就是一堆小 TPU

### 09.1 两种顶层组织

```
GPU:  规则网格的众多近似相同 SM        TPU:  少数粗粒度大单元
  ┌──┬──┬──┬──┐                         ┌──────────────┐
  │SM│SM│SM│SM│                         │  Matrix Unit  │  (大 systolic array)
  ├──┴──┴──┴──┤                         ├──────────────┤
  │    L2     │                         │  Vector Unit  │
  ├──┬──┬──┬──┤                         ├──────────────┤
  │SM│SM│SM│SM│                         │  Matrix Unit  │
  └──┴──┴──┴──┘                         └──────────────┘
```

**本质洞察**:把一个 TPU 缩小(小 matrix unit + 小 vector unit)就成了一个 SM。**GPU = 把许多小 TPU 平铺满整片;SM 里的 tensor core 类比 TPU 的 MXU。**

### 09.2 粗粒度 vs 细粒度的 trade-off

| | TPU(粗粒度) | GPU(细粒度) |
|---|---|---|
| systolic array | 可做大 → 更好摊薄 RF 成本(承接 §03.4) | 被约束成小单元 |
| vector↔matrix 数据通路 | 只能走少数边界(如 2 条线) | SM 内可走多条(如 16 条线) |
| 跨单元数据移动 | SM 内省能、距离短;跨 SM 才贵 | —— |
| 适合的 workload | 大而规则的矩阵乘 | 不规则、需要局部灵活性 |

**因为** TPU 把 vector 和 matrix 粗粒度分离,大量数据要挤过那两条边界线;**而** GPU 到处都是 vector unit,数据走更多线、距离更短(还省能)。**所以** GPU 在 SM 内数据移动便宜,但一旦跨 SM 就变复杂变贵。

### 09.3 MatX 的方向:splittable systolic array

Pope 公开确认 MatX 在做 **splittable systolic array**——"既能当大阵列、也能拆成小阵列"。隐含设计:拿到 GPU 那种"小阵列环绕 SRAM"的局部灵活性,同时丢掉支撑 CUDA 架构所需、占面积的那些东西(如 §07 的 branch predictor 一类)。

> 这正好对应你之前对 MatX 的架构 deep-dive(splittable systolic array、SRAM-first + HBM 混合、面向大 MoE 推理):splittable 本质是想在 §09.2 这张表里"两列都要"——大阵列的 RF 摊薄优势 + 小阵列的数据通路灵活性。

## 建模启示(Modeling Insights for archax)

把这期内容翻译成 archax 的可建模量与抽象决策:

**1. 计算/通信比应成为一等公民的物理量。**
本文六个层级的同一个 trade-off,说明 archax 的 Execution IR 里"data movement bytes / theoretical MACs"这个比值不是某一层的指标,而是**贯穿全层级的不变量**。建议在 IR 里把它做成可在任意聚合粒度(PE / array / core / chip)上求值的派生量,而不只在顶层算一次。

**2. 位宽的二次缩放必须显式建模,不能线性近似。**
乘法器面积 ∝ 位宽²。如果 archax 的 Capability/Constraint 用"FLOP 随位宽线性"来近似(像 B200 前的 Nvidia spec),会系统性低估低精度的面积/能效收益。建模 FP4/FP8 的 area 与 throughput 时,应以 p×q 为基,并显式标注 FP4↔FP8 的非 fungible 程度作为一个架构参数。

**3. register file ↔ systolic array 的面积预算应是一个显式的探索维度。**
§02.5 + §03.4 给出的"数据搬运 vs 计算"面积账,正好是一个可参数化的 sizing 旋钮(RF 深度、array 边长)。这应进入 archax 的 microarchitecture M1 结构层,作为 Pareto 前沿三元组里 microarchitecture 组合的一个坐标轴。**必须显式建模的状态变量**:array 边长 N、RF entry 数、RF 端口数、每周期跨 RF 边界的 byte 数。

**4. weight-stationary 的 trickle-feed 是"带宽而非延迟"的典型,建模时要分离这两个量。**
权重载入(罕见、可慢、窄带宽)与向量流(每周期、x 量级带宽)是两条语义完全不同的数据移动。archax 的 Interaction 抽象应能区分"一次性配置流"与"稳态数据流",并对前者只计带宽/面积、对后者计延迟+带宽。这也是你 3D 笔记里"宽而慢 vs SerDes"区分的同源问题。

**5. cache vs scratchpad 是两种不可混淆的 Interaction 语义。**
隐式 cache(硬件决定来源、非确定性命中)与显式 scratchpad(软件指令决定来源、确定性)在仿真里要用不同模型:cache 需要命中率/替换策略/非确定性 latency 分布;scratchpad 是编译期可解析的确定性访存。对 archax 的目标(面向 Groq 式静态、编译器决定数据放置的架构),scratchpad 模型是默认,但要保留对 cache 语义的建模能力以做对照。**事件类型建议**:`ScratchpadAccess`(确定 latency)vs `CacheAccess`(带命中/未命中分支)。

**6. 顶层"粗粒度 vs 细粒度"是 system-level S1 的一个根决策。**
§09.2 的表就是一个 system-level 候选的分类轴:粗粒度(大 array,跨单元数据贵)vs 细粒度(小 array 平铺,局部便宜跨片贵)。splittable systolic array 是这条轴上的一个非端点解。建模时跨单元数据移动的边界带宽(TPU 的"2 条线" vs GPU 的"16 条线")应是一个可量化参数,直接喂给 data-movement-first 的代价函数。

**7. 时钟/流水层在 archax 当前抽象层级大多可折叠,但有一个例外。**
pipeline register insertion 是纯 area↔frequency trade-off,M2 cycle-level 之下大多可抽象掉。**唯一必须保留的**是带反馈环逻辑设定的关键路径下界——它给出"这个微架构能跑多快"的硬上限,直接影响 throughput = 每周期工作量 × 频率 的频率项。若 archax 要在 M2 层给出可信的频率估计,需要对累加器/规约这类反馈环单独建模其关键路径,而非把所有逻辑当可任意切分的流水线。
```
