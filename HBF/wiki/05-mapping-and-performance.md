# 地址映射、并行度与带宽

上级：[HBF Wiki](./README.md)

高聚合带宽需要请求到达足够多的可用资源，并且下游接口能及时返回数据。地址交错可以帮助分散访问，但交错粒度、资源映射和请求并发必须一起考虑。

## 先区分两个映射阶段

OCP HBF v0.7 第 4.6 节描述：host 软件配置全局地址，并把地址分配到各 UCIe channel 的局部地址空间；base die 再把该 channel 的局部地址映射到 core die 的 bank、die 和 block。规范还描述了从配置获取相关信息的方式。[OCP HBF v0.7](https://www.opencompute.org/documents/ocp-hbf-architecture-specification-v0-7-0-final-pdf/)

因此，一个地址的教学示意可以写成：

1. **host 侧**：全局地址 → 选定的 channel 与 channel 局部地址。
2. **base die 侧**：局部地址 → 内部资源及数据位置。

这不是通用的地址位定义。尤其不能把 host 地址直接画成固定的 channel、die、plane、block、page 位字段，并声称它就是某一产品的真实映射。

## 一个可计算的交错例子

**假设**有 4 个 channel；全局字节地址从 0 开始；每 4 KiB 为一个条带，依次轮转到 channel 0–3。令 A 是字节地址，p 是 page 序号：

- p = ⌊A / 4096⌋。
- channel = p mod 4。
- channel 内 page 序号 = ⌊p / 4⌋。
- page 内字节偏移 = A mod 4096。

| 全局地址范围 | channel | channel 内 page 序号 |
| --- | ---: | ---: |
| 0–4095 | 0 | 0 |
| 4096–8191 | 1 | 0 |
| 8192–12287 | 2 | 0 |
| 12288–16383 | 3 | 0 |
| 16384–20479 | 0 | 1 |

连续读取前 16 KiB 时，四个 page 分散到四个 channel，有机会并行。只读取第一个 page 内的 64 B 时，这个例子只访问 channel 0。即使请求在 page 内连续，也不代表一定能使用所有 channel。

这是人为构造的 host 侧映射，**不是 OCP 的强制位布局**。假设每个数据范围恰好对应所示 channel，并且目标资源可并行；实际还要考虑 base die 映射、地址对齐、冲突和通路占用。v0.7 中的虚拟 AXI 接口交错与 host UCIe channel 交错也不是同一层概念。

## 为什么连续、稀疏和多模型负载不同

大块连续权重可按合适粒度分散到多个 channel，并通过预取提供并发。但如果只需要一个小片段，实际读取和搬运的数据可能大于有效数据。是否存在这种放大以及放大多少，取决于缓存、物理读取粒度和访问局部性。

MoE 在一次推理中只激活部分 expert。若活跃 expert 的数据集中在少数 channel，可能出现热点；若过度分散，小请求又可能带来更多调度和无用搬运。多个模型同时运行时，也可以考虑为模型划分不同 channel，以降低互相干扰；代价是单个模型可能不能使用全部带宽。OCP v0.7 第 13 节给出了交错与非交错的应用示例，并不是对所有工作负载的性能保证。

## 从资源到一个带宽上界

先构造一个理想模型：有 M 个独立、不可流水的阵列服务资源；每个资源每 T 秒完成一个 S 字节的有效读取；请求充足、均匀且没有额外冲突。所有计入带宽的读取都经过这些阵列资源，不考虑缓存命中。若返回链路带宽为 B<sub>link</sub>，则：

**有效带宽 ≤ min(B<sub>link</sub>, M × S / T)。**

例如，假设 M = 8、S = 4 KiB、T = 10 µs，则阵列一侧上界是 **8 × 4096 / 0.00001 = 3.2768 GB/s**。这只是计算示例，不是 HBF 的测量值。若资源可以流水，应该把 T 定义成可持续发起间隔，不能错误地把端到端延迟当成独占服务时间。

实际有效带宽还可能受 host 发起速率、bank 冲突、ECC、缓存命中、内部链路、流控和热限制约束。配置多个资源只是必要条件之一。

## 在途请求和延迟的关系

在稳定、长期平均的系统中，Little 定律给出：**平均在途请求数 = 请求完成速率 × 平均端到端时间**。如果每个逻辑请求都返回 4 KiB 有效数据，目标带宽为 1.6 TB/s，且相同观察边界内平均时间假设为 10 µs，则平均在途约为：

**(1.6 × 10¹² B/s ÷ 4096 B) × 10 µs ≈ 3906 个逻辑请求。**

这里 10 µs 纯属假设，不是 HBF 延迟。平均时间包括该观察边界内的排队；计算也不证明某个设备支持这个队列深度，更不能推出尾延迟或保证达到目标带宽。若一个 4 KiB 逻辑读取拆成多个 64 B 事务，两种请求计数边界也不能混用。
