# 为什么架构师必须懂工艺与封装

上级:[芯片制造与封测 Wiki 总览](./README.md)
相关:[为什么工艺红利在让位于封装红利](./why-process-and-packaging-matter-now.md), [工艺节点演化与 PPA 取舍](../02-front-end-fabrication/process-nodes-and-ppa-tradeoffs.md), [从架构需求反推工艺与封装选型](../06-cross-cutting-engineering/from-architecture-to-process-selection.md)

## 这页在回答什么问题

为什么一个系统软件和芯片架构背景的人，不能把工艺与封装视为“后端实现细节”。更具体地说，哪些架构决策会直接变成制造、封装、测试和可靠性约束。

## 架构决策会落到物理世界

架构师看到的是算力、带宽、片上存储、NoC 拓扑、I/O、功耗和 SKU；制造团队看到的是 die 面积、金属层拥塞、功耗密度、缺陷密度、良率、封装尺寸、热阻、warpage 和测试覆盖率。这两套语言描述的是同一个产品，只是视角不同。

当架构师把 SRAM 做大，前道问题会变成 bitcell scaling、阵列良率、漏电和面积占比；当架构师把 NoC 做宽，物理问题会变成 BEOL 走线、时钟、拥塞和功耗；当架构师选择 HBM，系统问题会变成逻辑 die 与 HBM stack 的近距互连、package PDN、热耦合和 KGD。架构定义越靠近性能极限，制造和封测越早成为一等约束。

## 为什么不能只等 PPA 报告

很多制造与封装约束在 RTL 或早期性能模型里看不见。模型可以轻松给出更大的 array、更宽的 memory interface、更密的 chiplet fabric，但这些对象最终要落在 design rule、reticle、package routing、micro-bump pitch、substrate 层数、热路径和测试接触窗口上。

如果这些约束在产品定义后期才出现，调整成本会非常高。把单 die 拆成 chiplet 不是简单“切开再连上”，会引入 die-to-die PHY、协议、封装路线、KGD、封装良率和失效隔离。把外存从 GDDR/LPDDR 换成 HBM，也不是把内存控制器带宽调大，而是把产品形态改成高价值复杂封装。

## 架构师真正需要掌握什么

这份 wiki 不要求架构师记住每种设备型号、化学材料或光刻算法。需要掌握的是三类判断。

| 判断 | 架构师要问的问题 | 错过后的后果 |
| --- | --- | --- |
| 工艺节点判断 | 这个节点给我的密度、频率、能耗和 SRAM 面积收益是否足以覆盖成本与设计复杂度 | 节点选择只看 marketing node，低估 PPA 与成本风险 |
| 封装路线判断 | 带宽、die 数量、package 尺寸、热和供电是否需要 2.5D/3D 或 fan-out/bridge | 把封装当作后置选项，导致物理方案闭合不了 |
| 测试/良率判断 | 组合 die、HBM、interposer、substrate 后的有效良率是否还能支撑产品价格 | 只看单 die 良率，低估 package 报废成本 |

## 与 BUS、RAM、NoC 的关系

BUS、RAM、NoC 讨论的是逻辑结构和数据移动路径；制造与封测回答这些结构为什么有物理边界。BUS 里的宽总线和返回路径最终会受 BEOL 布线、时序和功耗约束；RAM 里的 SRAM/DRAM/HBM 选择最终会受工艺 scaling 与封装形态约束；NoC 里的 chiplet 与 die-to-die 互连最终会受 package routing、bump pitch、热和测试约束。

因此，这份 wiki 是前面几份架构 wiki 的物理基底。它不替代 BUS/RAM/NoC 的协议和微架构讨论，而是解释为什么某些看起来合理的架构在物理产品里代价很高，为什么某些封装路线会改变架构探索的可行解空间。

## 常见误解

常见误解是“架构阶段只需要定功能和 PPA，工艺封装后面再选”。实际情况是，工艺和封装会反过来限定 PPA 能达到的区域。一个需要数 TB/s 级外存带宽的 AI 芯片，在架构定义时就已经接近 HBM 与先进封装问题；一个要跨 die 扩展算力的设计，在 topology 还没定完时就已经进入封装互连和良率问题。

另一个误解是“先进封装只是把 die 放近一点”。实际情况是，先进封装把互连、供电、热、机械应力、测试和供应链耦合成一个系统优化问题。距离变短只是收益之一，代价是更多制造节点、更多界面、更强良率耦合和更难的故障定位。

## 一句话理解

架构师必须懂工艺与封装，因为许多架构选择不是抽象 PPA 选择，而是在提前选择制造难度、封装路线、测试策略和量产风险。

## 架构师启示

如果我在做一颗大算力 NPU，早期架构评审不能只比较 TOPS、SRAM、NoC bandwidth 和 memory bandwidth，还要同时问：目标 die 面积是否逼近良率拐点；SRAM 是否在下一节点继续有效缩放；HBM stack 数量是否要求 CoWoS 类 2.5D 平台；chiplet 拆分是否会让 D2D 互连和 KGD 成为主风险。

这会改变架构探索的排序。一个理论上性能更高的方案，如果需要过大的 die、过密的封装互连或无法接受的组合良率，应该在架构阶段就降权，而不是等物理设计或封装团队最后判死刑。
