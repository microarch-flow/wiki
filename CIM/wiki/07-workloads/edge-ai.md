# Edge AI 与 Always-On 场景

## 为什么这是重点场景

很多 CIM 路线未必先在数据中心落地，反而更可能先出现在极低功耗端侧设备。

更准确地说，很多路线在 edge 更有现实感，不是因为 edge“技术更简单”，而是因为：

- 客户对功耗和待机更敏感
- 模型规模往往更可控
- 固定功能推理更常见
- 少搬数据本身就能转化成明确产品价值

也就是说，edge 场景更容易把 `CIM` 的局部优势转成系统优势。

## 为什么 edge 常常比 data center 更适合成为第一站

在很多数据中心 workload 里，系统已经有：

- 很强的 `GPU / NPU`
- 很成熟的软件栈
- 很高的吞吐优化

这意味着 `CIM` 要切进去，必须证明自己不只是“能算”，而是：

- 明显减少系统成本
- 明显改善 memory-bound 部分
- 值得客户改软硬件栈

但在 edge 端，问题往往换成：

- 电池能不能撑住
- 待机功耗够不够低
- 封装和散热能不能放进设备
- BOM 能不能接受

这时，哪怕不是极致通用算力，只要：

- 功耗明显下降
- 模型能稳定跑
- 客户不必频繁联网

路线就可能成立。

## Edge 场景真正关心的不是峰值算力

很多 edge 产品更关心的是：

- `mW` 级或低 `W` 级功耗
- 唤醒延迟
- 常开待机功耗
- 本地响应时间
- 封装和热设计
- 成本

因此，edge 判断不能只看：

- `TOPS`
- `TOPS/W`

更该看：

- energy per inference
- standby power
- local memory fit
- 设备级热预算

## 五个最关键的场景判断维度

## 1. 功耗预算

这是 edge 场景最先卡住的地方。

要继续问：

- 设备允许的是 `mW`、几百 `mW`，还是几 `W`
- 推理是连续运行，还是间歇触发
- 常开检测与重负载推理是否分离

### 一个关键现实

很多路线在“短时间跑起来”时没问题，但一旦变成持续运行，就会暴露：

- 动态功耗过高
- 待机收益不明显
- 热设计超标

## 2. 模型规模

Edge 不等于模型一定小，但模型通常比数据中心更受：

- 本地存储容量
- 片上 SRAM
- 外部 DRAM 是否存在
- 带宽与功耗

约束。

这意味着更适合的通常是：

- 小模型
- 规整模型
- 固定权重推理
- 明确任务导向模型

如果一个方案只能在需要大量外部 DRAM 的模型上成立，那么它的 edge 价值通常会被削弱。

## 3. 权重是否固定、模型是否常更新

这是判断 `CIM` 路线能否贴合 edge 的关键点。

### 更适合的情况

- 模型长期稳定
- 权重可离线编程
- OTA 更新频率低
- 主要是 inference，不涉及频繁在线训练

### 更不适合的情况

- 权重频繁更新
- 需要高频个性化训练
- 模型版本切换频繁

这也是为什么很多 `analog / ReRAM-CIM` 路线更适合固定模型 edge，而不适合高频动态更新场景。

## 4. 待机与唤醒行为

很多端侧产品不是一直满载推理，而是：

- 大部分时间待机
- 少量时间被事件触发
- 触发后要求快速响应

因此要继续问：

- 常开检测路径功耗是多少
- 唤醒后首帧或首个推理延迟是多少
- 为了实现 always-on，是否仍需频繁访问外部存储

如果一个方案在高负载下很省电，但待机和唤醒路径很重，它在 always-on 产品里未必真的占优。

## 5. 成本、封装与热约束

Edge 产品往往对：

- 封装尺寸
- PCB 面积
- 散热器空间
- BOM 成本

非常敏感。

因此某个路线即使技术上成立，也可能因为：

- 需要太多外围
- 需要外部 DRAM
- 封装复杂
- 认证成本高

而失去实际吸引力。

## 不同 edge 子场景差别很大

## 1. 可穿戴与超低功耗传感器侧

更关心：

- 极低待机功耗
- 极小模型
- 长电池寿命
- 快速事件检测

更适合的通常是：

- 固定模型
- 任务明确的 always-on 检测
- 小型 `SRAM-CIM` 或超低功耗 `analog CIM`

这类场景对“能不能长时间常开”比“峰值吞吐多高”更敏感。

## 2. IoT / 智能家居 / 边缘摄像头

更关心：

- 功耗与成本平衡
- 本地推理隐私
- 连接不稳定时的独立工作能力
- 中等规模视觉或音频模型

这类场景通常允许比可穿戴更高的功耗，但仍不接受数据中心式代价。

## 3. 手机 / 移动终端

更关心：

- 与现有 `SoC / NPU / ISP` 的集成
- 电池与热约束
- 软件生态兼容
- 多任务和复杂系统调度

这类场景未必需要单独的 `CIM` 芯片，更可能需要：

- 片上宏级集成
- 与现有数字系统深度耦合

因此 `SRAM-CIM / digital CIM` 往往更自然。

## 4. 车载 edge

更关心：

- 长期可靠性
- 温区
- 认证
- 安全冗余
- 持续供货和可维护性

这意味着即使某条路线功耗很好，也必须再跨过：

- 更重的验证周期
- 更高的稳定性门槛

所以车载不是“普通 edge 的放大版”，而是一个工程要求显著更高的子类。

## 哪些技术路线在 edge 更可能成立

## SRAM-CIM / Digital CIM

更可能成立的原因：

- 更兼容标准 `CMOS`
- 更容易和 `MCU / SoC / NPU` 集成
- 精度路径和验证路径更稳

更适合：

- 手机
- IoT
- 边缘摄像头
- 小模型本地推理

## ReRAM / Analog CIM

更可能成立的原因：

- 理论能效高
- 固定权重推理很有吸引力
- 非易失特性对某些 always-on 场景有价值

但要格外警惕：

- 校准
- 漂移
- 长期稳定性
- 量产一致性

它更适合被当成“高潜力但工程门槛高”的 edge 路线。

## DRAM / HBM-PIM

通常不是最自然的超低功耗 edge 路线。

它更像：

- 边缘服务器
- 车路协同节点
- 更接近 infra 的 edge 计算

也就是说，它更适合“大工作集 edge”而不是“电池端 edge”。

## 为什么 CNN 曾长期主导 edge 讨论

因为在很多早期 edge 场景里：

- 模型更小
- 卷积更规整
- 权重复用高
- 映射和工具链更容易起步

这也是 `CNN` 长期是早期 `CIM` 论文主战场的原因。

但今天需要继续问：

- 场景是不是已经转向更复杂的 `Transformer`
- 是否开始出现 edge LLM 或多模态需求
- 原先对 `CNN` 有效的映射逻辑还能否直接复用

## Edge LLM 为什么要单独看

今天有些路线会开始强调：

- 小型本地语言模型
- 端侧 agent
- 本地语音和多模态理解

但 edge LLM 和传统 edge CNN 不一样，必须继续问：

- 模型是不是足够小
- 权重能否常驻本地
- `prefill` 和 `decode` 哪个是主要瓶颈
- 外部内存访问是否仍然太重

因此，edge LLM 不是一句“端侧可跑”就能成立，而要继续拆：

- 是固定子算子加速
- 还是整条 token 路径真的受益

## 一张实用的适配度表

| 场景 | 更关注什么 | 更可能合适的路线 |
| --- | --- | --- |
| 可穿戴 / sensor-side | 待机、常开、超低功耗 | 小型 `SRAM-CIM`、部分 `analog CIM` |
| IoT / 智能家居 | 功耗、成本、本地隐私 | `SRAM-CIM / digital CIM` |
| 手机 / 移动终端 | SoC 集成、热约束、软件生态 | `SRAM-CIM / digital CIM` |
| 车载 edge | 可靠性、温区、认证 | 更稳妥的数字友好路线优先 |
| 边缘服务器 / infra edge | 大工作集、带宽、系统协同 | `DRAM / HBM-PIM` 或 memory-centric 路线 |

## 读论文或公司材料时建议直接追问

1. 目标 edge 场景到底是哪一类，不要只写 `edge AI`。
2. 功耗预算是 `mW`、`sub-W` 还是几 `W`？
3. 模型是固定部署，还是需要频繁更新？
4. 待机与唤醒路径的功耗和延迟是多少？
5. 是否依赖外部 DRAM 或复杂封装？
6. 目标场景如果是车载或工业，可靠性和认证怎么过？

## 一个最实用的判断原则

如果一个路线声称“适合 edge”，但没有清楚回答：

- 是哪一种 edge
- 功耗预算是多少
- 模型规模和更新方式是什么
- 待机和唤醒行为如何
- 成本、封装、热和认证是否可接受

那么这个“适合 edge”的说法通常还太粗。
