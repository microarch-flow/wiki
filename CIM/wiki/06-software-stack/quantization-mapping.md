# 量化与映射

## 为什么这一页不能只谈位宽

很多人一提 `CIM` 量化，第一反应是：

- 支不支持 `INT8`
- 能不能做到 `INT4`
- 精度掉多少

但在真实 `CIM` 系统里，位宽从来不是一个孤立变量。它同时受下面几类因素约束：

- 阵列本身能表达多少信息
- 输入与权重怎么编码
- `ADC / DAC / SA` 的读写精度与成本
- 非理想因素会把多少误差带进最终结果
- 模型本身能容忍多大的量化和硬件噪声

因此，这一页的重点不是简单比较 `INT4` 和 `INT8`，而是建立一套“精度预算”视角：

> 最终可用精度，是器件、电路、映射和模型共同决定的。

## 一条更实用的分析链

可以把量化与映射问题看成五级链条：

1. 模型想要什么数值精度
2. 编码方式允许什么位宽表达
3. 阵列和外围能承受什么数值路径
4. 映射工具如何把模型切到硬件约束下
5. 最终模型 accuracy 还能保住多少

只要其中任意一环过弱，理论位宽就很难转化成真实可用精度。

## 1. 模型层：不同模型对精度的容忍度不同

### 为什么先从模型层看

因为不是所有模型都一样敏感。

有些模型或子图：

- 对 `INT8` 很稳
- 对 `INT4` 仍可接受
- 对更低位宽非常敏感

而有些模型即使形式上能量化，也会因为：

- attention 路径
- normalization
- 累加范围
- 激活动态范围

而迅速掉精度。

### 需要先问的几个问题

- 权重和激活哪个更敏感
- 哪些层是精度瓶颈层
- 目标是保持分类精度、token quality，还是只保 kernel 误差

### 一个关键现实

同一个模型里，不同子图常常需要不同量化策略。

因此“全模型统一 `INT4`”往往只是表述方便，不一定是最佳部署方式。

## 2. 编码层：位宽不等于真实表达能力

### 为什么编码方式会改变问题本质

在 `CIM` 里，数值通常不是直接以理想整数存在，而是通过：

- `bit-serial`
- `bit-parallel`
- 电压、电流、电荷
- multi-level cell conductance

来表达。

因此同样写成“支持 `INT8`”，其真实含义可能完全不同：

- 是真的一次性 8bit 并行表达
- 还是通过 bit-serial 多周期展开
- 是权重 8bit、激活 8bit
- 还是只有其中一边是真多 bit

### 常见编码差异

- 权重可能是 multi-level cell 或差分对编码
- 激活可能是 bit-serial 输入
- partial sum 可能在阵列外用更高精度累加

### 这会带来什么后果

- 吞吐不再只由标称位宽决定
- 面积和外围成本可能随位宽快速增长
- 精度损失可能集中在输入侧、读出侧或累加侧

## 3. 电路与阵列层：精度受硬件路径约束

### 为什么“理论位宽”常常高于“可用位宽”

因为真正限制系统的，往往不是数学表示，而是：

- 阵列误差
- `ADC / DAC` 精度
- 读出噪声
- `IR drop`
- 电导漂移

这意味着某条路线即使在算法上能写成 `INT8`，在硬件上也可能只有：

- 低位真实有效
- 高位成本过高
- 高位误差无法稳定保持

### 不同路线的典型限制

#### SRAM-CIM / Digital CIM

更常见的限制是：

- 面积和布线成本
- bit-serial 展开的吞吐损失
- 本地累加路径复杂度

#### Analog / ReRAM-CIM

更常见的限制是：

- `ADC` 精度与能耗
- conductance variation
- drift 与 retention
- 大阵列下的误差传播

#### DRAM / HBM-PIM

精度约束更常来自：

- 支持的指令集合
- host / memory-side 协同方式
- memory-side logic 的实际数值路径

## 4. 映射层：量化要和硬件约束一起做

### 为什么不能把量化和 mapping 分开

如果先独立做模型量化，再让编译器去硬映射到 `CIM`，常常会出现：

- 某些层超出阵列支持范围
- 某些张量动态范围不适合当前读出链
- mapping 后的误差与原量化假设不一致

因此，更实用的方法通常是：

- `quantization-aware mapping`
- `hardware-aware quantization`
- `variation-aware mapping`

也就是在量化阶段就把硬件约束纳入。

### 映射层常见需要感知的因素

- array shape
- tile shape
- 输入位宽展开方式
- 权重是否常驻
- partial sum 精度路径
- `ADC / DAC` 限制
- 非理想误差分布

### 一个常见错误

只用软件仿真中的低位模型精度，代替真实硬件映射后的精度。

这通常会低估：

- 阵列误差
- 读出误差
- 映射切块后累加路径变化

## 5. 模型结果层：最终看的是任务精度，不是局部误差

### 为什么不能只看 kernel 误差

硬件论文里很容易报告：

- `MVM error`
- `ADC quantization error`
- `RMSE`

这些都重要，但客户真正关心的是：

- 分类准确率
- 检测精度
- token quality
- 端到端任务表现

### 一个关键判断

局部数值误差低，不自动代表模型级 accuracy 高。

反过来，局部误差不小，也不一定说明模型不可用，前提是：

- 误差可建模
- 训练和映射已做补偿

因此，量化与映射的最终目标不是“局部误差最小”，而是“任务精度与系统收益共同可接受”。

## 权重和激活通常不该一刀切处理

### 权重

更常见特点：

- 可离线量化
- 可预先编程
- 可结合器件特性做特殊编码

### 激活

更常见特点：

- 动态范围变化更大
- 运行时产生
- 更受输入编码和 `DAC` 成本影响

### partial sum

常常需要：

- 比输入和权重更高的内部累加精度
- 在阵列外或 tile 级做更稳定的合并

因此很多方案即使宣称低位输入和权重，也不代表整个数值路径都低位。

## 什么时候量化感知训练更重要

`QAT` 往往更重要的情况包括：

- 目标位宽较低，如 `INT4` 或更低
- 模型本身对精度较敏感
- 硬件误差不是纯理想舍入噪声
- 路线包含 analog / mixed-signal 非理想因素

在这些情况下，只做后训练量化通常不够。

## 什么时候还需要“硬件感知训练”

如果误差来源不仅是普通量化，而还包括：

- `ADC` 量化误差
- 阵列噪声
- conductance drift
- `IR drop`

那么更合理的做法往往是：

- `quantization-aware training`
- `hardware-in-the-loop` 或 hardware-aware training
- variation-aware calibration / mapping

也就是说，训练过程需要看到更接近真实硬件的误差模型。

## 一个实用的位宽判断框架

当一个方案宣称支持某个精度时，建议顺着下面的问题链走：

1. 权重和激活是否都是真多 bit？
2. 多 bit 是并行实现，还是 bit-serial 展开？
3. `ADC / DAC` 的精度和能耗是否把这一路径算全了？
4. partial sum 在哪里累加，内部用什么精度？
5. 精度结果是 kernel-level，还是 model-level？

## 不同常见位宽该怎么理解

## `INT8`

更像一个“工程上较稳妥”的中间点。

优点：

- 模型适配范围较宽
- 精度风险相对可控

代价：

- 对 `ADC / DAC`、bitline 动态范围或本地累加路径压力更大

## `INT4`

是很多 `CIM` 路线更现实的甜点区间。

优点：

- 面积、带宽、功耗和模型精度之间更容易平衡

风险：

- 某些模型或层会明显掉精度
- 更依赖 `QAT` 与硬件感知 mapping

## 更低位宽

通常适合：

- 特定 edge 场景
- 固定模型
- 对精度损失可容忍的任务

但它更容易把问题转成：

- 客户场景是否接受
- 是否真的还有足够模型表达能力

## 读论文或公司材料时建议直接追问

1. 权重、激活、partial sum 分别是什么精度？
2. 位宽是并行支持，还是通过 bit-serial 展开？
3. `ADC / DAC`、读出与累加成本是否完整计入？
4. 精度结果是否在真实硬件误差模型下验证？
5. 使用的是 PTQ、QAT，还是 hardware-aware training？

## 一个最实用的判断原则

如果一个方案只写：

- 支持 `INT4` 或 `INT8`
- 精度损失很小

但没有说明：

- 编码方式
- `ADC / DAC` 约束
- non-idealities 是否纳入
- 映射后精度口径

那么这个“支持某位宽”的说法通常还不够可判断。
