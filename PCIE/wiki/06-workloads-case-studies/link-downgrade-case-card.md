## 这页在回答什么问题

为什么设备“能用但很慢”时，链路降宽或降代际常常是第一批必须排掉的问题。

## 典型现象

- 理论上应该是更高代际或更宽链路，实际协商结果更低
- 吞吐始终上不去，但软件队列和 DMA 深度看起来正常
- 某些平台或插槽表现正常，另一些明显偏慢

## 最短排查链

1. 看 negotiated speed / width
2. 看是否有重训练、错误计数、AER 线索
3. 看平台插槽、switch、转接板或线缆路径差异
4. 再看是不是上层 workload 本身没有把链路喂满

## 最常见误判

- 只看应用吞吐，不看链路协商状态
- 把 host memory 瓶颈误判成链路降速
- 把单次小事务低效误判成“物理层一定出问题”

## 最值得抄走的判断

链路降速是 `上限变低`，但“感觉慢”不一定都来自降速；必须把链路上限问题和事务组织问题拆开。

## 一句话理解

先确认链路有没有按预期跑满代际和宽度，再谈 credit、completion 和软件队列是否成为下一层瓶颈。
