## 这页在回答什么问题

面对 AXI、AHB、APB、TileLink、crossbar、fabric 这些名字时，为什么应该先按设计约束分类，而不是按协议缩写背诵。

## 名字不是分类维度

BUS/互连的名字来自不同层级：`AXI` 是协议族，`APB` 是低复杂度外设访问约定，`crossbar` 是拓扑形态，`fabric` 是实现集合的统称。把这些词放在同一层级比较，会把“协议能力”“物理组织”“系统角色”混成一团。

架构师真正关心的问题是：它连接谁，承载什么流量，允许多少并发，是否必须保序，错误如何返回，仲裁会怎样影响延迟，物理实现能不能收敛时序。协议缩写只有在这些约束明确之后才有意义。

例如，外设寄存器路径和 DMA 到 DDR 的主数据路径都可以是 memory-mapped，但它们不该放进同一类性能模型。前者的主约束是简单、可验证、软件语义清楚；后者的主约束是吞吐、burst、outstanding 和共享资源上的尾延迟。如果只按“都是总线”分类，模型会抹掉真正决定系统行为的差异。

## 系统角色决定优化目标

分类 BUS 的第一问不是“它是不是 AXI”，而是“它服务哪条系统路径”。CPU 主干访问强调延迟和顺序语义，因为 load/store 的完成时间会暴露给执行流；DMA 数据路径强调持续带宽和 outstanding 深度，因为它要把长数据流送进 memory system；外设配置路径强调简单可靠，因为它服务的是状态寄存器而不是数据面；debug/boot 路径强调可达性，因为它必须在系统尚未完全初始化时仍能工作。

系统角色决定后续维度的权重。控制路径可以牺牲吞吐换简单性，数据搬运路径不能；debug 路径可以慢，但不能依赖一串尚未打开的复杂 fabric；一致性路径可以付出协议状态成本，但必须维护软件可观察的内存语义。

## 拓扑决定冲突在哪里发生

拓扑不是框图风格，而是冲突位置和扩展成本的定义。单共享总线把所有 master 和 slave 放到同一个仲裁点上，优点是简单、面积小、行为容易推断；代价是并发访问天然互斥，系统规模上来后，带宽、尾延迟和时序都会变成问题。

Bus matrix 或 crossbar 把全局互斥放宽到路径互斥。两个 master 访问不同 slave 时可以并行推进；代价是端口数增加会推高面积、布线和仲裁复杂度。分层互连把系统拆成主干、bridge、外设子树，让高性能路径不被低速外设拖住；代价是 bridge 会引入额外延迟、缓冲和顺序边界。

所以拓扑分类要回答的是：竞争发生在全局总线、目标端口、中间链路、bridge FIFO，还是 memory controller 前的队列。这个答案比协议名字更直接决定性能模型该在哪里放仲裁器和队列。

## 事务能力决定能隐藏多少延迟

简单总线可以把一次访问理解为“发地址，等数据或响应”。这种模型容易实现、容易验证，但只要下游 slave、bridge 或 memory controller 没有完成，发起方就会被阻塞。

Burst、split transaction、multiple outstanding、独立读写路径，都是围绕同一个矛盾演化出来的：物理系统里地址传输、数据传输、目标服务和返回响应的节奏并不一致。如果协议强行把它们绑成一个不可拆的动作，互连就会在等待中空转。

这些能力不是越多越好。更多 outstanding 需要更多 tag、buffer 和回收状态；burst 提高吞吐，也可能增加占路时间，让短请求尾延迟变差；独立通道提高并行度，但验证状态空间更大。分类时要看 workload 是否能利用这些能力，而不是看到“支持并发”就默认更优。

## 顺序模型决定并行度和可见性

顺序模型描述多个 transaction 发出之后，完成顺序能不能变化，变化到什么程度，谁负责恢复可观察语义。

严格顺序最容易理解，也最容易建模。请求按发出顺序被接受、执行、返回，软件不需要额外理解互连重排；代价是一个慢访问会挡住后面的快访问。允许乱序完成可以释放硬件并行度，让不同 slave、不同 bank 或不同路径各自推进；代价是协议必须提供 response matching、barrier 或 ordering rule，master 和软件也必须在需要顺序时显式约束。

因此，顺序模型不是协议文档里的附加条款，而是性能和正确性的分界线。只看带宽不看顺序，模型会高估系统；把所有路径都按全局顺序建模，又会低估现代互连能释放的并行度。

## 共享语义决定协议边界

不是所有互连都需要处理 cache coherence。当 DMA 不参与 cache coherent domain、外设寄存器不被 cacheable 访问、NPU 本地 SRAM 由显式搬运管理时，non-coherent memory-mapped transaction 就足够描述行为：地址、数据、响应和必要属性定义访问闭环，cache 可见性由软件、驱动或更上层机制保证。

当多个 cacheable agent 共享同一份内存视图时，互连就不再只是搬运请求，还要参与“谁拥有最新数据、谁可以写、哪些副本需要失效”这类状态维护。一致性互连和普通高性能数据总线解决的不是同一个问题：前者额外承担共享内存语义，后者主要承担传输、仲裁和返回。

这个维度的作用是防止模型过轻或过重。把 coherent path 当作普通 BUS，会漏掉一致性事务；把所有 DMA 或外设路径都建成 coherent fabric，又会引入不必要的状态和验证成本。

## 协议名只是坐标系里的落点

常见协议可以放回这些维度里理解。`APB` 主要落在低复杂度、低并发、外设寄存器路径；它牺牲吞吐和流水能力，换来小面积、低功耗和容易验证。`AHB/AHB-Lite` 更适合中等复杂度片上访问，顺序语义更强，系统规模不大时实现成本可控。`AXI` 面向更高吞吐和更强并发，用通道拆分和 outstanding 能力隐藏延迟，代价是状态、buffer、验证和互连实现复杂度上升。`TileLink` 把通道能力、缓存一致性能力和节点参数放进同一套可配置框架里，因此更适合需要随 SoC 生成过程裁剪或扩展协议能力的设计。

这些描述不是为了背“APB 慢、AXI 快”。更准确的判断是：APB 把简单可控作为主约束，AXI 把并发和吞吐作为主约束，coherent 协议把共享内存语义作为主约束。名字是结果，约束才是原因。

## 常见误解

- “协议名决定性能”：同样叫 AXI 的路径，也可能被 slave、bridge、ID 深度或返回路径限制住。
- “拓扑越强越好”：crossbar 提供更多并发，但面积、布线、仲裁和验证成本也会上升。
- “顺序越强越安全”：强顺序降低软件理解成本，也会压掉硬件本来可以利用的并行度。

## 一句话理解

分类 BUS 最有效的方式不是背协议缩写，而是先判断它服务的系统角色，再沿着拓扑、事务能力、顺序模型、共享语义和实现成本这些维度定位它。

## 建模启示

在 cycle-level 或 event-driven 仿真里，BUS/互连不应该先被建模成某个协议名字，而应该先被建模成一组约束：端点连接关系、仲裁位置、可并发 transaction 数、请求与响应的匹配规则、顺序约束、buffer 深度和 backpressure 传播方式。

如果只关心性能，协议细节可以折叠成少数关键状态：每个入口的 pending queue、每个出口或链路的 busy 状态、outstanding 计数、burst 剩余拍数、仲裁器当前选择、response 返回时间。具体信号名、精确编码、低频配置字段可以抽象掉；但一次访问仍然至少要拆成 request accepted、data movement、response generated、response consumed 这些阶段，否则无法表达排队、流水和反压。

如果关心功能验证，抽象边界要更低：ID matching、burst 边界、错误响应、barrier/order rule、读写方向的独立推进、bridge 两侧的顺序变化都必须保留。建模时最危险的简化是用协议名直接推导性能，例如把所有 AXI 路径都设成高并发，或者把所有 APB 访问都设成固定一拍；更稳妥的做法是把协议名只当作默认参数来源，再用系统角色、拓扑和事务能力校准模型。
