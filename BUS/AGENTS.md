## 重写的深度定位

### 正文：架构师视角

每一个概念必须回答这三个问题中的至少两个：

1. **设计动机**：这个机制是为了解决什么物理/时序/系统约束？如果没有它会怎样？
2. **Trade-off**：选择这个设计放弃了什么？竞争方案是什么？什么场景下另一个方案更好？
3. **演化路径**：这个设计是从什么前身演化来的？比如 AXI 五通道是怎么从 AHB 的单通道反推出来的？

**严禁**只写"X 是什么，包含 A/B/C 三类"这种平铺罗列。如果一个段落只是在定义术语，必须紧跟一段"为什么需要这个区分"。

### 每篇文末固定小节：「建模启示」

在每篇文档末尾，加一个标题为 `## 建模启示` 的小节，回答：

- 这个机制在 cycle-level / event-driven 仿真里应该如何抽象？
- 哪些状态变量是必须显式建模的？哪些可以抽象掉？
- 如果只关心性能（latency / bandwidth / SLA），哪些细节可以折叠？如果关心功能验证，哪些细节必须保留？
- 这个机制对应到 Execution IR / 事件模型里的哪种事件类型？

这一小节**不需要**和 archax 的具体术语（Resource/Topology/Interaction/Capability）强行绑定——只在 `06-scenarios-case-studies/` 和 `05-performance-debug/` 章节才显式使用这套抽象。其他章节保持总线知识本身的纯粹性，让"建模启示"是建模者的通用思考，而不是对某个框架的硬塞。

### 类比的使用原则

**适度类比，关键处用**：

- 只在引入一个**反直觉**或**初学者最容易混淆**的概念时使用类比（如：outstanding transaction、burst 与 narrow transfer 的关系、response channel 为什么独立、QoS 的仲裁语义）
- **一个概念至多一个类比**，类比之后立刻回到精确语言，不要让类比代替分析
- **避免**过度通俗化的类比（"地址就像门牌号"这种已经成废话的）
- 如果某概念在精确语言里就能讲清楚，**不要为了"通俗"硬加类比**
- 类比要**有张力**：好的类比应该揭示一个非平凡的结构相似性，而不只是换个说法

## 内容质量的具体标准

### 必须做到

1. **每个设计决策都要有"因为...所以..."**：例如不要只说"AXI 有五个独立通道"，要说"因为 read 和 write 在物理 DRAM 上是不同方向的操作、turnaround 代价高，所以解耦读写通道让它们可以独立流水；又因为地址和数据的握手节奏不一样（地址一拍发出，data burst 可能 16 拍），所以地址通道和数据通道也要解耦"
2. **对比要尖锐**：AXI vs AHB vs APB、bus vs NoC、shared bus vs crossbar、coherent vs non-coherent，每一对比都要给出"什么场景选谁，代价是什么"的明确判断
3. **波形/时序示例**：在讲握手、burst、outstanding 等概念时，至少给一个 ASCII 时序图或 markdown 表格表示的 cycle-by-cycle 行为
4. **真实硬件锚点**：尽量提到真实场景的具体数字或案例（DDR 的 row buffer 命中代价、典型 SoC 的 AXI 数据宽度选择、NPU 中 DMA 的 outstanding 深度量级）。如果不确定具体数字，明确说"典型量级在 X-Y 之间"而不是编造
5. **指明常见误解**：每个核心概念后给一句"常见误解：...，实际上：..."

### 必须避免

1. **不要使用 emoji**
2. **不要堆砌 bullet list**：能用连贯论述讲清的不要拆成 bullet。bullet 只用于真正的并列枚举（如某协议的几种 burst type）
3. **不要写"通常""一般""有时"这种含糊词**——要么给条件，要么给具体例子
4. **不要在每段开头都用粗体小标题**——这是 AI 生成内容的典型坏味道
5. **不要重复**：同一个概念在同一篇文档里不要换着说法讲两遍
6. **不要"水"过渡句**：诸如"接下来我们看看..."这类承上启下的废话直接删
7. **不要假装有经验**：case study 如果是构造的，明确写"构造案例"；不要用"在实际项目中我们..."这种伪装

## 一个示范：transaction-address-data-response.md 应该怎么写

原文件只是平铺了"地址/控制属性/数据/响应"四类信息，然后给了一段"为什么请求和完成不是一回事"。这是典型的"知其然不知其所以然"。重写后这篇应该讲清楚的核心是：

**为什么一个 transaction 必须分裂成这四类，而不是"地址 + 数据"两类就够了？**

这个问题的回答会牵出：

- 地址和数据的**握手节奏天然不对称**（地址一拍，数据多拍）—— 所以即便是最简单的协议，时序上也已经隐含了这种分裂
- 控制属性为什么不能和地址合并：因为有些属性（cacheable/bufferable/QoS）影响的是**路径选择**和**调度优先级**，必须在地址 decode **之前**就被互连看到，而不能藏在 payload 里
- 响应为什么必须独立：在 outstanding 场景下，请求和完成已经在时间上彻底分离了，响应不再是"数据返回的副产品"而是"事务闭环的独立证据"
- 这四类的分裂程度，恰好是协议复杂度的度量：APB 几乎不分裂（合一），AHB 部分分裂，AXI 彻底分裂成五通道

然后「建模启示」小节回答：在事件驱动仿真里，一个 transaction 不是一个事件而是**至少四个事件**（地址被接受、数据被接受、响应被生成、响应被消费），它们之间的时间关系才是性能模型的核心。如果用单一事件建模 transaction，等于丢掉了 outstanding、burst、turnaround 这些性能模型的全部信息。

**这就是我要的深度**。请用类似的方式重写每一篇。
