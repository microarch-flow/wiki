# MCU、CPU、GPU、NPU 为什么选择不同存储器

上级：[系统视角](./README.md)
相关：[LPDDR：为了功耗放弃了什么](../05-dram-protocol-families/lpddr-low-power-mobile.md), [HBM：从协议层面看它和 DDR 的根本不同](../05-dram-protocol-families/hbm-stacked-wide-io.md)

## 这页在回答什么问题

为什么不同类型的计算系统不会自然收敛到同一种存储路线。更准确地说，MCU、CPU、GPU、NPU 的目标函数、访问模式和软件模型有何根本差异，以至于它们会在 TCM、cache、DDR、LPDDR、GDDR、HBM 这些选项上各自停在不同的局部最优点。

## 正文

如果把存储器只看成“谁更快、谁更大、谁更省电”，很容易得出一种错误期待：技术继续进步之后，系统最终应该收敛到某一种“最强内存”上，大家都用它就好。前面几章其实已经不断在否定这件事。存储路线之所以长期并存，不是因为产业还没来得及统一，而是因为不同系统的约束根本不是同一组。目标函数不同，局部最优自然不同。

最值得先抓住的，不是具体器件，而是系统真正怕什么。`MCU` 最怕 deadline 抖动、功耗失控、软件不可证；`CPU` 最怕通用程序的大工作集和复杂控制流无法被透明高效地支撑；`GPU` 最怕大吞吐阵列被外存喂不饱；`NPU` 最怕数据搬运链路打不过计算阵列节拍，或者为此付出不可接受的功耗和封装代价。只要把“最怕什么”抓清楚，后面的存储器选择就不会再显得随意。

先看 `MCU`。它的核心问题往往不是追逐极端峰值带宽，而是保证关键路径行为稳定、功耗可控、实现容易分析。很多 MCU 的代码与数据规模并不大，但对中断响应、控制回路和安全行为的抖动非常敏感。因此它天然偏好 `ITCM / DTCM + 片上 SRAM + 相对简单外存层` 这类路线。cache 如果引入太多不可预测 miss，反而会伤害最坏情况。LPDDR、HBM、GDDR 这类路线即使在某些指标上更强，也通常不贴合 MCU 的主矛盾，因为 MCU 不是在追极端外存吞吐，而是在追低抖动、低功耗、低复杂度。

`CPU` 的问题则完全不同。它面对的是通用负载：控制流复杂、数据结构形态多样、工作集跨度大、软件生态希望尽量少关心底层数据搬运。这决定了 CPU 系统通常愿意投入大量 cache 层次和复杂 controller，让硬件替软件吸收局部性判断，同时配上一条容量大、可扩展的主存路线。于是 `cache hierarchy + DDR` 成为很自然的主流答案。这里 DDR 不一定在每 bit 能耗或带宽密度上最优，但它在容量、可插拔扩展、生态成熟度和通用性上的平衡，对 CPU 平台更有价值。

`GPU` 的局部最优则更靠近“总带宽第一”。它当然也有 cache 和片上寄存器文件，但其大量并行线程和高吞吐计算阵列对外存带宽极为敏感。相比 CPU，GPU 更能接受较高 I/O 功耗和更激进的板级设计，只要能够持续把大量数据流送到阵列旁边。因此历史上 `GDDR` 路线长期非常适合独立 GPU：在还保留外置显存和板卡生态的前提下，尽量把总带宽顶高。到了更高带宽密度需求的高端 GPU，`HBM` 才开始更频繁地成为合理选择，因为此时单靠高 pin-rate 外置显存已越来越贵。

`NPU` 则又不完全等同于 GPU。它通常拥有更结构化、更可设计的数据流，很多权重、激活和部分和的复用关系在编译期或映射期就能大致看见。这让 NPU 比 CPU 更适合使用 scratchpad 风格、本地 buffer 分角色管理的 SRAM 体系；比 GPU 更容易显式地把数据搬运编排成一条流水。于是 NPU 的内存路线通常不是“只选一种外存”，而是“片上多级 SRAM 组织 + 外层 HBM 或 LPDDR/DDR 的组合决策”。若模型大、带宽压力和每 bit I/O 能耗压力都高，HBM 往往很诱人；若目标更偏边缘设备、成本和功耗更紧，LPDDR 反而可能是更合理的外层选择。

这说明一个很关键的事实：系统不是在“挑一种最强内存”，而是在“把若干存储层次按自己的目标函数拼起来”。MCU 的拼法偏向 deterministic SRAM + 小而省的外层；CPU 的拼法偏向深 cache + 大容量主存；GPU 的拼法偏向大寄存器/片上缓存 + 高带宽显存；NPU 的拼法偏向按数据角色拆分的片上 SRAM + 外层高带宽或低功耗主存。它们不是在器件榜单上挑选，而是在系统图上布点。

可以把四类系统的主矛盾压成一个对照表：

| 系统 | 主矛盾 | 典型局部最优存储路线 |
| --- | --- | --- |
| `MCU` | 最坏情况可预测、低功耗、低复杂度 | TCM / SRAM 优先，外层简单 |
| `CPU` | 通用工作集、透明局部性管理、容量扩展 | 深 cache hierarchy + DDR |
| `GPU` | 持续高带宽喂饱大吞吐阵列 | 片上寄存器/缓存 + GDDR 或高端 HBM |
| `NPU` | 数据搬运优先、片上复用、外存带宽与能耗平衡 | 分角色 SRAM + HBM/LPDDR/DDR 组合 |

这个表最重要的价值，不是分类记忆，而是提醒你每个系统真正在乎的是不同的失败模式。MCU 最不能接受的是 jitter 和不可证；CPU 最不能接受的是软件必须手工安排大量数据搬运；GPU 最不能接受的是算力空转；NPU 最不能接受的是数据流设计没有把局部复用和外存路径压顺。只要失败模式不同，存储路线自然不会统一。

还要特别强调一个容易被忽略的点：软件模型会反过来塑造硬件最优点。CPU 之所以偏 cache，不只是硬件想偷懒，而是因为通用软件生态无法大规模接受 scratchpad 式显式搬运编程。NPU 之所以更容易接受分角色本地 SRAM，不只是因为硬件“更像加速器”，而是因为它的软件栈和编译流本来就在显式做 tiling、double buffering 和数据布局。也就是说，同一种物理资源，在不同软件契约下会有不同局部最优。

从系统演化的角度看，这些边界也不是完全静止的。现代 CPU 在片上 SRAM、HBM、CXL 等方向上也在尝试新组合；GPU 和 NPU 在某些产品形态里也会因为成本或功耗回到 LPDDR/GDDR；MCU 也会局部引入 cache。但这种演化并没有推翻前面的判断，只是在说：目标函数一旦变，局部最优也会跟着移动。你不应该期待“大家最终都选同一个”，而应该期待“大家在自己的约束下继续重排层次”。

所以，这一页真正要建立的不是一个按系统类型背答案的表，而是一种判断框架：先识别该系统最怕哪类失败，再看哪一组存储层次最愿意为避免这种失败买单。只要这个顺序对了，为什么 MCU/CPU/GPU/NPU 选择不同内存，就会变成一个可以推出来的结果，而不是经验结论。

## 一句话理解

MCU、CPU、GPU、NPU 之所以选择不同存储器，不是因为它们接触到的器件名单不同，而是因为它们最怕的失败模式不同，于是各自在不同的存储层次组合上找到局部最优。

## 建模启示

在系统级建模里，最有用的做法不是为每种系统硬编码“推荐内存”，而是先把系统目标函数显式化，再让存储路线去匹配。也就是说，应该先定义哪些指标在这个系统里最值钱，然后再看 DDR/LPDDR/GDDR/HBM 与片上 SRAM 组织哪种组合最合适。

一个最小可用的目标函数草图可以写成：

```text
SystemMemoryObjective {
  weight_latency_predictability: float
  weight_capacity_scalability: float
  weight_peak_bw: float
  weight_bw_density: float
  weight_io_energy: float
  weight_sw_transparency: float
}
```

然后将候选层次组合建成：

```text
MemoryHierarchyCandidate {
  local_sram_style: enum { TCM, CACHE_HEAVY, SPM_BUFFERED, REGFILE_HEAVY }
  external_dram_family: enum { DDR, LPDDR, GDDR, HBM }
}
```

再做匹配：

```text
score(candidate) = fit(candidate.capabilities, system_objective)
```

如果只是做 very-high-level 产品路线比较，这种模型已经足够抓住“为什么不是所有系统都选 HBM”；若进一步进入 AI 芯片架构探索，再把候选拆到 `weight/activation/accumulator buffer + external memory route` 粒度，会更接近真实设计空间。
