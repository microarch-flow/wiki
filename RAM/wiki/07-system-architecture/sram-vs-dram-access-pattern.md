# SRAM 和 DRAM 在访问模式上的根本区别

上级：[系统视角](./README.md)
相关：[同样是 RAM，为什么 SRAM 和 DRAM 走向了完全不同的工程路径](../01-overview/sram-dram-divergence.md), [Open、close、adaptive page policy 的权衡](../06-memory-controller/page-policy-open-close-adaptive.md)

## 这页在回答什么问题

为什么同样被叫作“随机访问存储器”，SRAM 和 DRAM 对访问模式的反应却完全不同。更准确地说，什么样的访问流是在顺着 SRAM 工作，什么样的访问流是在顺着 DRAM 工作；反过来，什么样的访问流会把两者各自最痛的代价全逼出来。

## 正文

到这里再回头看 SRAM 和 DRAM，最值得收住的一点已经不是“一个快一个大”，而是它们对访问模式的成本函数根本不同。SRAM 的访问成本相对局部、相对稳定，主要受端口冲突、bank 冲突、阵列尺寸和时钟窗口影响；DRAM 的访问成本则高度上下文相关，强烈依赖 row 是否命中、bank 是否繁忙、总线方向是否切换、refresh 是否在挡路。也就是说，系统眼中的“随机访问”这个词，在 SRAM 和 DRAM 上其实对应的是两种完全不同的物理现实。

先看 SRAM。对大多数片上 SRAM 资源来说，只要端口可用、bank 不冲突、数据已经在本层，访问就更接近“给地址，付一个近似稳定的本地代价”。这个代价当然不是绝对常数，但它的主要变化来源相对简单：单口还是多口、有没有 bank 冲突、阵列有多大、是否正处在低功耗唤醒窗口。也就是说，SRAM 更不在乎”你上一次访问的是哪一行”，更在乎”你现在是否在争同一个局部资源”。这就像自动售货机——你投了币选了号，它就吐出商品，价格基本固定，跟你上一次买的是什么、隔壁机器有没有人用没什么关系。常见误解是以为 SRAM 就完全不看访问模式；实际上它看，但看的主要是 `并发冲突形态`，而不是 `历史打开状态`。

再看 DRAM。DRAM 之所以难，不是因为它单次绝对更慢，而是因为它的慢和快取决于你是不是刚好顺着当前 open row、bank 状态和总线节奏走。对 DRAM 来说，访问模式好不好，首先不是看你地址是否”随机”，而是看这些地址经过映射后，是否能够形成 row locality、bank interleaving 和较少的读写方向切换。DRAM 更像一个需要预约的图书馆特藏室——如果你连续借的几本书都在同一个书架上（row hit），管理员只需要开一次柜子就能连续给你取；但如果每次都要去不同的柜子，每次都要锁上旧柜子、走过去、开新柜子，成本就会飙升。也就是说，DRAM 更在乎 `结构相关的时序可重用性`，而不是单纯的地址是否连续。

一个非常关键的差异在于：SRAM 的”历史依赖”较弱，DRAM 的”历史依赖”很强。换一种说法：SRAM 的定价更像超市——不管你之前买了什么，这瓶水就是 3 块钱；DRAM 的定价更像打车——你上一单去了机场，司机现在在机场附近，你叫他回市区接你就很贵（row conflict），而你让他在机场再接一单就很便宜（row hit）。对 SRAM 来说，本次访问是否便宜，和前一次访问落在哪一行通常没有直接关系；对 DRAM 来说，前一次甚至前几次访问决定了当前 bank 的 open row 状态，本次是否 row hit 几乎完全取决于这个历史。于是，SRAM 的代价更像由当前竞争决定，DRAM 的代价更像由当前竞争加上一段短历史共同决定。这个差别是系统行为完全不同的根源。

可以用一个最简对照来抓住这种成本曲线差异：

```text
SRAM:
  cost(access) ~= base_access + port/bank_conflict_penalty

DRAM:
  cost(access) ~=
      row_hit_cost
      or row_miss_cost
      or row_conflict_cost
      + maybe refresh/turnaround/queueing penalties
```

这两行已经足够说明问题：SRAM 的代价波动通常来自“当前能不能排上这次本地访问”；DRAM 的代价波动则来自“当前 bank 处在什么状态、未来是否还要切换、总线是否还要腾方向”。

这就解释了为什么同一种顺序访问模式，在两者身上体现的价值也不同。对 SRAM 而言，顺序访问的最大好处通常是让软件、编译器或硬件更容易做 burst、bank 分配和局部预取，但它不会像 DRAM 那样把一次高成本开行摊给整行后续访问。对 DRAM 而言，顺序访问如果映射得当，可能直接转化为多个列访问命中同一 row，从而把 activate 成本摊得很薄。因此，顺序性在 SRAM 上主要改善调度便利和冲突概率，在 DRAM 上则可能直接决定是否进入低成本模式。

反过来看“随机访问”，差别就更尖锐。SRAM 遇到随机访问时，通常仍能给出较稳定的本地服务，只是如果随机访问把请求打散到同一端口或同一 bank，会出现冲突和队列等待；DRAM 遇到随机访问时，最糟糕的情况不是“多等几拍”，而是把几乎每次访问都变成 row conflict，频繁触发 `PRE -> ACT -> RD/WR`，还可能让 FR-FCFS 和 open-page policy 的收益全面蒸发。也就是说，DRAM 对坏访问模式的惩罚往往更陡，而且更容易级联放大成总线低利用率和尾延迟恶化。

这也是为什么前面会反复强调：cache、scratchpad、DMA、tiling、address mapping、page policy 这些机制，本质上都是在把上游访问模式尽量改造成更适合下游存储层的形状。对片上 SRAM 来说，你主要想避免端口和 bank 热点；对外层 DRAM 来说，你主要想形成 row locality、bank-level parallelism 和 burst 友好流量。若你用一套完全一样的访问直觉去驱动两者，通常会错。常见误解是以为“只要访问连续就都好”；更准确的说法是，连续性只是原材料，是否真的好，还取决于它在不同层次上会被翻译成什么结构形状。

从系统设计角度看，这种差异会直接塑造层次分工。为什么小而确定的热数据、操作数和局部工作集会尽量留在 SRAM 一侧？因为那里更适合细粒度、低抖动、局部高频访问。为什么大容量数据最终要落到 DRAM/HBM 一侧，但又总想在上面叠 cache、scratchpad、tiling 或 prefetch？因为外层 DRAM 的原生代价函数对访问模式太敏感，系统必须在更内层先把访问塑形，尽量把坏模式截住。

可以把这种分工压缩成一句非常实用的设计经验：

```text
SRAM 喜欢：
  细粒度、频繁、本地、确定的访问

DRAM 喜欢：
  可聚合、可重排、可形成 row/bank 局部性的访问
```

这不是说 SRAM 不需要局部性，或者 DRAM 不支持细粒度请求，而是说它们“最划算的工作方式”不同。只要系统能把合适的访问留在合适的层，整体效率就会好很多；反之，若让大量细碎控制流直接扎进 DRAM，或让本可在 scratchpad 内循环的数据反复回外存，硬件就会显得异常低效，其实问题在于访问模式没有被放到正确层次。

对 AI/NPU 场景，这个差异尤其关键。NPU 的片上 SRAM buffer 设计，本质上是在为 compute array 提供一种“更像 SRAM 喜欢的访问模式”：局部、分块、可预测、可双缓冲。而外层 HBM/LPDDR 则被期待接收的是已经聚合好的大块传输请求。如果系统没把这一层职责分清，外层内存会看到太多细碎、不同步、方向混乱的流量，片上又会因为 bank 组织不当承受不必要冲突。后面 AI 章节的很多设计判断，其实都可以追溯到这里这条根分叉。

所以，这一页真正要建立的不是一句“SRAM 快、DRAM 慢”的旧结论，而是更强的系统判断：SRAM 和 DRAM 对访问模式的最优响应完全不同。前者主要惩罚即时局部资源冲突，后者主要惩罚结构状态错配与历史不可重用。系统层次设计的价值，就在于让不同形状的数据流尽量落到它们最匹配的介质上。

## 一句话理解

SRAM 的成本主要看“当前本地资源是否冲突”，DRAM 的成本主要看“当前结构状态和短历史是否匹配请求”；因此同样一串地址，在两者上会被翻译成完全不同的代价曲线。

## 建模启示

在模型里，千万不要把 SRAM 和 DRAM 都建成“容量不同、延迟不同”的同类资源。更合理的做法是让它们拥有不同的成本函数。对 SRAM，成本主要依赖 `port/bank occupancy`；对 DRAM，成本主要依赖 `row state / bank state / bus state`。

一个非常直接的并列抽象可以写成：

```text
SramAccessCost(req) =
  base_latency
  + port_conflict_penalty
  + bank_conflict_penalty

DramAccessCost(req) =
  row_state_cost
  + queue_delay
  + turnaround_penalty
  + refresh_penalty
```

如果你在系统模型里把两者都近似成固定 latency，很容易得到错误结论：比如误以为把更多访问直接打到 DRAM 只是“平均慢一点”，而忽略它其实会因为 row conflict 和状态切换把尾延迟拉得很难看。反过来，如果你把 SRAM 也建成强历史依赖资源，就会错误高估它对访问顺序的敏感度。

更进一步，若要让这页结论落到多层系统图里，可以给每一层标出“最痛的代价来源”：

```text
LayerCostSignature {
  dominant_penalty: enum {
    PORT_CONFLICT,
    BANK_CONFLICT,
    ROW_CONFLICT,
    REFRESH_BLOCK,
    TURNAROUND
  }
}
```

这个标记虽然粗，但对做体系结构判断非常有用。因为很多优化动作的本质，就是在把请求从一种 `dominant_penalty` 环境迁移到另一种更适合它的环境。
