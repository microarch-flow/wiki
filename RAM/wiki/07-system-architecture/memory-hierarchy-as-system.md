# 把 register、cache、scratchpad、DRAM、HBM 看作一个系统

上级：[系统视角](./README.md)
相关：[速度、容量、成本、功耗四角矛盾的根源](../01-overview/memory-hierarchy-tension.md), [NPU 的存储层次：L0/L1/L2 SRAM 与 HBM/LPDDR](../09-ai-chip-memory-architecture/npu-memory-hierarchy.md)

## 这页在回答什么问题

为什么存储层次不应该被看成“几种内存从快到慢排个队”，而应该被看成一张由不同资源角色组成的系统网络。更具体地说，register、cache、scratchpad、DRAM、HBM 各自在为哪类距离、容量、带宽和管理语义付账，它们之间又如何共同决定数据搬运路径。

## 正文

很多入门图都会把内存层次画成一个金字塔：上面小而快，下面大而慢。这个图并没有错，但它容易把系统理解带向一个过于静态的方向，好像每一层只是“同一种资源不同容量和速度的版本”。前面几章其实已经说明，事实远不是这样。register file、cache、scratchpad、DDR、HBM 之所以同时存在，不是因为大家排队占不同档位，而是因为它们分别解决的是不同的系统问题。就像一个厨房里，手边的调料盒、案板上的备料、冰箱里的食材、储藏室的干货和超市的供应链不是"同一种东西的大小版本"，它们各自承担完全不同的角色——有的保证你炒菜时伸手就够到，有的保证你今天不用出门采购，有的保证你这个月不会断粮：有的在解决极低延迟操作数供给，有的在解决透明局部性捕获，有的在解决可控数据搬运，有的在解决大容量承载，有的在解决高带宽外存供数。

因此，最稳的系统视角不是问“哪一层更高级”，而是问“每一层在替系统承担哪一类代价”。register file 在替执行管线承担最小粒度、最强并发、最严格时序的操作数服务；cache 在替通用代码承担局部性猜测与平均延迟优化；scratchpad/TCM 在替软件承担显式放置和确定性控制；DRAM 在替系统承担大容量低每 bit 成本；HBM 在替高吞吐系统承担高带宽密度与更低每 bit I/O 能耗。只要你从“系统角色”而不是“物理标签”看，这些层级之间的关系就会清晰很多。

可以把这张图压缩成一个非常实用的问题链：

```text
这份数据现在离计算有多远？
它多久会被再次使用？
它的访问是否必须确定可控？
它需要的是首字节快，还是长期吞吐高？
为了让它更近，我愿意付出多少面积、功耗、软件复杂度或封装复杂度？
```

不同层次对这几问给出的答案不同，于是它们自然分化成系统中的不同节点。

先看最上层的 `register file`。它不是“最小的 cache”，而是执行资源的延伸。它服务的不是地址空间，而是指令级操作数，要求是同拍多读多写、极低延迟、严格时序语义。为了做到这一点，它愿意牺牲面积效率和功耗。这说明：最顶层资源追求的不是“存更多”，而是“在最关键的一个时钟窗口里绝不能掉链子”。

`Cache` 则是在另一条轴上工作。它不对软件暴露显式搬运，却要求硬件去猜哪些数据值得留在本地。它的价值在于平均延迟优化，而不是可预测性最大化。Cache 就像一个聪明的助手，他观察你的工作习惯，提前把你可能要用的文件放到桌上——大多数时候猜得很准，但偶尔也会猜错，让你等一下他去找。因此 cache 的本体不只是 SRAM 阵列，而是 tag、替换、refill、writeback 和一致性协议的综合体。它说明了一件事：越想让存储层次对软件透明，硬件就越要吞下更多管理复杂性和不确定性。

`Scratchpad` 和 `TCM` 又把这件事反了过来。它们通常仍然用 SRAM 实现，但不愿意为透明性买太多单，而是把放置和搬运责任交还给软件、编译器或 DMA 调度器。如果说 cache 是自作主张帮你整理桌面的助手，scratchpad 就是一块干净的白板——你自己决定写什么在上面、什么时候擦掉，控制权完全在你手里，但你也得自己动手。这样做的回报，是更高的净数据容量、更稳定的访问延迟和更可控的局部带宽；代价是编程模型更重、调度错误更容易直接变成 stall。它们说明：同样是片上存储，系统可以选择把复杂性留在硬件，也可以选择把复杂性移交给软件。

再往外层看，`DDR/LPDDR/GDDR/HBM` 虽然都属于 DRAM 路线，但在系统图里扮演的也不是同一个角色。通用 DDR 更像大容量、较通用的主存承载层；LPDDR 更像移动系统里受功耗和封装约束的主存层；GDDR 更像外置高带宽显存层；HBM 更像贴近计算、为带宽密度服务的外层大池子。它们在物理上都还是 DRAM，在系统上却分别站在不同的“距离/带宽/成本”坐标点上。

这张系统图最有价值的地方，是它能解释“为什么某些优化在一层很合理，放到另一层就荒唐”。比如：

- 为 register file 加复杂替换策略几乎没有意义，因为它服务的是确定性操作数而不是局部性投机
- 让 HBM 追求像 TCM 那样的首字节低延迟也不现实，因为它的价值在高带宽密度而不是最短控制路径
- 让 scratchpad 像 cache 一样自动管理，往往会把它最核心的可控性优势抹掉
- 试图用更多 cache 直接替代所有外存，也会很快撞上容量和功耗墙

也就是说，一层之所以存在，不只是因为它比上下层“快一点或慢一点”，而是因为它提供了一组其他层没有的契约组合。

从数据搬运角度看，把这些层次看成系统还有一个更关键的好处：你会开始自然追踪一份数据的生命周期，而不是只盯着“当前在哪层”。一份数据可能从 HBM/DDR 进来，经由 DMA 或 cache refill 到达片上 SRAM，再进入 scratchpad/activation buffer，最后被读进 register file 或本地 accumulator。每一次跨层，系统都在支付一笔不同类型的费用：有的是启动延迟，有的是持续带宽，有的是总线争用，有的是软件调度复杂性，有的是封装与功耗代价。存储系统优化，本质上就是在重新安排这些跨层次数和跨层距离。

这也解释了为什么“谁更先进”这种问法几乎总是低质量问题。先进不先进，必须附着在目标函数上。对服务器数据库来说，DDR 可能比 HBM 更合理，因为容量和成本是主矛盾；对高端 AI 训练平台，HBM 可能明显更优，因为带宽密度和 I/O 能耗才是主矛盾；对 MCU 控制环路，TCM 比 cache 更“先进”，因为可预测性比平均命中率值钱。只有把整张系统图放出来，才知道该在哪个节点上押注。

从建模角度进一步压缩，这一页最大的价值在于提醒你：不要把内存层次建成一串“容量更大、延迟更高”的参数列表。更合理的做法，是把每一层建成一个有自己服务语义、资源边界和交互方式的节点，然后再看事务在这些节点之间怎么流动。只有这样，模型才会自然长出“为什么多了一层 cache 反而不总是更好”“为什么 HBM 加上去仍可能 memory-bound”“为什么片上 SRAM 配得不对会让外存再强也没用”这些系统级结论。

所以，这一页真正要建立的不是一张漂亮金字塔，而是一张功能网络图。register、cache、scratchpad、DRAM、HBM 并不是简单的大小版本，而是系统为了同时管理延迟、带宽、容量、功耗、软件复杂度和封装复杂度，被迫拼出来的一组互补节点。

## 一句话理解

存储层次不是“几种内存按快慢排队”，而是一张由不同资源角色组成的系统网络；每一层都在为某类距离、容量、带宽或管理语义付账。

## 建模启示

在模型里，最稳妥的做法是把每一层存储建成带有“角色语义”的节点，而不是只给它一个容量和延迟。至少要显式区分：它是 `operand-serving`、`hw-managed locality`、`sw-managed local store`、`bulk capacity` 还是 `high-bandwidth backing store`。

一个可用的节点抽象可以写成：

```text
MemoryHierarchyNode {
  id: string
  role: enum { REGFILE, CACHE, SCRATCHPAD, TCM, DDR_MAIN, HBM_MAIN }
  capacity_bytes: uint64
  startup_latency_cycles: int
  sustained_bw_bytes_per_cycle: int
  management: enum { FIXED, HW_MANAGED, SW_MANAGED, DMA_MANAGED }
  predictability: enum { HIGH, MEDIUM, LOW }
}
```

再通过边连接成端到端路径：

```text
ResourceEdge {
  src: NodeId
  dst: NodeId
  transfer_granularity_bytes: int
  edge_bw_bytes_per_cycle: int
}
```

如果只关心局部层次性能，这些角色字段似乎可以省；但只要你要分析系统级 bottleneck 或路线选型，它们非常关键。因为很多时候问题不是“某层太慢”，而是“这份数据被放在了错误角色的那一层，或者跨层次数太多”。
