# CXL、近存计算与未来封装方向

上级：[封装与集成](./README.md)
相关：[把 register、cache、scratchpad、DRAM、HBM 看作一个系统](../07-system-architecture/memory-hierarchy-as-system.md), [Memory bound vs compute bound 的本质与缓解策略](../09-ai-chip-memory-architecture/memory-bound-vs-compute-bound.md)

## 这页在回答什么问题

当传统“片上 SRAM + 片外 DRAM/HBM”层次继续承压时，CXL、near-memory 和更激进的封装路线会怎样重新划分内存的边界。

## 正文

如果只看过去几十年的主流系统，内存层次大致还能被画成一条比较清晰的线：核心附近是 register 和 cache，芯片上更远一些可能有 scratchpad 或片上 SRAM，封装外面是 DDR，极少数高带宽系统再加上 HBM。这个图仍然有用，但它正在变得不够。原因不是旧层次突然失效，而是几个长期压力正在同时变重：模型越来越大，工作集越来越难装进片上；外存容量和带宽需求一起抬升；不同 workload 对延迟、带宽、容量、成本的偏好越来越分化。结果就是，系统开始不满足于只在“芯片内”和“主板上”这两个位置放内存，而是试图重新划分边界。

这里最容易混淆的，是把 `CXL`、`near-memory` 和“先进封装”看成同一类东西。它们确实都在推动边界变化，但各自作用层不同。`near-memory` 更像一种系统目标，意思是让计算离大容量数据更近，减少长距离数据搬运；先进封装是实现这种靠近的一组物理手段，包括更短互连、更高密度连接和更紧耦合的集成方式；`CXL` 则不是封装技术，而是把“主机如何和外部扩展内存、加速器内存池、共享内存设备交互”这件事重新接口化、语义化的一条系统互连路线。把这三者分开，后面的判断才不会乱。

先看为什么未来方向一定会继续往“更近”推进。过去很多系统的默认办法，是把算力做大，再想办法把外部 DRAM 带宽跟上。但到了一定规模以后，问题不再只是 DRAM 本身够不够快，而是数据在不同物理边界间反复穿梭的代价越来越高。你可以把这个代价理解成三件事叠加：链路时间、链路能耗、链路竞争。数据每多跨一层边界，就更容易在其中某一项上付出高税。于是系统自然会问：能不能把部分存储做得更近，或者把部分计算推得更靠近数据？

`near-memory` 就是在这种背景下出现的。它不是一个单一器件，而是一类设计方向。最温和的形态，是在更靠近内存的位置加上更强的缓冲、预处理和数据搬运引擎；再往前走，是在内存 stack 附近放轻量计算逻辑，做 reduction、gather/scatter、简单 transform 或特定算子；更激进的路线才会走向真正意义上的 `processing-in-memory`。这几种路线的共同点不是”把 CPU/GPU 搬进内存里”，而是承认：如果大量数据搬运本身已经成为瓶颈，那么减少搬运有时比继续提高远端算力更划算。就像一个大型仓库——与其每次都把货物运到远处的总部去检验分拣再运回来，不如直接在仓库旁边设一个分拣站，把简单的分类和检查就地完成。

但 near-memory 不是白拿的。它之所以难，不只是因为“在内存旁边放逻辑更复杂”，而是因为你同时改写了数据一致性边界、软件可见抽象、调试方式、热分布和产品分工。只要某段功能从主计算 die 挪到内存附近，你就必须重新定义三件事：谁拥有这段数据、谁对它的更新负责、谁来支付同步成本。很多 near-memory 方案在论文里看起来很强，到了产品化阶段却变慢，往往不是局部算力不够，而是系统边界没有被重新设计干净。

先进封装之所以重要，是因为它决定了“更近”到底近到什么程度。前几页已经讨论过 HBM 的 2.5D、3D 和 TSV。未来方向并不只意味着继续堆更高的 HBM，也意味着把更多本来板级分散的资源提前搬到封装级统一组织。这样做会带来两个直接变化。第一，内存与计算的物理距离继续缩短，单位带宽的链路代价下降。第二，原来可以在板级较松耦合处理的问题，会更早在封装级被绑定，比如热、供电、良率和 SKU 组合。也就是说，未来封装的本质不是“更炫的封装形式”，而是把系统的关键权衡更早、更硬地锁进物理集成方案里。

`CXL` 代表的则是另一个方向：不是把所有东西都挪得更近，而是承认有些资源仍然会保持在相对更远的位置，但希望用更统一的语义去接入它们。传统 DIMM 主存路线的一个强项，是容量扩展和模块化；弱项是距离远、带宽密度低、板级电气约束重。HBM 路线的强项，是高带宽密度和更低每 bit I/O 代价；弱项是封装重、成本高、容量扩展不自由。`CXL memory expansion` 试图打开第三种空间：把一部分容量资源放在更远但更灵活的地方，通过一致性或准一致性的协议框架接入，让主机、加速器和外部内存池之间的边界更可编排。你可以把 CXL 理解成云存储对本地硬盘的关系——云存储更远、访问更慢，但它让你不必在每台机器上都插满硬盘，需要时可以按需挂载共享池里的存储空间。

这里必须强调一次：`CXL` 不是在物理上把远端内存变近。它改变的是系统可见资源边界，不是传播速度本身。远端内存仍然更远，链路仍然更长，访问延迟和抖动也仍然更大。所以 CXL 的价值从来不是“替代本地 DDR/HBM”，而是让容量扩展、设备共享、内存池化和分层放置有了更清晰的系统路径。你可以把它理解成：HBM 更像在争取更近、更宽、更高带宽密度；CXL 更像在争取更灵活、更可池化、更可组合的远端容量层。两者不是同一问题的两个品牌，而是在不同方向上改写内存边界。

这也解释了为什么“未来内存系统”越来越像一张图，而不是一条线。系统可能同时存在：

- 极近的片上 SRAM 或 scratchpad
- 封装内的 HBM
- 本地插槽上的 DDR/LPDDR
- 更远的 CXL 扩展内存或共享内存池

从软件和运行时角度看，这些资源不会再自然坍缩成一个统一“RAM”概念。它们的延迟域、带宽域、容量域和共享域都不同。未来真正难的地方，不是有没有某项新技术，而是系统能否把这些不同域管理成一个可用的层次，而不是一锅杂乱的“可寻址但不可预测”的存储空间。

如果从架构视角再往下压一层，未来方向其实在逼着系统承认两件事。第一，`capacity tier` 和 `bandwidth tier` 会继续分化。不是所有大容量都需要高带宽，也不是所有高带宽都必须附带大容量。第二，`data placement` 会越来越从隐式决策变成显式策略。过去很多通用系统可以把数据放置这件事大部分交给硬件和操作系统；未来如果同时有本地 HBM、本地 DDR、远端 CXL pool、甚至 near-memory 处理单元，放错层的代价会迅速变大。

所以，本页的重点不是预测某一项技术会赢，而是建立一个更稳的判断框架：未来封装方向在做的是把更多资源更早拉进紧耦合集成；near-memory 在做的是减少长距离数据搬运；CXL 在做的是把更远的容量和共享资源更规范地接进来。三者共同作用的结果，是“内存边界”从固定位置变成了一组可设计的系统边界。

这也意味着，后续做系统分析时，不能再用“主存只有一种”去思考。你需要先问：这个数据是更怕远、还是更怕贵、还是更怕搬？就像物流规划——生鲜食品怕远（需要冷链就近配送），日用品怕贵（大批量远距离仓储反而便宜），而大型设备怕搬（每次搬运本身就是巨大成本，最好就地加工）。如果它更怕远，就往片上和封装内靠；如果它更怕贵，就接受更远但更便宜的容量层；如果它更怕搬，就考虑 near-memory 或显式数据流组织。未来内存系统的核心，不是谁把所有指标都做到最好，而是谁把不同指标拆到合适的位置上承担。

## 一句话理解

未来内存方向不是单纯“更先进封装”或“更新协议”，而是封装把高带宽资源拉得更近，near-memory 减少数据搬运，CXL 把更远的容量层和共享资源重新语义化接入。

## 建模启示

在模型里，不能把未来内存系统继续压成一个 `main_memory`。至少要把资源按 `distance / bandwidth / capacity / shareability` 四个维度拆开。否则你无法表达：两个都可寻址的内存层，为何一个适合热数据，一个适合冷数据，另一个却只适合扩容量。

一个够用的抽象可以写成：

```text
MemoryTier {
  name: str
  latency_ns: float
  peak_bw_GBps: float
  capacity_GB: float
  energy_per_bit_pJ: float
  share_scope: enum { private, local_socket, package, pooled }
  placement_cost_norm: float
}
```

如果要把 CXL 和 near-memory 也放进去，就再补两个对象。一个描述“远端容量层”的进入代价：

```text
FarMemoryLink {
  protocol: enum { cxl, proprietary }
  hop_count: int
  added_latency_ns: float
  bandwidth_GBps: float
  jitter_ns: float
}
```

另一个描述“靠近数据的处理能力”是否存在：

```text
NearMemoryCapability {
  supported_ops: set
  local_bw_GBps: float
  setup_overhead_ns: float
  coherence_cost_norm: float
}
```

做系统级仿真时，最重要的不是把这些数字做得特别精确，而是保留三类会改写结论的状态：`数据放在哪一层`、`层与层之间通过什么链路连接`、`某些处理是否能在数据附近完成`。这三件事一旦被模型抹平，未来封装、CXL 和 near-memory 的差异就会被错误地平均掉。
