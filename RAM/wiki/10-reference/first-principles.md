# 存储器设计的第一性原理清单

上级：[参考资料](./README.md)
相关：[为什么存储器是体系结构里最难的部分](../01-overview/problem-statement.md), [“数据搬运优先”原则在 NPU 设计中的体现](../09-ai-chip-memory-architecture/data-movement-first-principle.md)

## 这页在回答什么问题

如果把前面所有章节压缩成一组最稳定的判断原则，哪些原则值得在架构讨论、性能分析和选型评审里反复拿出来用。

## 正文

前面整套 wiki 跨了很多层：从 6T SRAM、1T1C DRAM，到 DDR/HBM、memory controller、NUMA、NPU 数据流和先进封装。如果每次讨论都从头把所有细节铺开，效率会很低；但如果只记住零碎术语，又很容易在关键地方失真。所以这一页要做的，不是重复前文，而是把那些最不容易过时、最值得反复拿出来校正方向的判断压成少量原则。

这些原则有一个共同特点：它们不是某代标准的经验结论，而是能跨很多具体实现继续成立的结构性判断。真正有用的第一性原理，不该只帮你记忆过去，更该帮你在遇到新架构、新封装或新 workload 时，先把明显错误的分析排除掉。

**原理 1：存储器问题首先不是“存不存得下”，而是“取出来要付什么代价”**

很多初学讨论会把 memory 简化成容量问题，好像只要容量足够大，剩下只是访问快慢。更稳的看法是：存储器的核心矛盾在于 `bit 被存在哪里、离消费者多远、要经过多少共享边界才能被取到`。同样 1 bit，放在寄存器、L0 SRAM、L2 SRAM、DDR、HBM 或 CXL 远端池里，系统意义完全不同。就像一瓶水——放在你手边的杯子里、放在冰箱里、放在超市货架上、放在城市水库里，"有水"这件事没变，但你拿到它要付出的时间和代价完全不同。容量当然重要，但它从来不是独立指标，而是和访问代价绑在一起的。

这条原则的用途，是在做任何选型或架构比较时，先把问题从“更大行不行”改写成“更大之后访问成本会怎么变”。很多讨论一旦忘了这一步，就会错误地把容量扩展看成免费收益。

**原理 2：SRAM 和 DRAM 不是先进与落后的关系，而是面积效率和访问质量的两条分叉**

SRAM 选择了稳定、局部、可低延迟访问的路线，但每 bit 面积更贵；DRAM 选择了每 bit 更高密度的路线，但因此必须接受破坏性读出、refresh、row buffer 和更复杂的控制语义。这不是”谁技术更新”的关系，而是同一个 RAM 家族在不同目标函数下做出的两种根本分叉。就像猎豹和大象——猎豹快但体型小，大象大但跑不快；你不会说猎豹比大象”更先进”，它们是同一个进化树上朝不同生存策略分化的结果。

这条原则的用途，是防止把 SRAM 和 DRAM 错当成可以直接互相替代的大小版本。很多系统错误直觉，正是从“为什么不用更大的 SRAM 代替 DRAM”或“为什么不用更快的 DRAM 代替 SRAM”这类问题开始的。

**原理 3：带宽不是一个物理部件给出来的，而是一整条路径被同时撑开的结果**

公式上你当然可以写 `bandwidth = transfer_rate x width`，但工程上，带宽从来不是某一层单独决定的。阵列内部是否支持并行读写，bank 是否足够分散，controller 是否能维持 row locality，片上网络是否扛得住分发，封装是否允许足够宽的 I/O，都会共同决定有效带宽。也就是说，理论峰值往往只是某一段链路的能力上限，而系统带宽是多段链路里最窄一段与它前后配合程度的结果。就像一条河流的通航能力不取决于最宽的河段，而取决于最窄的那个峡口——上游再宽，船到峡口还是得排队。

这条原则的用途，是在看到高带宽数字时，立刻追问“是哪一段的峰值”“剩下的段跟得上吗”。它能有效阻止把 HBM 峰值、NoC 峰值或 SRAM 总带宽误当成系统可用带宽。

**原理 4：延迟和带宽通常不是一起最小化的，而是在不同资源组织上分别优化**

低延迟偏向近、小、少共享、少仲裁；高带宽偏向宽、并行、分层缓冲、强共享和更积极的时间重叠。很多内存设计之所以复杂，不是因为工程师喜欢堆结构，而是因为同一个资源很难同时做到最小首访问时间和最大持续输送能力。

这条原则的用途，是在讨论“为什么不既快又宽”时快速落地。它提醒你：某项优化如果明显朝带宽方向走，比如更宽 I/O、更大 burst、更深 buffering，就不应再用低延迟思路去要求它保持同样性质。

**原理 5：DRAM 的真实行为是状态机行为，不是常数延迟行为**

一旦进入 DRAM 世界，访问代价就会强烈依赖前史：当前 bank 开着哪一行、下一个请求是不是 row hit、refresh 是否撞进来、读写方向是否需要切换、controller 是否偏向某些流。也就是说，DRAM 不是“一个更慢的数组”，而是一个状态显著影响未来成本的共享系统。

这条原则的用途，是防止在建模或性能分析时把 DRAM 压成单一固定 latency。只要问题开始依赖 row locality、page policy、QoS 或 tail latency，这个简化通常就已经太粗。

**原理 6：控制器决定理论资源能被兑现成什么样的系统行为**

DRAM 颗粒和协议标准给出了 capability envelope，但真正把请求流翻译成 row hit、bank parallelism、refresh 避让、write drain 和多 master 公平性的，是 memory controller。很多系统性能差异，并不来自“用了不同内存”，而来自“同样内存被不同策略组织”。

这条原则的用途，是在看到性能问题时不要只盯存储器颗粒本身。只要现象里出现了 tail latency、冷热 workload 干扰、row-locality 利用率差异或者有效带宽远低于峰值，controller 都应该被优先怀疑。

**原理 7：数据移动往往比计算本身更早成为主成本**

这在 AI 芯片里最明显，但不只局限于 AI。数据只要跨层、跨 die、跨 package、跨 socket，通常都会比在本地多做几次简单运算更贵。于是很多看起来像“高性能计算技巧”的设计，其实都在服务一个更基础的目标：减少最远、最共享、最贵边界上的移动。

这条原则的用途，是在评估优化时不要只看算术量变化，而要同时看跨层流量是否变多、是否更频繁回外层、是否在更贵边界上重复搬运。很多局部看似聪明的优化，正是死在这里。

**原理 8：封装不是后端细节，而是现代内存系统能力边界的一部分**

DIMM、PoP、HBM 2.5D/3D、未来近存和更远的扩展内存路线，之所以影响巨大，不是因为封装本身神秘，而是它直接改写了距离、位宽、I/O 能耗、热和成本耦合。进入高带宽时代后，封装不再只是把现成颗粒接起来，而是决定哪些内存拓扑根本可不可行。

这条原则的用途，是在做现代 AI/HPC 或高集成 SoC 分析时，避免把封装当成“实现层以后再考虑”的事情。很多路线之所以可行或不可行，答案在封装层就已经被决定了一半。

**原理 9：大多数 memory-bound 问题都必须按层定位，不能只贴一个总标签**

系统之所以跑不满，可能是 off-chip 带宽不够，也可能是 on-chip 分发不够、local SRAM bank 冲突、psum 回路太窄、cache miss 流量没被整形好，甚至是 NUMA 放置错误。把这些都叫 `memory-bound` 没错，但对工程行动几乎没有帮助。

这条原则的用途，是在任何“带宽不够”“内存成瓶颈”的说法出现时，继续追问：到底是哪一级、哪条边、哪个时间尺度在限速。只有定位到层，优化才有方向。

把这些原则合在一起，其实就构成了一个很稳的总判断：RAM 架构设计不是在找“最快/最大/最便宜”的单点答案，而是在不同层、不同距离、不同共享语义之间不断重排 `容量、延迟、带宽、功耗、成本、复杂度` 的承担位置。前面所有细节，最终都能回到这条主线。

## 一句话理解

存储器架构的稳定主线不是某代标准或某个参数，而是不断在 `距离、共享、带宽、延迟、容量、能耗、成本` 之间重排最优承担位置。

## 建模启示

这页里的每条原理，都可以被看成建模前的“问题校正器”。也就是说，在你动手写任何 memory model 之前，先用这些原则检查一次，往往能提前发现模型是不是把关键矛盾压没了。

一个简单用法是把它们映射成建模前检查问题：

```text
1. 这个模型区分了容量和访问代价吗？
2. 它把 SRAM / DRAM 的根本差别保留下来了吗？
3. 它记录的是哪一段带宽，而不是只记总峰值吗？
4. 它把延迟和带宽当成独立目标处理了吗？
5. 它把 DRAM 建成状态机了吗？
6. 它把 controller 作为策略层而不是透明层了吗？
7. 它有没有显式统计跨层数据移动？
8. 它有没有把封装/拓扑边界带进系统可行性里？
9. 它能定位 memory-bound 发生在哪一层吗？
```

如果这九问里有几项答不上来，模型通常还没到能稳定支持架构判断的程度。
