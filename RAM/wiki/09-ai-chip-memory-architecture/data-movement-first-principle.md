# “数据搬运优先”原则在 NPU 设计中的体现

上级：[AI 芯片内存架构](./README.md)
相关：[Scratchpad 和 cache 都是 SRAM，差异在哪](../03-sram-applications/scratchpad-vs-cache.md), [Memory bound vs compute bound 的本质与缓解策略](./memory-bound-vs-compute-bound.md)

## 这页在回答什么问题

如果把 NPU 设计目标表述为“先控制数据搬运，再谈算力堆叠”，那么存储层次、buffer 组织和调度策略应该如何跟着重排。

## 正文

到了这一章，其实已经可以把很多零散结论压成一句更底层的话：对大多数 NPU 而言，真正昂贵的往往不是一次乘加，而是为了让这次乘加发生，数据跨了多少层、走了多远、搬了多少次。如果这一点没抓住，后面很多设计选择就会看起来像风格偏好；一旦抓住，你会发现多级 SRAM、weight buffer、activation double buffering、片上带宽预算、HBM/LPDDR 选型，其实都在围绕同一个原则重排，那就是 `data movement first`。

这条原则并不是说“算力不重要”，而是说在现代 AI 芯片里，算力扩张通常比数据搬运优化更容易。堆更多 MAC、做更宽阵列、提高 nominal TOPS，当然都有工程难度，但如果数据供不上，这些新增算力会立刻变成闲置面积和空转功耗。也就是说，算力是潜在能力，数据搬运决定它能兑现多少。这很像一个拥有顶级发动机的赛车，如果燃油供给管路太细、油箱太远、加油站只有一个窗口，再强的发动机也只能半速运转——不是马力不够，而是燃料到不了气缸。于是更合理的设计顺序，往往不是“先堆算力再补内存”，而是先问：`这份数据是否值得被搬到更近处，是否能在更近处多用几次，是否能少跨一次边界`。

从第一性原理看，数据搬运之所以昂贵，主要体现在三个维度。第一是 `energy`。数据每跨一层边界，通常都比在本地寄存器或附近 SRAM 中被再次使用更贵。第二是 `time`。长链路搬运不仅有传播和访问启动开销，还会引入等待、对齐和仲裁。第三是 `interference`。数据一旦在共享路径上流动，就会和别的流量互相挤压，最后把问题从单纯的延迟变成系统级抖动和吞吐损失。乘加本身也消耗能量和时间，但在很多 AI 芯片里，真正先失控的是这三项搬运成本。

所以，`data movement first` 并不只是一个偏软件的“多做数据复用”建议，而是一个会直接重写硬件组织的原则。它首先会改写存储层次。你不会满足于“有一块大 SRAM 和一块外部 DRAM”，而会更主动地问：是否要把不同数据角色拆开，让 weight、activation、partial sum 在不同层以不同方式停留；是否要引入多级本地 buffer，让远端数据在靠近计算的过程中逐级被整形和复用；是否要让某些层更偏 staging，另一些层更偏驻留或反馈回路。这些都不是装饰，而是在减少无意义的往返。

它接着会改写数据流选择。为什么有 weight-stationary、output-stationary、activation-stationary？表面上看是“谁留在本地”，本质上看是在决定 `谁少搬、谁多搬、谁在最贵的边界上少出现`。如果权重复用最强，让它 stationary 是自然的；如果 partial sum 回路最难撑，让 output-stationary 缩短本地反馈路径就合理。也就是说，dataflow 不是单纯计算图映射问题，而是”把最贵的数据搬运剪掉谁”的选择题。就像搬家时决定”哪些东西值得放在随手包里，哪些塞进大箱子慢慢运”——你会把护照、钱包、手机放在身上（stationary），因为它们被反复使用；大件家具走货运就行，因为用完就不动了。Dataflow 就是在为不同角色的数据做这个分类。

再往下，`buffer organization` 也会跟着重排。weight buffer 设计不再是“能不能多装些参数”，而是“哪些权重最值得不回外存”； activation buffer 设计不再是“有没有一个输入缓冲”，而是“下一 tile 能否在当前计算期间无冲突就位”； accumulator buffer 设计不再是“结果先放哪里”，而是“高频读改写能否留在最短回路中”。一旦你从数据搬运优先出发，这些 buffer 的存在理由会变得非常统一：它们都在阻止某类数据不必要地回到更远层。

这条原则也会改写你怎么看 `double buffering`。如果没有 data movement first 的视角，很容易把 double buffering 看成一种“通用性能技巧”。但本质上，它是在为搬运和计算建立重叠窗口，把不可避免的搬运税尽量藏到当前计算后面。换句话说，double buffering 不是为容量而设计，而是为减少显性搬运停顿而设计。它能否成立，最终还是回到这条原则：有没有真正减少对前台计算可见的搬运成本。

再看 `HBM vs LPDDR`，这条原则同样成立。HBM 的核心价值，不是“显得高端”，而是在某些场景下把最昂贵的远端搬运边界做得更宽、更短、更省每 bit I/O 能量。LPDDR 的价值，也不是“只是便宜”，而是在更受限的产品边界里接受外层更紧，然后通过片上复用和更审慎的数据组织，把远端搬运需求压下来。二者看起来路线差很大，本质上都在回答同一个问题：哪些数据值得在最外层走多少次。

甚至连编译映射和调度策略，最终也会被这条原则重新排序。一个只追求阵列利用率、却频繁把同一份权重或激活在层次中来回翻运的映射，常常不如一个表面算力利用率稍低、但显著减少跨层流量的映射。因为后者更可能在真实芯片上赢。也就是说，NPU 优化里常见的“牺牲一点局部并行度，换更好的数据复用”并不是保守，而是在承认数据搬运常常比额外算几下更贵。

从 `Topology` 与 `Interaction` 的角度看，这条原则也非常自然。NPU 不是一堆 PE 加几块 SRAM 的集合，而是一张数据在不同节点间流动的图。只要图上的边太长、太粗、太共享，系统就会为这些边付出高税。于是最好的架构，往往不是把每个节点都做得最强，而是把图上最贵的边尽量缩短、削薄或变少。某些设计通过更大的本地 buffer 做到这一点，某些通过更激进的 tiling，某些通过让权重或输出更“stationary”，某些通过换到 HBM，某些甚至通过 near-memory。路径不同，原则一致。

这也带来一个很重要的工程判断：`不是所有减少计算次数的优化都值钱，也不是所有增加一点本地存储的优化都浪费`。如果一个优化让算术量下降 5%，但导致更多权重回取、更多 activation 回写和更差的片上对齐，它可能整体更差。反过来，如果一个优化多占几 MB SRAM，却大幅减少最远边界上的搬运次数，它可能整体更好。这个道理和通勤类似：如果公司附近的房子贵一点（多占片上面积），但每天省下两小时通勤（减少远端搬运），长期看这笔账往往是划算的。data movement first 的真正价值，就在于它提供了一个更稳的优先级排序标准。

因此，本页真正想建立的不是一句口号，而是一种评判框架：当你面对某个 NPU 设计选择时，先别问它让 TOPS 变成多少，先问它让数据少搬了没有、近搬了没有、按角色更合理地搬了没有。如果答案是否定的，那么这个优化很可能只是把问题往后推。前面整章出现的许多机制，之所以同时成立，就是因为它们都在为这三件事服务。

## 一句话理解

NPU 设计里的很多“高性能技巧”本质上都在服务同一个第一性原理：让最贵的数据少跨层、少走远路、少重复搬运，再去谈新增算力能否真正兑现。

## 建模启示

在模型里，如果想把 `data movement first` 变成可比较的指标，最直接的做法不是只记 MAC 数，而是给不同层之间的数据移动赋不同代价。

一个够用的抽象可以写成：

```text
MovementCost {
  src_level: str
  dst_level: str
  bytes: int
  latency_ns: float
  energy_per_byte_pJ: float
  contention_group: str
}
```

然后把 workload 的总成本分成两块：

```text
WorkloadCostSummary {
  total_macs: int
  total_compute_cycles: int
  total_moved_bytes: int
  total_move_energy_pJ: float
  total_move_stall_cycles: int
}
```

如果想更进一步，可以对不同移动边界赋权重，例如：

- register < L0 SRAM < L1/L2 SRAM < offchip

这样你就能把“同样 1 MB 数据移动”在不同边界上的代价区分开，而不是错误地把所有 byte 当成等价。仿真时最有价值的比较，不是某个方案少搬了多少字节，而是它少掉的是哪一层到哪一层的搬运，以及这些搬运原本是不是系统最贵的边。
