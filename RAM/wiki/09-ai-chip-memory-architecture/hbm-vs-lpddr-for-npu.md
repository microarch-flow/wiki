# NPU 选 HBM 还是 LPDDR：决策框架

上级：[AI 芯片内存架构](./README.md)
相关：[LPDDR：为了功耗放弃了什么](../05-dram-protocol-families/lpddr-low-power-mobile.md), [HBM 的成本结构为什么这么高](../08-packaging-integration/why-hbm-is-expensive.md)

## 这页在回答什么问题

NPU 外存选型不该停留在“HBM 更快”这种结论；应当如何从模型尺寸、batch 形状、成本、功耗和封装能力出发做判断。

## 正文

如果只看最表面的结论，`HBM bandwidth` 更高，`LPDDR power` 更友好，这当然都对。但对 NPU 来说，这样的判断几乎没法指导真实设计。因为外存选择不是“谁参数更强”的问题，而是“哪条路线更匹配当前工作负载、产品成本、封装能力和系统能效目标”的问题。也就是说，`HBM vs LPDDR` 不是一个单维排序，而是一道系统边界题。就像选交通工具不是"跑车一定比面包车好"——你是要在赛道上跑圈速，还是要在乡间小路上拉货？答案取决于你要解决什么问题，而不是谁的发动机更大。

先把一个最重要的误区拿掉：HBM 并不天然等于“更好的 AI 内存”，LPDDR 也不等于“只能做低端”。HBM 的长处确实很突出，尤其是高带宽密度和较低每 bit I/O 能耗，这使它特别适合高吞吐训练、大模型推理、超大阵列持续供数这类场景。但它的强项恰恰也暴露了它的前提条件：你得有足够强的片上和算法层需求，真的能把这些带宽转成有效吞吐；你还得愿意承担先进封装、热设计、供应链协同和成本结构的重量。反过来，LPDDR 的长处不是峰值带宽，而是更轻的集成负担、更友好的系统功耗、更成熟的移动或边缘生态，以及在很多中小型推理场景中“其实已经够用”的现实。

因此，做这道题时，第一步不该先问“HBM 有多快”，而该先问 `workload 的外存需求到底长什么样`。这里至少要拆成三件事。第一是 `capacity pressure`，也就是模型参数、KV cache、中间激活和 batch 工作集到底有多大。第二是 `sustained bandwidth pressure`，也就是阵列在目标吞吐下，是否会持续向外层拉取大量权重或激活。第三是 `latency/jitter sensitivity`，也就是负载是否能容忍更不均匀、更低峰值的外层供数。很多设计一上来就奔着 HBM 去，结果问题根本不在带宽，而在总容量、成本或者软件部署形态上。

举个更直白的对照。假设你在做一个数据中心训练或高并发推理加速器，片上算力很高、芯片内已有多级 SRAM、工作流希望长期保持高阵列利用率，而且模型大到权重或 KV 工作集频繁越过片上层次。这时外存的角色更像“持续高压供水系统”，HBM 的价值就非常自然。因为你最怕的是阵列长时间断粮，而 HBM 正是在为高带宽密度和持续供数能力买单。反过来，如果你做的是边缘推理、移动推理、车载本地模型执行，系统更在意整机功耗、成本、热和封装复杂度，工作负载的 batch、并发和持续外存压力也没有那么极端，那么 LPDDR 往往是更合理的解。它可能让峰值不那么夸张，但整体系统更容易闭合。

这说明外存路线和 `product envelope` 强耦合。所谓 product envelope，指的就是你允许芯片和整机承担多重的封装、散热、BOM 和电源代价。HBM 不是只让 memory subsystem 变强，它会把整颗芯片带进更重的封装与热设计世界。你不仅要为 HBM stack 本身买单，还要为 interposer、封装良率、测试复杂度、热热点分布和研发节奏协同买单。这就像开餐厅选址——市中心旺铺人流量大、曝光率高，但租金、装修、消防审批、人工全都贵；社区小店虽然没有那种黄金位置的客流优势，但整体运营成本低得多，对许多菜品来说其实已经够用。只要产品的 ASP、出货规模或上市节奏不支持这条路线，HBM 再强也可能不是合理选项。LPDDR 的优势恰恰在这里：它通常让系统更容易做到紧凑、低功耗和可量产。

但如果就此得出“LPDDR 更省事，所以大部分 NPU 都应选 LPDDR”，同样会错。因为片外路线还会反向改写片上体系。上一页已经讲过，片上带宽预算是一张内部税单。若外层是 LPDDR，总外带宽和带宽密度通常更紧，那么片上 SRAM 层次就得更努力地减少外存往返，weight buffer 要更 aggressively 驻留高复用工作集，activation 流也得更强调重叠与裁剪。这意味着你不是绕开了成本，而是把一部分系统压力转回片上架构、编译映射和数据流设计。HBM 则相反，它在很多场景里可以买到更宽松的外层供数条件，但这不代表片上随便做，因为高并发下内部带宽税单同样可能先爆。

所以，更稳的判断方式是把 HBM 和 LPDDR 看成两种不同的资源边界配置。

- `HBM`：更高外带宽密度、更低每 bit I/O 代价、更重封装成本、更高系统复杂度。
- `LPDDR`：更低集成门槛、更友好待机和系统功耗、更轻封装压力、但外带宽上限和带宽密度更紧。

这两个边界各自适合的 NPU，不只是“高端”和“低端”的差别，而是 workload 时空形状不同。若 workload 长时间维持大流量、数据重用不足以把外存需求压回片上，HBM 更容易站住脚。若 workload 可以通过较强片上复用、较小 batch、较窄并发或较低 duty cycle 运作，LPDDR 的综合性价比常常更好。

还有一类常被忽略的因素，是 `deployment pattern`。训练卡、机房推理卡和云侧大模型服务，往往可以接受更高 BOM 和散热预算，因为它们卖的是高吞吐和高密度服务能力。移动 SoC、端侧 NPU、车载推理模块，往往卖的是低功耗、低成本、长时间稳定工作和更宽的环境适应性。也就是说，外存选型不只是硬件工程判断，还和产品商业模式强相关。就像航空公司选飞机——头等舱宽体客机舒适度高、服务能力强，但只有在洲际长途航线上才划算；短途城际通勤用窄体经济机反而更赚钱。HBM 的很多优势只有在”每单位吞吐值得高价购买”的市场里才真正兑现。

如果进一步压成一个决策问题，可以按下面顺序看。先问：`外存是否真是主瓶颈`。如果主要瓶颈已经在片上带宽、算子映射或 DRAM 访问形状，那直接换 HBM 可能只是昂贵绕路。再问：`外存需求是持续性的还是尖峰性的`。HBM 更擅长长期大流量，LPDDR 有时也能应对峰值但不适合持续高压。再问：`容量与带宽哪个更紧`。如果系统主要被大容量工作集压住，而持续带宽并没那么极端，那么多颗 LPDDR 或分层外存也许更合算。最后才问：`封装、散热和 BOM 是否允许 HBM 路线`。这一步不该排第一，因为没有 workload 需求支撑的 HBM，只是在提前为复杂度买单。

从 `Capability` 的角度看，HBM 和 LPDDR 真正提供的不是两个固定数值，而是两种不同的系统可实现空间。HBM 让你更容易把高算力阵列和大外流量绑定在一起；LPDDR 让你更容易把较温和的外存系统嵌入低功耗、低成本、紧凑产品里。你最终应该选择的，不是哪一个在参数表上“赢”，而是哪一个让整机最容易在目标吞吐、目标能效、目标成本和目标量产路径上同时成立。

因此，本页真正要建立的框架是：先看 workload 外存需求形状，再看片上是否已尽量吸收流量，再看产品边界是否承受得起更重路线。HBM 是为高带宽密度和持续供数付出系统级代价，LPDDR 是为更轻系统边界接受更紧的外层带宽条件。两者没有抽象上的绝对优劣，只有目标函数是否匹配。

## 一句话理解

NPU 选 HBM 还是 LPDDR，不是“谁更快”的单轴比较，而是外存需求形状、片上复用能力、封装热设计和产品成本边界共同决定的系统路线选择。

## 建模启示

在模型里，不要只给 HBM 和 LPDDR 各填一个 `peak_bw`。更有用的做法，是把它们建成两种不同的 `offchip capability profile`。

一个最小抽象可以写成：

```text
OffchipMemoryProfile {
  type: enum { hbm, lpddr }
  capacity_GB: float
  sustained_bw_GBps: float
  access_granularity_bytes: int
  io_energy_per_bit_pJ: float
  package_cost_norm: float
  thermal_complexity_norm: float
  integration_risk_norm: float
}
```

再让 workload 显式暴露自己的外存压力：

```text
WorkloadOffchipDemand {
  model_bytes: int
  active_working_set_bytes: int
  sustained_fetch_GBps: float
  peak_fetch_GBps: float
  bandwidth_duty_cycle: float
}
```

做系统评估时，至少看三类匹配关系：

- `sustained_fetch_GBps` 是否长期逼近外存上限
- 片上复用后剩余的外流量是否仍大到必须上 HBM
- 额外吞吐收益能否覆盖 `package_cost_norm + thermal_complexity_norm`

如果再往前一步做设计空间搜索，可以把 HBM/LPDDR 看成与片上 SRAM 容量、tile 形状和目标 batch 一起联动选择的参数，而不是先拍板再让其他模块去适配。
