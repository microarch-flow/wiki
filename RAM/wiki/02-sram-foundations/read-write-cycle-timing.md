# SRAM 一次读写的 cycle-by-cycle 行为

上级：[SRAM 基础](./README.md)
相关：[字线、位线、读出放大器：SRAM 的电路骨架](./wordline-bitline-sense-amp.md), [ACT、RD、WR、PRE：DRAM 命令集为什么长这样](../05-dram-protocol-families/commands-act-rd-wr-pre.md)

## 这页在回答什么问题

一笔 SRAM 访问从地址到达、控制信号拉起，到数据真正被读出或写入，中间到底经历了哪些阶段。更关键的是，为什么“读”和“写”虽然都在访问同一个 6T cell，却不是同一条时序路径的镜像。

## 正文

在系统视角里，我们很容易把 SRAM 访问抽象成”地址进，数据出”，就像点外卖——你只关心下单后多久送到，不关心厨房里是先洗菜还是先热锅。这个抽象在很多软件层讨论里够用，但到了架构和电路边界，它会掩盖两个重要事实。第一，SRAM 的读取不是直接把某个稳定节点无代价地拿出来，而是要经过字线选通、位线差分发展、sense amp 判决这条完整链路。第二，写入也不是把值”塞进去”这么简单，而是要靠外围位线驱动压过 cell 内部的正反馈，把状态真正翻转。读和写用的是同一套阵列骨架，但临界路径和脆弱点并不相同。

先看一次典型读取。为了便于讨论，可以把它拆成五个阶段：地址译码、位线预充、字线拉高、位线差分发展、sense amp 放大并锁存结果。只有把这几个阶段分开，你才会明白为什么 SRAM 虽然快，但并不是零开销。

一个简化的读时序可以写成：

```text
Cycle    0      1        2           3             4
Addr     A ------------------------------->
Prechg   ON ---- OFF
WL       0 ------ 1 ------------------- 0
BL/BLB   1/1 ---- 1/1 -> 1/0.9 -> diff -> restore
Sense    OFF ------------- ON ---------- OFF
DataOut  X ------------------------ VALID ------>
```

上面这个图不是在表示绝对电压值，而是在说明阶段关系。`Cycle 0` 地址进入译码路径，同时上一笔访问若已结束，位线通常处于预充状态，`BL/BLB` 被拉到相同高电平。`Cycle 1` 末到 `Cycle 2`，目标行的字线被拉高，选中的 cell 通过访问晶体管接入位线。若 cell 内部存的是 `Q=1, QB=0`，那么其中一侧位线会保持得更高，另一侧则开始轻微放电。`Cycle 3` 时，差分已经足够大，sense amp 被使能，迅速把这点差异放大成完整数字结果。`Cycle 4` 起，数据可以被外围锁存或送往后续 mux/总线，同时字线关闭，位线准备回到预充状态。

这里最重要的不是记住“五个阶段”本身，而是理解每一阶段在为哪件事付账。预充存在，是因为 sense amp 要在一对尽量对称的初始条件上工作，否则小差分会被历史残留状态污染。字线不能过早拉起，是因为译码和位线准备没完成时，cell 会被无意义地接入共享导线。sense amp 不能一开始就开，是因为如果差分还太小，放大会更容易被噪声和失配误导。常见误解是把 sense amp 理解成“读完以后再做一点整理”；实际上，在高性能 SRAM 中，sense amp 是决定你能在多早时刻停止等待位线继续摆动的关键器件。

读路径的最脆弱点，是被选中 cell 的内部低节点在字线导通后可能被位线轻微抬高。这就像用听诊器听心跳——你需要贴得够近才能听清，但如果你用力按压，反而会影响心脏跳动本身。如果这个节点被抬得太多，交叉耦合反相器就可能错误翻转，这就是前一篇讲的 read stability 问题。外围想尽快看清 cell 的状态，但又不能看得太用力。于是读路径里会出现两个典型优化方向。一个方向是减少位线总电容，让 cell 更快制造出差分；另一个方向是让 sense amp 尽可能在更小差分下可靠工作，这样就不需要等位线摆幅太大。它们的共同目标都是缩短 `WL assert -> sense complete` 这一段。

再看写入。写操作看起来也会经历“地址译码 -> 字线拉高 -> 位线参与 -> 完成”的表面顺序，但其本质完全不同。读的时候是 cell 拉位线，写的时候是位线推 cell。外围写驱动器会先把 `BL/BLB` 强行设成目标差分，例如要写入 `Q=0, QB=1`，就让 `BL=0, BLB=1`。然后字线拉高，被选中的 cell 内部节点与位线相连，低位线一侧开始压低原来的存储节点，直到某个节点跌破反相器翻转点，正反馈接管，整个 cell 迅速切换到新稳定状态。

一个简化的写时序可以写成：

```text
Cycle    0      1        2             3            4
Addr     A ---------------------------------------->
WriteDrv OFF --- PREP --- DRIVE ---------------- OFF
BL/BLB   1/1 --- 0/1 ------------------------- restore
WL       0 ------ 1 -------------------------- 0
Cell Q   old ---- disturb -> flip ---------- new
WriteAck X -------------------------- VALID ------->
```

这里的关键不是位线被拉成差分，而是 cell 什么时候真正翻转。写成功的判据不是“位线已经有目标值”，而是 cell 内部正反馈已经被迫跨过翻转点，并在字线关掉后仍能稳定停在新状态。如果字线脉宽太短、写驱动太弱，或者访问晶体管相对 cell 内部保持能力太弱，就会出现位线动作发生了、cell 却没有完成翻转的情况。常见误解是认为写操作天然比读简单，因为“只是把值写进去”；实际上，写常常是更强的侵入动作，需要明确压过原有状态。

读写时序最大的不同，在于它们的成功条件不同。读成功要求“足够早地产生可判决差分，同时不破坏原状态”；写成功要求“足够强地压过原状态，并给正反馈留够翻转时间”。因此两者的关键延迟项也不同。读取更敏感于位线电容、差分发展速度和 sense amp 触发时机；写入更敏感于位线驱动强度、访问晶体管导通能力、字线脉宽以及 cell 内部翻转点。这也是为什么很多 SRAM 宏会分别给出 read latency、write latency、write recovery 甚至 minimum pulse width 等参数，而不是一个统一的“access time”。

如果把一次 SRAM 访问放到更接近系统的同步视角里，你还要再加上几个外围阶段，例如地址寄存、列 mux、输出寄存和时钟边界。于是宏观上看，SRAM 常被表现为“单周期读、单周期写”或“同步读、时钟后出数”。但这些宏观接口不应掩盖底层本质：所谓单周期，只是把上面的多个模拟与数字阶段都压缩进了一个目标时钟窗口内。一旦阵列做大、位线变长、bank 更多、工艺电压更低，这个窗口就会先从读路径或写路径中的某一段被撑爆。

这也是为什么 SRAM 与 DRAM 的时序心智模型应该明确区分。用一个比方来说：DRAM 的访问像坐飞机——值机、安检、登机、起飞、降落，每个环节都是显式暴露的独立步骤（`ACT -> RD/WR -> PRE`），因为它的行级感测和恢复成本太大，无法被藏进一个小周期内。SRAM 更像坐电梯——你按个按钮，门开，进去，到了，出来；内部的钢缆牵引、制动控制、楼层检测全藏在里面。但”藏起来”不等于”不存在”，只是因为 SRAM 的访问链更局部，所以很多阶段可以在一次片上周期内完成。后面讲多端口和阵列切分时，这种”局部但不免费”的认识会非常重要。

## 一句话理解

SRAM 的读是“cell 轻推位线，sense amp 尽早判决”，写是“位线强推 cell，正反馈完成翻转”；两者共用阵列骨架，但成功条件和临界路径并不相同。

## 建模启示

在 cycle-level 模型里，如果只给 SRAM 一个统一的 `latency_cycles`，很多情况下是够用的；但只要你关心片上带宽预算、双缓冲切换、bank 冲突或低电压模式，最好把读写拆开。至少应该显式区分 `read_latency_cycles`、`write_latency_cycles`、`recovery_cycles` 三类时间，因为它们分别对应差分发展、cell 翻转和位线/端口复位。

一个可用的离散事件草图可以是：

```text
event ReadIssue(array_id, bank_id, row_id, col_id)
event ReadSenseDone(array_id, bank_id, req_id)
event WriteIssue(array_id, bank_id, row_id, col_id, data)
event WriteCommit(array_id, bank_id, req_id)
event PortRecoverDone(array_id, bank_id, port_id)
```

对应的数据参数可以写成：

```text
SramAccessTiming {
  read_decode_cycles: int
  read_sense_cycles: int
  write_drive_cycles: int
  write_flip_cycles: int
  post_access_recover_cycles: int
}
```

如果只做粗粒度性能分析，可以把前四项分别折叠成 `read_latency` 和 `write_latency`。但如果要比较不同 bank 组织、不同端口设计，或者建模双缓冲切换是否真能隐藏访存，`post_access_recover_cycles` 往往不能省，因为很多“理论上可并行”的访问实际上会被同一 bank 或同一端口的恢复窗口卡住。
