# 单口、双口、多口 SRAM，端口数为什么是关键代价

上级：[SRAM 基础](./README.md)
相关：[Register file 为什么是一种特殊 SRAM](../03-sram-applications/register-file-as-sram.md), [bank、sub-array、mat：SRAM 阵列怎么划分才高效](./sram-array-organization.md)

## 这页在回答什么问题

为什么端口数在 SRAM 设计里不是一个“多加几根线”的局部改动，而是会同时推高面积、功耗、时序和布局难度。更实际的问题是，什么时候必须为真多端口付费，什么时候应该改用 banking、复制或时分复用来绕开这个代价。

## 正文

在系统需求文档里，“需要同时支持两读一写”“希望读写并发”“最好多路同时访问”看起来像很自然的功能要求。但一旦底层介质是 SRAM，这类要求往往会立刻变成设计的第一成本中心。原因不在于端口控制逻辑有多复杂，而在于 SRAM 的每个端口都不是一个抽象接口，而是一整套会一路穿透到 bit cell、字线、位线、sense amp、写驱动和外围布线的物理通路。端口数一增加，阵列不是“多挂几个 client”这么简单，而是在重写整个访问骨架。

先从单口 SRAM 开始看。单口的含义不是“只能每拍做一件事”，而是整个阵列对外只暴露一套读写访问通路。典型单口 SRAM 在某个时刻只能做一次读或一次写，或者在同步宏定义里接受一组地址与控制信号，然后在固定时序后返回数据或提交写入。它的好处很直接：cell 结构最简单，位线和字线数量最少，sense amp 和写驱动可以被整齐共享，面积和功耗都最省。代价同样明确：所有并发访问需求都必须在阵列外部排队、仲裁或被拆散。

双口 SRAM 看起来只是“多一套访问能力”，但它已经可以有完全不同的实现语义。最常见的一类是 `1R1W`，也就是一个读端口、一个写端口，适合 FIFO、queue、某些 buffer 和部分 cache 结构。另一类是 `2RW`，两个端口都能独立读写，这就显著更贵。这里的关键不是名字，而是你是否真的需要两个操作在同一时刻落到同一 bank、甚至同一个 word 上仍保持正确语义。功能语义越强，底层要付出的物理代价越高。

为什么端口数会这么贵，首先要回到 bit cell 本身。标准 6T cell 之所以高效，是因为它只服务一套差分位线和一根字线控制下的访问晶体管。你如果要支持更多独立端口，最直接的方法是给 cell 增加额外访问晶体管和额外位线。于是 6T 很快会变成 8T、10T、12T 甚至更复杂的变体。每加一套端口，cell 面积会上升，列方向和行方向的布线密度也会上升，寄生电容随之增加，最终不仅每 bit 更贵，访问时间也更难压低。常见误解是觉得“多端口主要贵在外围 mux 和仲裁”；实际上，真正昂贵的部分往往是 cell 和阵列本体被迫变胖了。

第二个代价来自位线和 sense amp 资源不再能像单口那样简单共享。一个端口如果要独立读，就需要自己可控的感测路径；如果要独立写，就需要自己可控的写驱动路径。端口越多，阵列外围的 sense amp、预充电路、写驱动器和列 mux 数量都会迅速膨胀。更糟的是，这些电路不是“只长在边缘上”就没事，它们会反过来限制阵列能做多宽、读写周期能压多短，以及电源分布和时钟边界怎么收敛。

第三个代价来自冲突语义。单口 SRAM 的冲突模型很简单，同一时刻只有一次访问。多端口则必须回答更难的问题：同一拍两个端口若指向同一地址，是返回旧值还是新值；两个写端口同时写同一 word，谁赢；一个端口读、另一个端口写同一地址时，是否支持 write-through 或 bypass 语义。这些问题不是纯粹的“接口定义”，因为你定义了什么语义，底层就要用更复杂的比较、前递或互锁逻辑去兑现。很多多端口 memory 宏之所以昂贵，不只是因为能并发访问，还因为它们承诺了更强的一致性语义。

这也是为什么真实系统里常常不愿意直接堆“真多端口”，而会优先尝试替代策略。最常见的替代是 `banking`。如果两个请求大概率打到不同 bank，那么与其做一个真双口大 SRAM，不如做两个单口 bank，再用地址映射把并发分散开。这样做的优势是面积和位线负载都更好控制。代价是并发能力从“逻辑保证”退化成“依赖访问分布”：只要两个请求撞到同一 bank，冲突仍然发生。第二种替代是 `replication`，也就是把只读或读多写少的数据复制到多个阵列实例里，用空间换读端口。第三种替代是 `time-multiplexing`，也就是把一个更快时钟下的单口或双口资源在多个微拍中复用给多个逻辑端口。它能省面积，但会提高时序和时钟域设计难度。

什么时候必须上真多端口？最典型的场景是 register file。一个标量或向量执行管线在同一拍里往往天然需要多个源操作数读口和至少一个写回口，这不是通过简单 banking 就能完全规避的，因为同一周期读取哪些寄存器由动态指令流决定，冲突概率高且不可接受。因此 register file 往往愿意为多端口付出极高面积和功耗成本。相反，很多 scratchpad、DMA buffer、NPU local SRAM 并不真的需要“任意地址的完全并发”，它们更适合通过 bank 划分、数据布局和访问调度把需求重写成多个单口或 1R1W 子阵列的问题。

cache 处在中间地带。L1 cache 经常要面对取指、load/store、tag 查找、数据返回等近似并发的需求，但设计者并不总是用真多端口 data array 去硬扛。更常见的做法是让 tag/data 路径分层、用多 bank、多 pipe stage、way prediction、bypass network 或 duplicated tag array 来平衡成本。这个现象本身就说明：端口数不是一个独立参数，而是与访问模式、语义要求和系统流水深度共同决定的设计点。

从时序角度看，多端口的难点还在于你不是只增加“通路数量”，而是在增加“同时成立的最长路径数量”。单口 SRAM 只需要保证一条读路径或写路径在周期内收敛；多端口则要保证多个端口的字线驱动、位线差分、sense amp、写驱动甚至冲突仲裁都在更复杂耦合条件下同时稳定工作。端口越多，阵列布线越拥挤，串扰和寄生越重，功耗峰值也越高。因此，多端口设计常常不是慢在逻辑判断上，而是慢在阵列物理实现上。

所以讨论端口数时，真正该问的不是“我想要几个端口”，而是“我需要哪种并发语义，以及这个语义是否值得用真多端口去实现”。如果访问模式可调度、可分块、可按 bank 分散，那么 banking 往往比真多端口划算；如果读远多于写，复制可能更合适；如果系统允许更细粒度时间切分，time-multiplexing 也可能成立。只有当并发访问既强、又细粒度、又不能接受冲突或额外拍数时，真多端口才会成为合理答案。

## 一句话理解

SRAM 的端口数之所以昂贵，是因为每个端口都会穿透到 cell、位线、sense amp 和冲突语义，而不是只在外围多加一层接口逻辑。

## 建模启示

在架构模型里，很多人喜欢直接给片上 SRAM 标一个“2 ports”或“4 ports”，但如果不再往下说明它是 `true multi-port`、`banked pseudo-port` 还是 `time-multiplexed logical-port`，这个数字几乎没有解释力。至少需要把“并发能力来自哪里”显式建模，否则模型会高估可用带宽并低估面积和功耗代价。

一个实用的数据结构可以把这几种来源分开：

```text
SramPortModel {
  physical_port_type: enum { SINGLE_RW, ONE_READ_ONE_WRITE, TRUE_MULTI_RW }
  logical_read_ports: int
  logical_write_ports: int
  bank_count: int
  replicated_copies: int
  time_mux_factor: int
  same_bank_conflict_penalty_cycles: int
}
```

如果只关心功能吞吐，`logical_read_ports` 和 `logical_write_ports` 也许够用；但只要开始做面积、频率或带宽预算，`physical_port_type` 和 `bank_count` 就必须保留，因为 `4 logical read ports` 通过 `4-bank single-port` 和通过 `true 4R cell` 实现，代价完全不同。一个对应的冲突判定草图可以是：

```text
if accesses_in_cycle <= available_physical_service_slots:
    serve_all()
else:
    if banked and conflict_on_same_bank:
        stall(conflict_penalty)
    else:
        arbitrate_or_pipeline()
```

如果后续要建模 register file、L1 cache 或 NPU scratchpad，这个区分尤其重要。因为很多上层“并发访问需求”，本质上并不是要求真多端口，而是要求“不发生不可接受的结构冒险”；两者在实现和成本上差别很大。
