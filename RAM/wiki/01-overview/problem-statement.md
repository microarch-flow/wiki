# 为什么存储器是体系结构里最难的部分

上级：[概览](./README.md)
相关：[速度、容量、成本、功耗四角矛盾的根源](./memory-hierarchy-tension.md), [把 register、cache、scratchpad、DRAM、HBM 看作一个系统](../07-system-architecture/memory-hierarchy-as-system.md)

## 这页在回答什么问题

为什么计算系统里的很多性能问题，最后都不是算力问题，而是存储器问题。更具体地说，为什么存储器总是在同时承受物理、电气、时序、封装、控制器和工作负载六个方向的拉扯。

## 正文

体系结构里有很多复杂模块，但存储器之所以特别难，不是因为它的局部机制最多，而是因为它最容易把不同层级的约束耦合到同一个结果变量上。你看到的一次 load miss、一次 DMA stall、一次 NPU pipeline 气泡，表面上都是“数据没及时到”，但它们背后可能分别对应完全不同的根因：片上 SRAM bank 冲突、DRAM row conflict、memory controller 调度失配、封装带宽不够、甚至 workload 自身没有提供足够的数据复用。也就是说，存储器问题天然不接受单层解释。

算力模块的很多问题可以在局部闭合。一个乘加阵列面积不够大，可以多堆一些 PE；一段流水线频率上不去，可以重切时序路径；一个功能单元吞吐不够，可以复制实例。但存储器很少允许这种线性扩展。你不能简单把一个 DRAM channel 的频率继续往上提来无限换带宽，也不能把片上 SRAM 无限做大而不付出访问延迟和漏电代价，更不能假设把 cache 再加一层就一定能改善系统表现。每一次“扩资源”的动作，都会沿着距离、布线、电源、热和控制复杂度这几条链路把副作用带回来。

这也是为什么存储器问题总是横跨多个物理尺度。最底层是 bit cell 级别的稳定性问题。SRAM 要解决双稳态存储和读写扰动，DRAM 要解决电容漏电和破坏性读出。再往上一层是阵列组织问题：位线多长、sense amp 怎么布、bank 如何切分、端口数怎么控制。再往上是接口和时序问题：DRAM 为什么要有 `ACT/RD/WR/PRE`，为什么存在 `tRCD/tRP/tRAS/tRFC` 这些约束。继续往上是控制器问题：地址映射怎样决定 row locality，FR-FCFS 为什么既有效又不公平，refresh 为什么会变成调度问题。到系统层，则要回答 cache、scratchpad、DMA、NoC、HBM 和软件访问模式如何共同决定有效带宽。这几层并不是串联的，而是相互回灌的。

一个典型例子是“为什么理论带宽很高，真实程序还是跑不满”。这不是一个协议层的小问题，而是一串跨层因果链。因为 DRAM 需要先开行再列访问，所以访问模式如果缺少 row locality，就会把更多请求变成 `PRE -> ACT -> RD/WR` 的长路径。因为 bank 数量和地址映射是有限的，多个流即使总流量不高，也可能集中打到同一组 bank 上。因为控制器往往偏好 row hit 和读优先，请求等待时间会受到队列混合形状影响。因为总线存在读写切换和 refresh 插空，纸面带宽还会继续折损。最后到程序视角，就只剩下一个现象：memory bound。常见误解是把这类问题理解成“DRAM 不够快”；实际上，很多时候真正不匹配的是访问模式与硬件组织之间的关系。

存储器难的第二个原因，是它没有统一的“最优方向”。算力单元的优化目标往往可以压缩成更高吞吐、更低面积或更低功耗，而存储器的优化目标从一开始就是多目标竞争。低延迟、容量大、功耗低、成本低、带宽高、可扩展、可维护，这些目标不会自然对齐。服务器主存愿意接受 DIMM 带来的更长电气距离，因为它优先看容量扩展和替换便利；手机愿意把内存做成 PoP 或 MCP，因为它优先看面积和待机功耗；AI 加速器愿意为 HBM 和先进封装买单，因为它优先看带宽密度和每 bit 能耗。这里不存在脱离场景的最佳存储器，只有在给定系统目标下更合适的局部最优。

第三个困难来自软件与硬件之间的契约并不对称。很多计算单元的行为由 ISA 或明确协议控制，边界相对清晰；而存储器系统中，大量行为是“半显式”的。软件知道自己发了 load/store 或 DMA，但不知道这个请求最终命中了哪一级、打到了哪个 bank、是否遇到 refresh、是否与别的 master 竞争、是否被 page policy 误判。cache 试图用透明性减少软件负担，scratchpad 则反过来把更多控制权交还给软件。对架构师来说，这意味着存储器设计不仅是硬件内部组织问题，还是“哪些复杂性由硬件吞掉，哪些复杂性暴露给软件”的接口设计问题。

对于 AI 芯片和架构探索，这个问题会更尖锐。许多 workload 的算术强度并不低，但仍然受存储器限制，不是因为单次 DRAM 延迟过大，而是因为整个数据搬运路径太长、太窄、太不连续。权重、激活、部分和在不同层次之间来回移动，每一级都可能形成新的带宽瓶颈。此时如果只看某个 HBM 峰值数字，或者只看某个 SRAM 总容量，都会得到错误结论。真正需要回答的是：数据在哪一层复用、哪一层搬运、哪一层排队、哪一层发生冲突，以及这些事件如何叠加成端到端的 stall。

因此，说“存储器是体系结构里最难的部分”，并不是一句感叹，而是一个很具体的技术判断。它难在每一个局部机制都在为别处的约束付账，难在每一个系统现象背后都可能站着一串跨层因果链，也难在你很难只靠增加某一种资源就把问题单独消掉。后面整套 wiki 的结构，就是为了把这些纠缠的链条一段段拆开，再在系统层重新拼回去。

## 一句话理解

存储器最难，不是因为它“概念多”，而是因为一次看似简单的数据访问，往往同时受 cell 物理、阵列组织、协议时序、控制器调度、封装距离和访问模式共同决定。

## 建模启示

这篇对应的核心建模原则是：不要把“memory”当成一个黑盒延迟常数。哪怕在高层性能模型里，也至少要把存储路径拆成几个会独立产生等待的阶段，例如 `onchip_queue`、`bank_service`、`bus_turnaround`、`refresh_block`、`offchip_transfer`。如果把这些来源全部折叠成一个 `avg_mem_latency`，模型会失去解释力，也无法回答“瓶颈到底在哪一层”。

一个最小可用的事件视角可以是：

```text
event LoadMiss(req_id, addr, source_master)
event QueueEnter(req_id, mc_id)
event RowActivate(req_id, bank_id, row_id)
event DataTransfer(req_id, bytes)
event ResponseReturn(req_id)
```

仅关心系统级吞吐时，可以把 cell 级读写细节折叠掉，但至少要保留“排队”“bank 竞争”“数据传输”这三类延迟来源。如果关心尾延迟、QoS 或 worst-case 行为，还必须进一步显式建模 `refresh_block`、`read_write_turnaround` 和 `master_priority`。一个对应的数据结构草图可以写成：

```text
MemoryRequest {
  addr: uint64
  source: MasterId
  arrival_cycle: uint64
  mapped_channel: int
  mapped_bank: int
  mapped_row: int
  service_state: enum
}
```

这里最重要的不是字段名本身，而是建模时承认：同一个地址请求的成本，不是固定属性，而是“当前硬件状态 + 当前队列状态 + 当前访问模式”的函数。
