# 速度、容量、成本、功耗四角矛盾的根源

上级：[概览](./README.md)
相关：[同样是 RAM，为什么 SRAM 和 DRAM 走向了完全不同的工程路径](./sram-dram-divergence.md), [带宽与延迟：为什么不能兼得](../07-system-architecture/bandwidth-vs-latency-fundamental.md)

## 这页在回答什么问题

为什么任何一种存储器都不可能同时把速度、容量、成本和功耗做到最好。更关键的问题是，这四个目标之间的冲突到底从哪里来，为什么它不是“现有工艺还不够先进”的暂时问题。

## 正文

“存储器有速度、容量、成本、功耗之间的 trade-off” 这句话本身没有错，但如果只停在这一步，它几乎没有解释力——就像说”减肥需要少吃多动”，正确但无法指导行动。真正重要的是看清：这四个目标不是人为列出来的评价维度，而是由三个更底层的物理事实共同推出来的。第一，数据存储需要占据物理面积。第二，数据访问要穿过真实存在的导线和驱动器。第三，数据离计算越远，每一次读写都要付出更多时间和能量。这三个事实一旦成立，四角矛盾就不是”设计风格差异”，而是硬约束。

先看速度与容量为什么天然冲突。这里有一个很直观的物理类比：图书馆。一个只有一面书架的小阅览室，你伸手就能拿到任何一本书；但一座百万藏书的图书馆，你可能要走过长长的走廊、乘电梯到不同楼层，拿到书的时间不可避免地变长。存储器阵列面临同样的问题——要把容量做大，就得让单 bit 更省面积，同样面积里塞进更多 bit。但 bit 一旦变多，阵列就会变大，字线和位线就会变长，感测和驱动就会更慢，访问路径上的电容负载也会更重。容量扩大不是一个孤立的”多放点数据”的动作，而是把访问路径整体拉长。SRAM 之所以快，是因为它愿意用更大的 bit cell 和更重的外围电路换取更短、更强壮的读写路径（小阅览室策略）；DRAM 之所以容量大，是因为它把单元做得极省面积，但接受了更复杂、更慢的访问过程（大图书馆策略）。常见误解是把”高容量”理解成纯粹的制造能力问题；实际上，容量一旦提升到阵列规模，访问延迟和感测难度就会跟着上升。

再看速度与功耗为什么也经常冲突。很多人会本能地以为“更快”只是“更高频”，而更高频只是把时钟打快一点。真实情况是，速度提升通常依赖更强的驱动、更宽的并行通路、更激进的时序余量和更频繁的数据翻转，这些都会直接推高动态功耗。即使先不谈频率，单次访问想变快，也常常意味着更多外围电路要提前上电、预充、感测、比较或广播。对于片上 SRAM，这表现为更高的端口代价、更长的全局布线和更重的时钟负担；对于片外 DRAM，这表现为更强的 I/O 驱动、更严的信号完整性要求和更高的每 bit 传输能量。速度越极致，功耗就越不可能“顺便”变低。

成本与速度的冲突也不是营销口径，而是面积、工艺和封装共同决定的。低延迟存储往往需要更大的 bit cell、更多 sense amp、更复杂的端口组织、更短的互连距离，甚至要把存储器直接放到更昂贵的位置，例如芯片上或先进封装里。这些都会把“每 bit 成本”抬高。DRAM 相对便宜，不是因为它物理上更简单，而是因为它用 1T1C 这条路线把面积效率推得足够高，从而让每 bit 成本下降；HBM 带宽高，也不是凭空得到的，而是通过堆叠、TSV、interposer 和更复杂测试流程把成本推了上去。这里的关键不是“技术越先进越贵”这种空话，而是低延迟和高带宽往往依赖更低的距离成本与更高的互连密度，而这些条件本身就不廉价。

功耗与容量之间同样存在深层张力。单看静态存储，好像容量大只是多放一些 bit，功耗未必立刻升高；但一旦进入真实系统，容量增加意味着更大的阵列、更长的互连、更复杂的刷新或保持机制，以及更高的背景功耗。对 DRAM 来说，容量越大，refresh 需要覆盖的 cell 越多，刷新对可用带宽和能量的侵占就越难忽略。对 SRAM 来说，容量越大，漏电总量就越高，尤其在先进制程下，保持电压和 standby power 会越来越难压住。也就是说，大容量不是白来的“存得更多”，而是在持续支付保持和访问这些 bit 的系统级成本。

如果把这几个冲突放到同一张图里，就能看见为什么现代系统必然走向层次化，而不是寻找”一种统一的最好存储器”。这跟城市的仓储系统是同一个逻辑：你不会把所有货物都放在市中心的便利店里（太贵、放不下），也不会把今天就要卖的货放在郊区大仓库里（取货太慢）。于是就形成了”柜台 -> 店面仓库 -> 区域配送中心 -> 远郊大仓”的分层体系。存储器也一样：离计算最近的一层把速度放在第一位，因此接受小容量和高每 bit 成本，比如 register file、L1 cache、局部 scratchpad。中间层会在容量和速度之间折中，比如更大的片上 SRAM、L2/L3、片上共享 buffer。更远的一层把容量和成本放在前面，因此愿意接受更高延迟，例如 DDR 或 LPDDR。再往高带宽方向走，像 GDDR 和 HBM，则是在容量与带宽密度之间重新寻找新平衡点。层次化不是工程师”喜欢复杂”，而是因为单一存储层不可能同时贴住所有目标。

这也是为什么“带宽、延迟、容量、成本、功耗”这几个词不能分开看。举一个常见场景：AI 加速器觉得片外带宽不够，于是换 HBM。表面上看是用更贵内存换更高带宽，实际上发生的是整套最优点迁移。接口更宽了，互连更短了，每 bit I/O 能耗下降了，但封装成本、热设计压力、良率风险和可扩展性边界都变了。如果不把这些变量放在一起看，就会误以为 HBM 只是“更快的 DRAM”，而不是另一组工程约束下的重新平衡。

还有一个容易被忽略的点：这四角矛盾不是静态的，它会随着工作负载变化而移动。就像同一条公路在早高峰、午间和深夜的瓶颈完全不同——早高峰堵在匝道容量，午间可能是施工占道，深夜反而是照明和安全的问题。同样一套存储层次，在高局部性 workload 下可能主要受容量和命中率影响，在流式访问 workload 下则主要受带宽和搬运距离影响，在实时系统里又可能转化为尾延迟和确定性问题。因此，讨论存储器取舍时，必须把”谁在访问、按什么模式访问、是否能复用、是否允许软件管理”这些条件一并带上。脱离 workload 谈最优存储器，没有意义。

所以，这一页真正想建立的不是一句“有 trade-off”，而是一个更硬的判断：存储器层次之所以存在，是因为物理面积、互连距离和访问能量三个底层事实强迫系统不断分层。你可以通过工艺改进、封装改进、控制器改进把某一角向前推，但不可能把四个角一起拉到极致。后面 SRAM、DRAM、HBM、scratchpad、cache、memory controller 的所有具体机制，都是围绕这个基本张力展开的局部应答。

## 一句话理解

速度、容量、成本和功耗的冲突，本质上来自 bit 存储面积、访问路径长度和数据搬运能量三者不能同时最小化，所以现代系统只能靠分层而不是靠单一存储器解决问题。

## 建模启示

这一页对应的核心抽象，不是某个具体 timing 参数，而是“每一层存储都必须有自己的优化目标函数”。在性能模型里，不能只给每层填一个 `latency` 和一个 `capacity` 就结束，至少还要保留能反映这四角张力的字段，例如 `energy_per_access`、`cost_per_bit`、`sustainable_bandwidth`、`background_power`。否则模型只能回答“哪层更快”，回答不了“为什么系统不把这一层无限做大”。

如果只关心体系结构级比较，一个可用的简化数据结构可以是：

```text
MemoryTier {
  name: string
  capacity_bytes: uint64
  hit_latency_cycles: uint32
  sustainable_bandwidth_Bps: float
  energy_per_access_pJ: float
  background_power_mW: float
  cost_per_bit_norm: float
}
```

在更高层的 design-space exploration 里，可以把不同存储层的选择建模成受约束优化问题，而不是固定配置。例如：

```text
objective = minimize(total_time, total_energy, total_cost)
subject to:
  working_set_fit_prob >= target
  peak_power <= budget
  package_io_count <= limit
```

如果只关心粗粒度性能，`cost_per_bit_norm` 这类字段可以不进入周期级仿真，但在架构探索时必须保留，因为很多设计之所以不可用，并不是性能不达标，而是成本、功耗或封装约束先越界了。
