# Wiki 与博客设计规则

本文件记录整理本仓库 Wiki 和博客时的共同要求，供内容作者、维护者和协作工具使用。专题可以在本文件之外维护更具体的术语、模板和技术约束。

规则随需求调整。用户可以随时要求增加、删除或修改；维护者也可以在发现问题时提出调整。以本文件的当前内容为准，并用 Git 记录变更。当前任务中用户的明确要求优先，不把一次性的具体选择自动固化为长期规则。

## 1. 目标与内容范围

- 文章要**通俗易懂，也要直指本质**。让读者知道问题是什么、为什么发生、机制如何起作用，以及结论在什么条件下成立。
- 以读者建立认知的过程组织知识，而不是按知识分类照搬教材目录。从具体问题出发，沿着因果关系，在真正需要时引入新知识，使读者能够利用已建立的认知独立推导和解释现象。
- 以中文为主，运用约 80% ASD-STE100 的写作原则：句子简短、表述明确，每段尽量只解释一件事。普通正文每段不超过 150 字，公式、表格、代码等按其自身的阅读需要组织。控制的是认知负担，不为缩短文字而省略必要推导。术语保持准确、一致；重要术语首次出现时按需要解释。
- Wiki 是关联知识和技术上下文的来源，博客面向公开阅读。打磨文章时结合现有 Wiki，检查前后章节、术语和链接；不要默认已有内容一定正确。
- 按用户指定的范围和顺序逐篇打磨。已有内容可以逐步完善，不要求一次性改写整套 Wiki。

## 2. 技术内容与资料

1. 先梳理文章所在章节、相关概念及已有链接，再确定本文要解决的问题和阅读边界。阅读相关正文，核查前置知识是否已经介绍、介绍到了什么深度，不仅凭标题判断覆盖情况，也不默认读者已掌握未介绍的概念。跨章节内容优先利用已有解释，必要的前置认知应简明回顾，避免只给链接或重复完整推导。
2. 编写或实质性打磨技术内容时，结合 Wiki 上下文和联网检索核查关键事实。优先使用规范、权威教材、器件厂商资料、官方文档和原始论文等可靠来源；根据主题选择读者易于访问的资料。
3. 对重要事实、数据和外部观点提供可追溯的来源。核对来源的适用对象、版本、时间与条件，不把某一器件或实现的参数当作普遍规律。资料无法核实时，明确说明，不编造引用或数字。
4. 区分事实、假设、推论、建议和待验证结论。区分概念的定义、特定条件下的现象及产生现象的机制，不将特例写成定义。明确公式、模型和示例的前提、单位、观察边界及必要的边界条件；构造案例和理想估算不能写成实测结果。
5. 解释机制时，按需要说明输入、输出、状态、职责和执行过程。重视因果推导：先解释为什么会发生变化，再解释变化怎样引起下一步结果；不要用术语、现象列表或同时发生的两个现象代替因果关系。先从简单、可观察的对象和变化出发，再用合适的例子、公式、结构图或反例提高抽象层次。涉及不同方案时，说明适用条件、收益和代价。
6. 避免没有依据的绝对判断，例如“总是”“一定更快”或“最难”。类比只用于帮助理解；回到技术问题时，要说明类比的边界。

网页样式或导航等纯界面修改，不必为了满足本规则而强行增加技术内容或外部引用。

## 3. 文章组织与导航

### 3.1 认知主线与知识边界

- 解释技术原理时，先在宏观层面简明交代是什么（What），为什么需要、解决什么问题（Why），再深入工作机制和因果（How），最后回到原来的问题，并联系可解释的工程现象与设计取舍（Implications）。这是一种思考方式，不强制各篇采用四个固定小节。
- 正文优先回答一个清楚的核心问题。由真实问题驱动知识的引入：说明已有认知为什么不足、接下来需要理解什么，再引入相应概念。不要仅因为某个知识点重要，就让读者学习它；不要为了介绍一个物理规律或术语而构造问题。
- 对于存在简单、常见应用场景的器件或电路，优先从该场景的真实需求与可观察效果切入，让读者先知道为什么需要这种功能，再引出实现它的器件、电路及其工作机制。应用场景只承担建立认知需求的作用，不提前展开与主线无关的机制，也不强行构造场景。
- 区分以下三类知识，并据此安排阅读层次。知识归属取决于当前文章要解决的问题，同一知识点在不同文章中可能属于不同层次。

  | 层次 | 判断依据 | 组织方式 |
  | --- | --- | --- |
  | 核心知识 | 不理解其机制，就无法正确理解后续核心机制 | 正文展开必要的因果推导和图解 |
  | 支撑知识 | 知道结论、关系或适用条件即可继续理解主线 | 简明交代，必要时给出直观算例 |
  | 深化知识 | 不影响主线理解，但有助于定量分析、拓展应用或深入理解 | 归入深化阅读、选读或更合适的文章 |

- 审查每个知识点的必要性：如果省略其详细解释，读者仍能正确推导后续核心机制，就考虑精简或下沉。主线必须自洽，不要求读者展开选读才能继续阅读。追求本质不等于无限向下追溯，也不等于删除必要的技术细节。
- 尽量沿用同一个观察视角和认知模型，持续跟踪同一类对象、状态及变化。例如半导体追踪电子和能带状态，数字电路追踪信号，计算微架构追踪数据和指令，存储追踪访问请求，互连追踪数据包，编译器追踪程序语义和 IR。需要转换抽象层次时，说明新旧模型的对应关系。
- 优先利用当前研究对象解释机制，能够直接结合现有对象讲清楚的概念，不另建算例打断主线。选择具体、简单、可观察的例子，不为了贯穿案例而过早引入复杂任务。标题应对应真正需要解决的问题；没有独立认知价值的次要问题可合并到相关小节或选读。

### 3.2 编写与打磨的思考顺序

新编文章或实质性重构正文前，结合文章目标梳理以下问题。这些是编写和评审的参考，不是必须逐项输出的固定模板。

1. 确定核心问题：读者读完这篇文章应该能够理解或解释什么？
2. 核查前置认知：已有文章介绍了什么，当前还缺少什么？
3. 构建因果主线：各个知识点怎样由前一个问题自然引出，最终回到核心问题？
4. 设计图解：需要追踪哪些对象、状态、方向和变化过程，怎样直观表现？
5. 审查知识边界：哪些机制必须理解，哪些只需知道结论，哪些应移入深化阅读或其他文章？

### 3.3 文章导航与链接

- “接下来怎么读”等章节入口应与目标文章及侧边导航的名称对应。章节按顺序阅读时，正文列表与导航顺序保持一致；跨章节推荐可以按阅读目的组织，并说明选择理由。
- 具体文章应能在侧边导航中找到对应项，并有清晰的当前页面高亮。选中状态不应改变导航项的缩进或使相邻文字跳动。
- 文章标题前提供面包屑，反映实际层级；有目标页的上级可点击，当前页面可识别。导航和上级面包屑可以使用易识别的短名称，正文和当前页面面包屑可以保留完整标题；两者应清楚对应，悬停时可查看完整标题。
- 修改标题、路径或章节结构时，同步检查相关链接和导航。尽可能保留已有 URL 与锚点；确需变化时，为旧链接提供合理的兼容方式。

## 4. 视觉、图解与交互

- 保持正文、表格、公式、说明块和图形与网站整体风格协调，并保证文字对比度。避免出现与页面背景突兀割裂的大块纯白区域。
- 公式、事件路径和说明不是代码时，使用适合阅读的样式；真实代码仍应保留代码格式。布局应便于长文阅读，并适配桌面和手机。
- 图形应承担解释作用，帮助理解关键结构、因果或过程，而不是仅作装饰。优先展示具体结构、前后状态、变化方向和过程中可观察的量。需要展示机制演变时，优先采用按顺序排列的静态图，使读者可以连续阅读、不依赖点击交互；动画与交互可作为选读和探索工具，不强制使用。
- 统一同一认知模型中对象的颜色、符号、名称和坐标含义；不同图解之间如果改变观察角度、坐标或尺度，应说明变化，避免读者误以为对象或机制发生了变化。独立正文图默认居中，成组对照图可按阅读需要并排或顺序排列，并兼顾电脑和手机的阅读体验。
- 图解的状态变化、方向、数量和文字必须与正文一致。明确箭头、状态符号、坐标、比例各自表示什么，以及图中省略的条件；区分教学示意、模型结果和实际测量，不把抽样示意画成真实占比，不把动画当作电路仿真或性能证明。
- 图解应有可读的文字说明，并按需要支持键盘操作、减少动态效果和窄屏阅读。独立图解入口是否突出展示，取决于实际内容质量和用户意愿。

## 5. 网站结构与公开访问

- 当前微架构内容只是技术笔记中的一个系列。站点结构应允许未来增加其他系列；不要预先固定尚未确定的系列名称，也不要创建空栏目冒充已有内容。
- 优先保持系列配置和页面结构易于扩展。新增系列的实际名称、内容和发布方式由届时需求决定。
- 博客面向所有读者公开访问。经用户授权发布时，除本地预览外，还要检查构建、部署和公开地址上的实际结果；本地可访问不等于已经公开。

## 6. 验证与维护

- 内容修改后，按改动范围检查术语、数字与公式、前提条件、引用来源以及相关 Wiki 链接。不要把尚未验证的推断写成事实。
- 评审文章时沿主线通读，检查每个概念引入时是否有明确的认知需求、前置认知是否充分、因果关系有无跳步、图文是否一致，以及次要问题是否打断主线。不仅检查技术事实是否正确，还要检查读者能否利用已建立的认知理解后续内容。
- 涉及网站时，检查文章标题、导航高亮、面包屑、阅读顺序、图文排版及适用的桌面和手机视图。改动交互时，检查相关状态与操作方式。
- 使用 [网站构建与维护](../website/README.md)中的构建和检查方法。只运行与修改相称的验证；生成目录不是正文维护位置。
- 新增独立博客仓库时，在该仓库的协作说明中显式引用或同步本规则；本仓库的 `AGENTS.md` 不会自动约束其他仓库。
