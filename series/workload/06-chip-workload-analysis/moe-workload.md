# MoE 工作负载：从专家分配计数到数据交付

上级：[专题导读](README.md)

MoE 的算法选择形成专家负载，专家放置进一步形成通信。本文先算逻辑工作量，再说明怎样转换为指定硬件上的流量。

## 构造一个可核算的分配

设 4 个 token，每个 token 有 8 个 FP16 元素，采用 top-2。专家选择依次为 $(0,1),(0,2),(0,1),(1,2)$。这里假设所有选择都被接纳，没有容量溢出，也没有共享专家。

| 专家 | 接收的 token 数 |
| --- | ---: |
| 0 | 3 |
| 1 | 3 |
| 2 | 2 |

总共有 8 次 token-expert 分配。路由前输入是 4×8×2 = 64 B；若为每次分配分别交付完整向量，dispatch 的逻辑载荷为 8×8×2 = **128 B**。

## 专家计算与返回

若专家是两层 FFN，维度为 $d\rightarrow m\rightarrow d$，忽略偏置与激活，每次分配约为 $4dm$ FLOP。构造例 $d=8,m=16$，每次 512 FLOP，8 次合计 4096 FLOP。门控 FFN、共享层或不同专家尺寸需要另算。

若每次分配返回一个 8 元素 FP16 向量，返回逻辑载荷也是 128 B。合并器使用路由权重，将每个 token 的两个结果合成为一个输出。路由分数、索引、重排与合并开销不在上述 FFN 计数内。

若门值已生成，对每个输出元素做两次乘法和一次加法，则合并另需 $4\times8\times3=96$ FLOP。构造一个两设备放置例。四个 token 都源于设备 A，专家 0、1 在 A，专家 2 在 B。只有两次分配发往 B，每次携带 16 B 向量，因此 A→B 的输入载荷为 32 B，B→A 的返回载荷也是 32 B。这里按单播向量计，未计路由元数据、包头与填充。移动专家会改变跨设备字节数，原来的 8 次分配仍然成立。

## 逻辑载荷为什么不是网络流量

专家与 token 若在同一端点，交付可能不经过网络；多个目的端可能共享分发路径；分块、复制、包头和填充又会改变传输量。应记录每次交付的源、目的、字节数、依赖与完成事件。

NoC 的 byte-hop 还取决于路径长度。跨设备 All-to-All 是一种实现组织方式，不是每个 MoE 层在任意拓扑上的强制通信原语。具体网络建模见 [MoE 通信案例](../../interconnect/NOC/06-ai-noc-specifics/workload-moe-routing.md)。

## 容量、排队与完成时间

总专家参数需要存放，但每次激活只使用其中一部分。小专家批次可能难以利用计算单元；热点专家可能延长完成时间；权重按需加载又会增加数据搬运。是否发生瓶颈，需要把这些需求与服务能力比较。

分析输入应包含 token 到专家的实际分配、容量策略、专家位置、权重驻留和到达时间。只给“平均每专家多少 token”不足以预测尾部等待。

## 复核步骤

先核对每个 token 的接纳专家数，再检查各专家计数之和，最后分别统计 dispatch、返回和 combine。改变放置时固定相同分配，才能分清是模型路由变化还是网络映射产生了收益。
