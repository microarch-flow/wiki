# 一条点到点专线，什么时候需要仲裁和事务标识？

上级：[02 基础对象与事务语义](./README.md)

<span id="bus-vs-noc-vs-point-to-point"></span><span id="这页在回答什么问题"></span><span id="三者的分界不是线多线少"></span>
在[桥和 DMA 争用一个 SRAM 出口](./arbitration-ordering-backpressure.md)的例子里，先把 DMA 移开，给桥和 SRAM 控制器之间留一条专线。只有一方会发读地址，当然不用在两个发起者之间轮流挑选。可如果桥再读一个字，先后两笔都还没返回，桥怎么知道下一份数据该交给谁？

## 只有一对端点，为什么还会停？

<span id="point-to-point-适合固定关系"></span>
**点到点**（point-to-point）说明这段连接的两端固定。控制器知道从这个入口收到的请求都交给本地 SRAM，便可以省去在多个目标之间选路的逻辑。不过，要读 SRAM 内的哪个字，仍要看地址。控制器的输入队列满了，桥照样要等。直连省下了中间的选择与转发；线长、流水级数、队列深度和接收方的服务时间，仍会影响延迟。

固定 DSP 流水线能给出一个更小的例子。前一级产生一个采样值，后一级只需知道它何时有效，并在能接收时收下它。这条流可以完全没有内存地址。设前一级已经摆好数据，后一级在第 0、1 沿没有空位，到第 2 沿才给出就绪信号。这三个沿里只完成一次交付。AMD 的软判决纠错模块（SD-FEC）就用点到点的 AXI4-Stream 接口，发送与接收两方分别给出有效和就绪信号。[AMD PG256 的接口说明](https://docs.amd.com/r/en-US/pg256-sdfec-integrated-block/AXI4-Stream-Interface)

## 固定的一条返回线，能分清两笔读吗？

<span id="bus-适合共享事务语义"></span>
回到桥与 SRAM 的专线。桥先读 `0x4000_0120`，再读下一个字 `0x4000_0124`。一端只有一个目标，这能确定**谁发回数据**。要知道**答的是哪笔读**，还要看接口允许什么行为。

- **一次只允许一笔在途。** 第一个结果回来前不发第二笔。桥只需记住当前请求，收到的结果就属于它。
- **允许多笔在途，返回严格按序。** 桥依次记录两笔请求。第一份响应交给队首，移走队首后，再把下一份响应交给新的队首。
- **允许多笔在途，返回可以重排。** 如果第二个字能先回来，桥按队首取记录就会交错结果。接口要通过返回标识配合保存的上下文，或在交给桥前恢复顺序。AXI4 可以让不同读 ID 的独立读先后交换；同一读 ID 下还可以有多笔请求，它们的响应要按该 ID 的发出次序交付。[ID 与在途事务](../03-on-chip-protocol-families/axi-channel-id-outstanding.md)

因此，专线上也可以运行有地址、有响应的 AXI4。成功或错误的含义、响应顺序、桥在哪个沿收下结果，都来自接口契约。同样的契约也可以跨越片上网络，由两端的网络接口保存和恢复。[一次读取怎样变成 NoC 里的请求包和返回包？](../../NOC/05-system-integration/ni-network-interface-design.md)

## 什么时候需要把专线改成共享入口？

<span id="noc-适合大规模空间分布"></span><span id="选型要看三类约束"></span><span id="一句话理解"></span>
把 DMA 接回来，再允许调试器读这块 SRAM。如果三者共用控制器的一个读地址口，两个有效地址同时到达时，输入选择器只能接通一路。仲裁器决定先选谁，未获选的一方需要保留请求；返回路径还要知道结果属于哪个入口。若某个发起者还能访问别的外设，就要根据地址窗口把请求送到相应目标。由此可以分别数清系统新增了哪些资源，而无需把每一对模块都接上专线。

把这个判断用于 SoC 选型，可以先问三件事：谁要访问谁并可能同时到达？软件能观察到哪个完成或错误？扩展后，哪几条线、哪个选择器或哪组缓冲最贵？固定加速流水级之间可以保留局部专线。CPU 访问配置寄存器、门铃和中断控制器时，需要可寻址的寄存器和明确的读写行为。调试和启动还要考虑时钟、地址映射或主网络尚未就绪时能否到达目标；应答超时如何处理，则取决于系统另行约定的策略。

DMA 到 HBM 的长突发与 CPU 短请求共用端口时，要看仲裁粒度及在途窗口；多个计算 tile 同时交换激活值时，还要看各流是否重合在同一条链路或同一接收口。端点集中、规模较小时可以考虑局部交叉开关；端点分散时，集中式选择和长线布线的代价可能上升，多跳网络则要支付路由、缓冲、流控和逐跳等待的成本。同一组读请求在三种结构中的并行度和等待位置，放在同一篇逐项比较。[两笔读能同时通过吗？从共享总线、交叉开关到多跳 NoC](../../NOC/01-overview/bus-vs-noc-vs-crossbar.md)

## 板级 I/O 需要另看哪些边界？

<span id="和板级-io-互连的边界"></span>
主机从加速卡片内 SRAM 读一个字，卡内的专线、交叉开关或 NoC 只负责其中一段。主机怎样发现 PCIe 设备、怎样通过 BAR 窗口发起访问、完成包怎样回到主机，是卡外协议的责任。分析网卡、GPU 或 NVMe 控制器，还要按实际路径检查 DMA 地址映射；若涉及 CXL 的一致性访问，再按对应协议判断可见性。[一次跨桥读取](../../PCIE/06-workloads-case-studies/pcie-vs-axi-noc-boundary.md) · [PCIe 专题](../../PCIE/README.md)

## 建模启示

给固定专线先建一条有延迟、容量和回压的路径。加入未返回请求的记录，再由返回顺序决定使用一个槽、一条顺序队列，还是能按标识查找的表。若端点共享控制器，增加地址译码、仲裁、队列与握手，按接口要求记录突发拍数、权限、错误和完成。若要解释多跳网络的热点或某一拍的阻塞，则逐跳记录路由、缓冲、链路带宽和服务机会，按具体实现加入虚通道、信用和前进条件。仅统计 flit 已抵达的时刻，会漏掉最初那笔读在什么时候真正交给桥。[BUS 在解决什么问题](../01-overview/problem-statement.md) · [BUS 分类框架](../01-overview/taxonomy.md) · [片上网络专题](../../NOC/README.md)
