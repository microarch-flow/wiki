# 设计与调试检查表：把现象转换为可验证的问题

遇到旧数据、事务挂起或性能异常时，先固定访问路径和观察边界，再检查对应证据。不要从“这是缓存问题”直接跳到增加屏障或扩大缓冲。

## 先记录一条可复现路径

记录请求者、地址空间、目标范围、访问属性、读写类型和预期结果。保存初始缓存状态、事务 ID、关键消息及软件同步事件。跨 CXL 时，还要记录设备类型、链路模式、region 和 decoder 配置。

以下检查表适用于定位问题，不代替具体协议规范。

| 现象 | 核心问题 | 应取得的证据 |
| --- | --- | --- |
| 读到旧值 | 地址是否相同，副本是否有效，读写是否有规定顺序？ | 物理地址、缓存属性、owner 与同步关系 |
| 两处都能写 | 权限何时授予，失效何时真正完成？ | 授权、确认集合、本地流水线与探查竞争 |
| 脏数据丢失 | 最新值的责任在哪一步被删除？ | 写回缓冲、在途数据、接收确认 |
| 事务挂起 | 谁持有资源，谁等待资源？ | 队列占用、事务槽、信用和依赖图 |
| 大量重试 | 是资源拒绝、地址冲突还是传输错误？ | 重试类型、目标、信用与错误日志 |
| CXL 容量不可用 | 设备发现、区域配置、使用模式、上线到哪一步？ | Memdev、decoder、region、DAX 与内存块状态 |
| 带宽低 | 缺少并发，还是某个资源饱和？ | 在途数、平均时延、链路与设备利用率 |
| 移除失败 | 是否还有不可迁移或未退出的使用者？ | 固定页、应用映射、DMA 和内核下线错误 |

## 三个反例检查

**给所有访问都加屏障，旧值就一定消失吗？** 不一定。错误地址映射、不合法属性、非一致性路径缺少缓存维护，不能用普通顺序屏障一概修复。先分清顺序与副本维护。

**链路利用率很低，所以互连没有瓶颈吗？** 不一定。同一行串行化、Home 事务槽耗尽或请求并发不足，都可能让链路空闲而程序停顿。

**容量重新分配成功，所以旧主机不会再访问吗？** 不一定。管理面成功必须与旧映射撤销、访问排空及软件资源退出共同验证。只检查新主机能读，缺少隔离证据。

## 按问题选择阅读入口

- 权限与旧值：核对[A 取得写权限的时刻](../01-foundations/coherence-invariants.md#write-permission)和[B 再读时的数据来源](../01-foundations/coherence-invariants.md#read-again)。
- 消息交叉与挂起：读[瞬态状态](../02-protocols/transient-states-and-races.md)和[前进条件](../02-protocols/forward-progress.md)。
- CHI 接口：查[事务完成](../03-chi/chi-flow-control-retry-completion.md)，同时核对目标规范版本。
- CXL 接入：先查[地址路径](../04-cxl/cxl-type3-address-path.md)，再查[Linux 对象](../04-cxl/cxl-linux-regions-and-memory.md)。
- 测试结论：按[模型验证](modeling-and-validation.md)注明范围与未覆盖条件。

## 关闭问题需要什么

保留失败轨迹和最小配置，说明修复改变了哪项条件，再重跑原始反例和受影响的相邻场景。性能修复还要确认结果值、吞吐和尾延迟没有相互牺牲。未复现的问题可以记录观察和假设，但不要写成已经验证的根因。
