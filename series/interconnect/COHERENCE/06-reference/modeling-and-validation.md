# 一致性模型怎样验证：从可检查状态到竞争反例

先写“模型保证什么”，再决定需要哪些状态和测试。只统计平均延迟的流量模型，无法证明缓存一致性；拥有详细状态机，也不自动证明不会死锁。

## 定义最小可检查模型

一个教学模型可以包含两个请求者、一个 Home、两条缓存行，以及有限深度的消息队列。每条行记录权限、数据值、owner、sharers 和在途事务。给每次逻辑写入附加版本编号，有助于追踪新值在哪里。

输入是读、写、回收以及消息到达事件。控制器根据当前状态更新权限与责任，并输出数据、探查、确认或重试。事件调度应允许协议许可的不同到达顺序，不能总按最顺利的一种顺序发送响应。

## 断言要检查义务，不能只检查字母

| 性质 | 应检查的对象 | 容易漏掉的状态 |
| --- | --- | --- |
| 单写者 | 已生效的写权限与其他有效副本 | 授权在途、失效尚未确认 |
| 新值不丢失 | 缓存、写回缓冲、网络和内存的数据责任 | owner 已删除标签但写回未接收 |
| 读值正确 | 该模型允许的访问顺序与返回版本 | 并发读写时错误要求“绝对最新” |
| 事务匹配 | 地址、事务 ID、数据分拍与确认集合 | ID 回收后的迟到响应 |
| 前进 | 资源依赖、重试和公平性 | 队列永远满、某请求长期饥饿 |

“读必须等于最近发出的写”通常不是正确断言。要先规定操作何时在模型中生效，以及并发事件允许怎样排序。否则测试器可能把合法行为误报成错误。

## 一个小型穷举练习

采用[瞬态状态文章](../02-protocols/transient-states-and-races.md)的变体，四个输入事件分别为授权元数据、完整数据、B 确认、C 确认。允许它们以任意顺序到达，控制器先记录事实；只有授权有效、数据齐全、所需确认集合全部到齐时才允许写入。

四个不同事件共有 4!=24 种顺序。逐一检查每个前缀：前缀不足四项时不能错误授予写权限；全部到齐后应能前进。若“收到数据就转 M”，那么数据先到的顺序立即构成反例。

这个练习只验证一个完成条件，不包含真实协议的全部依赖、分拍、错误、重试和竞争。不能把 24 个顺序通过写成“MSI 已验证正确”。

## 定向测试比单纯增加随机次数更有目的

至少覆盖双写者竞争、脏 owner 遇到读取、回收与探查交叉、数据和确认乱序、事务 ID 复用、有限缓冲回压，以及重试信用先到。测试应给出初始状态和希望触发的冲突。

[gem5 的 SLICC 调试教程](https://www.gem5.org/documentation/learning_gem5/part3/MSIdebugging/)使用协议跟踪与随机测试查找错误。随机覆盖可以发现反例，但不能代替全状态证明。形式化探索同样受节点数、地址数、队列深度和公平性假设限制。

## 报告结果时写清范围

可复核的记录应包含模型版本、状态与消息定义、调度约束、断言、测试配置、随机种子或反例轨迹、通过条件与未覆盖功能。功能检查通过后再分析时延；抽象事件步数不能未经校准就标成硬件纳秒。
