# 内存错误、复位与容量移除：数据何时仍然可用？

一致性描述正常访问如何协调，可靠性还要回答损坏、失联和撤销资源以后怎么办。链路能够重试，不意味着设备内存中的错误可以恢复。

## 四类事件要分开

| 事件 | 主要处理对象 | 不应推导出的保证 |
| --- | --- | --- |
| 链路传输错误 | 编码、校验、纠错或重试机制 | 内存介质数据一定正确 |
| 介质或内部数据错误 | ECC、错误报告、隔离与恢复 | 任意多位错误都可纠正 |
| Poison 标记 | 标识不可当作正常数据使用的内容 | 已经修复原数据 |
| 设备复位或失联 | 访问终止、资源状态与恢复 | 原映射可以继续透明使用 |

具体纠错能力取决于实现。Poison 将“有数据返回”和“数据可信”分开；清除标记也不能凭空恢复原来的用户数据。系统需要结合错误范围、访问者和恢复副本决定后续处理。Linux 的一般内存错误处理见 [hwpoison 文档](https://docs.kernel.org/mm/hwpoison.html)。

## 内存类型与持久化边界

CXL 设备可以提供易失或持久容量。协议连接方式不改变介质的基本持久性，也不能保证所有缓存、队列和控制器都在断电保护域内。

若需要故障后保留数据，必须说明哪些组件属于持久化域、怎样推动缓存中的修改进入该域、怎样确认顺序和完成。普通 store 完成、收到一致性确认、事务写入内存控制器，都不能脱离平台定义直接等同于持久化完成。

## 移除正在使用的容量会发生什么

构造例子：A 主机把某 CXL 区域上线为 System RAM，页分配器把其中页面分给应用。管理器准备把容量转交给 B。仅让 B 获得新映射仍不够，A 的页表、CPU 缓存、设备 DMA 和固定页面都可能继续引用旧区域。

安全的退出过程需要停止新使用、撤销或迁移旧使用、完成必要的缓存和访问排空、确认内核下线，再按平台流程解除映射与分配。具体顺序由硬件和软件接口共同约束，不能把这个概念列表当成通用拔卡脚本。

Linux 下线可能因不可迁移或被固定的页失败。失败时不能假装容量已经释放。[Linux 6.16 Memory Hot(Un)Plug](https://docs.kernel.org/6.16/admin-guide/mm/memory-hotplug.html)区分内存下线和移除阶段，并解释可移动性限制。

## 故障后的“最新值”可能已经不存在

若某缓存持有唯一脏副本，而节点失效并丢失该副本，正常协议中可追踪的最新值不一定还能恢复。硬件一致性不能替代复制、日志或应用恢复协议。多主机共享还要明确故障隔离范围，避免一个失效参与者使其他主机永久等待。

验证应覆盖正常移除与意外失联，分别检查内核事件、受影响地址、应用行为、残留映射和资源重新分配。故障注入只适合受控测试配置；本页不提供会改变现有内存内容的注入命令。
