# CXL.cache 与设备内存：两个方向的一致性

CXL.cache 的名字容易造成误解：它不是“CPU 访问 CXL 内存时必须使用的缓存协议”。先区分内存归属，再看谁缓存谁的数据。

## 两条基本路径

| 路径 | 谁保存可复用副本 | 关键子协议 |
| --- | --- | --- |
| 设备访问并缓存主机内存 | 设备缓存主机数据 | CXL.cache |
| 主机访问并缓存设备内存 | 主机缓存设备数据 | CXL.mem |

Type 1 支持 CXL.io 与 CXL.cache；Type 2 支持三类子协议；Type 3 支持 CXL.io 与 CXL.mem。Type 3 不实现 CXL.cache，并不意味着 CPU 必须以不可缓存方式访问其内存。[Linux 设备类型说明](https://docs.kernel.org/driver-api/cxl/devices/device-types.html)可用于核对这些基本方向。

## 设备缓存主机内存时，设备承担什么责任

构造一个加速器读取主机数组的例子。若设备按协议获得并缓存该行，后续 CPU 或其他参与者申请冲突权限时，系统必须能够处理设备副本。设备不能把“我已经读过”当作永久读取权，也不能在应交出脏数据时只返回一个空确认。

因此，设备上的缓存不只是性能优化，还引入协议状态、探查响应和数据责任。算法结束不代表所有脏数据已经回到主机内存，仍需依照设备与软件接口定义完成和同步。

## 设备内存也可能有多个访问者

对简单 Type 3 扩展内存，主机负责自身缓存域内的副本协调。对 Type 2 加速器内存，设备计算单元也可能访问数据，需要更完整的主机与设备协调。不能把设备内存控制器当作一个永远只服务主机的被动 DRAM 接口。

CXL 3.0 的 HDM-DB 路径引入通过 CXL.mem 发起的 Back-Invalidate Snoop。它让设备侧能够请求处理主机缓存副本；相关语义还支持更复杂的共享访问。它不要求把这条探查改称 CXL.cache，也不能推广到所有早期 Type 3 配置。[CXL 3.0 规范第 2.2.1、3.5.1 节](https://computeexpresslink.org/wp-content/uploads/2024/02/CXL-3.0-Specification.pdf)定义了该机制。

## 有一致性，仍需定义数据交接

设 CPU 更新任务描述符，然后通知设备。即使数据路径一致，通知之前仍需遵守平台要求的发布顺序；设备完成以后，CPU 也需按接口规定观察完成。缓存一致性不能决定“任务已经完成”这个应用事件。

共享内存中的锁、原子操作、访问权限、异常处理和对象生命周期，也必须在目标主机与设备组合中成立。特别是跨主机共享，不能仅凭可访问同一设备地址就推导出完整的软件共享内存模型。下一篇区分[池化与共享](cxl-pooling-sharing-fabric.md)。
