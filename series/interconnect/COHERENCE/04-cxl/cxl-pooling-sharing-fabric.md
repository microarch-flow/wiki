# 内存扩展、池化与共享：容量怎样分配，数据怎样协调？

扩展增加可用容量；池化管理容量归属；共享允许多个参与者访问同一数据区域。这三个目标可以组合，但不能只用“共享内存池”一个名称概括。

## 先看分配关系

构造一个设备含两个等大区域 P、Q 的例子。

| 模式 | 主机 A | 主机 B | 需要解决的问题 |
| --- | --- | --- | --- |
| 单主机扩展 | 使用 P、Q | 不使用 | 地址映射、容量接入 |
| 池化分配 | 使用 P | 使用 Q | 容量归属、隔离、重新分配 |
| 同一区域共享 | 使用 P | 也使用 P | 副本协调、同步、权限与故障处理 |

P 从 A 转交给 B，与 A、B 同时缓存 P，是不同操作。重新分配前必须处理旧映射和旧访问者，不能只改交换机的一张路由表。

## 版本能力需要逐项看

| 版本 | 与本页相关的能力 | 阅读边界 |
| --- | --- | --- |
| CXL 1.x | 主机与设备的基本访问关系 | 不能据此假设交换池化 |
| CXL 2.0 | 单级交换、内存池化与逻辑设备分配 | 池化不等于多个主机同时共享同一位置 |
| CXL 3.0 | 多级交换、fabric、增强共享与一致性、动态容量 | 需要相应设备、拓扑和软件能力 |
| CXL 3.1 / 3.2 | 对 fabric、管理、安全等能力继续扩展 | 应按具体功能查规范，不能只看版本号 |
| CXL 4.0 | 更高速率、端口聚合及 RAS 增强 | 不意味着任意 Type 3 设备都能聚合端口 |

前两代差异见 [CXL 2.0 池化问答](https://computeexpresslink.org/blog/cxl-2-0-specification-memory-pooling-questions-from-the-webinar-part-2-2391/)与 [CXL 3.0 白皮书](https://computeexpresslink.org/wp-content/uploads/2023/12/CXL_3.0_white-paper_FINAL-1.pdf)。4.0 的端口聚合有设备类型和模式限制，见[官方 4.0 问答](https://computeexpresslink.org/blog/introducing-the-cxl-4-0-specification-webinar-qa-recap-4386/)。这张表描述规范能力，不是已安装设备或当前 Linux 的支持清单。

## 管理面不承载每一次 load

Fabric Manager 等管理实体负责发现、配置、分配和撤销资源。配置生效以后，普通内存访问沿硬件数据路径执行。不能把管理器画成每个 CPU load 都必须调用一次的软件代理。

动态容量也不意味着应用地址空间会自行增长。设备报告变化、平台映射、内核接入、内存上线及应用分配，是不同阶段。每一阶段都需要失败处理，缩容还要证明旧使用者已经退出。

## 硬件共享不是软件同步

即使选定配置支持多主机缓存一致共享，应用仍需决定谁更新对象、如何发布、怎样使用受支持的原子与同步机制，以及一个主机失败后如何恢复数据。硬件保证的作用域和故障边界要与软件假设一致。

容量池可以提高资源分配灵活性，却不保证每个应用更快。更多交换跳数、共享链路和远端数据访问可能增加代价。地址路径见[Type 3 地址映射](cxl-type3-address-path.md)，系统层数据放置见[存储集成专题](../../../storage/06-system-integration/future-packaging-cxl-near-memory.md)。
