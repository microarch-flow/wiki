# 瞬态状态与并发竞争：收到数据以后，还在等什么？

稳定状态描述事务结束后可使用的权限。瞬态状态描述尚未完成的义务，例如等待数据、等待失效确认、等待写回被接收。只画 MSI 的三个圆圈，无法决定这些时刻能否接受新事件。

## 数据和确认不保证同时到达

构造一个允许数据直接返回请求者的 GetM 变体。A 起初为 I；B、C 为共享者。H 给 A 的授权元数据说明需要收回 B、C 的权限，数据和确认经过不同路径返回。

| 到达事件 | A 已有数据？ | 尚欠确认 | A 可以写入？ |
| --- | --- | --- | --- |
| 收到授权元数据 | 否 | B、C | 否 |
| 收到数据 | 是 | B、C | 否 |
| 收到 B 的确认 | 是 | C | 否 |
| 收到 C 的确认 | 是 | 无 | 是，且其他授权条件已满足 |

若确认先于数据到达，控制器应保存确认结果，再等数据。不能因为当前还不知道期望确认数，就丢弃早到响应。可用事务 ID、已收到集合、期望集合和有效位处理；集合未确定前不判断完成。

[gem5 MSI 状态机](https://www.gem5.org/documentation/learning_gem5/part3/cache-declarations/)用不同瞬态区分等待数据与确认的情况。表中的消息组织是本文构造变体，不能直接当成该实现的逐拍轨迹。

## 两个写者同时请求

A 和 B 都想写同一行。H 必须建立冲突事务的处理顺序，不能各自看到“对方暂时没有 M”就同时授权。

一种保守模型让后到请求排队，直到先到事务收到接收端完成通知。允许流水重叠的实现则需要额外状态，处理后续探查与先前数据返回交错的情况。两种实现的吞吐不同，但都必须维护单写者约束。

## 写回和探查交叉

A 正在回收脏行，写回消息已经发出，但 H 还没有接收完成。此时探查抵达 A。若 A 只查标签并回答“我没有数据”，而 H 又认为 A 仍是 owner，就可能丢失新值或形成循环等待。

控制器需要把写回缓冲也纳入责任跟踪。可选做法包括从写回缓冲供数，或由 H 识别并合并相交事务。具体选择取决于协议；“已发出写回”不是可以删除唯一数据的充分条件。

## 用事件表检查控制器

每个瞬态至少要回答四个问题：收到新 CPU 请求怎么办；收到探查怎么办；收到数据或确认怎么办；资源不足时由谁持有数据和重试责任。无法立即处理的事件可以排队或重试，但必须说明最终由什么事件解除等待。

完成条件应是明确的谓词，例如“授权有效 ∧ 数据齐全 ∧ 欠缺确认集合为空”，而不是“最后一个预想消息到了”。还要验证重复消息、错误事务 ID 和回收后的迟到响应不会被误认成新事务。前进条件见[下一篇](forward-progress.md)。
