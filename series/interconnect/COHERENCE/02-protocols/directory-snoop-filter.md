# 目录、Home 与 Snoop Filter：谁知道缓存行在哪里？

协议需要找到可能持有副本的节点，并协调冲突访问。广播探查、目录和探查过滤器是解决这个问题的不同组织方式，可以在同一系统中组合使用。

## 先分清四个角色

| 名称 | 职责 | 不必具备的性质 |
| --- | --- | --- |
| Home | 协调某地址的事务及相关顺序 | 不一定保存该行数据 |
| Directory | 记录副本、owner 或协议状态 | 不一定与 LLC 数据阵列绑定 |
| Owner | 承担协议定义的数据或权限责任 | 不一定是 Home，也不总有写权限 |
| Snoop Filter | 排除不可能持有副本的探查目标 | 不一定包含完整精确目录 |

广播方案让多个缓存检查标签，优点是无需先精确记录所有共享者；代价是无关节点也接收探查。目录方案先查元数据，再向相关节点发消息；代价是元数据容量、访问延迟和维护流量。

## 精确目录的容量估算

构造模型：每条被跟踪缓存行有 N 个共享者位。跟踪容量为 C 字节，缓存行大小为 L 字节，暂时忽略标签、状态、owner、ECC 和空项。

**共享者位图容量 = (C ÷ L) × N bit。**

取 C=1 GiB、L=64 B、N=64，得到 2²⁴ 个目录项，每项 64 bit，共 128 MiB 位图。这是模型算术，不是某产品的目录容量。它说明按节点数线性增加位图可能很贵，实际设计可采用有限指针、分层、稀疏或压缩表示。

减少元数据不免费。有限指针溢出后可能改为广播；分层需要多级查询；替换一条仍代表有效副本的目录项，可能需要先回收相关副本。

## 过滤器能否“猜错”

若过滤器把一个实际上没有副本的节点列入目标，会产生多余探查。只要响应处理正确，这类保守误判通常影响性能。

若过滤器漏掉真实持有者，且系统直接据此授予冲突权限，就会破坏正确性。允许信息丢失的实现必须有配套措施，例如在遗忘前失效相关副本，或退回覆盖全部潜在持有者的探查；不能简单声称“过滤器只是优化，漏了也无所谓”。

## Home 热点不一定是链路热点

地址映射可能把多个热行分配到同一个 Home。即使网络总带宽充足，目录端口、事务表或同一行串行化也可能成为瓶颈。改变哈希能分散不同地址的压力，却不能让多个写者同时获得同一行的独占权限。

[gem5 的目录实现教程](https://www.gem5.org/documentation/learning_gem5/part3/directory/)可用于检查 owner、sharers 和目录状态怎样配合。它是具体教学实现，不是对所有目录的硬件规定。接着读[瞬态状态与并发竞争](transient-states-and-races.md)，检查这些记录如何在消息途中保持有效。
