# NoC 在解决什么问题？

上级：[01 认识 NoC](../SUMMARY.md#01-overview)；原章节：[01 认识 NoC](./README.md)

相关：[共享总线、Crossbar 与 NoC：怎样比较？](./bus-vs-noc-vs-crossbar.md)、[NoC 的设计维度与工作负载](./taxonomy.md)

<span id="problem-statement"></span><span id="这页在回答什么问题"></span>多个计算、存储和控制模块需要同时交换数据。片上网络（Network-on-Chip，NoC）把连接、转发和共享资源组织成一个通信系统，使设计者能够分析数据经过哪里、在哪里等待，以及目的端能否及时接收。

NoC 是一种组织通信的候选方案。是否采用它，要比较工作负载、端点位置、时序、面积和功耗；端点数量本身没有通用的选型门槛。

## 片上通信为什么需要管理

<span id="从共享互连到分布式网络问题是一步步长出来的"></span>一个处理器、DMA 引擎或计算 tile 都可以是通信端点。端点访问本地存储时，可以使用专用连接；多个端点共享一个存储端口时，就需要确定谁先使用它。端点分布到芯片各处后，还要考虑长线、共享路径和多个目的端。

片上互连的设计需要同时回答几个问题：

- **连接**：哪些端点可以相互通信？数据经过哪些共享资源？
- **服务**：一个请求何时被接受？多个请求竞争时谁先前进？
- **交付**：目的端能否接收数据？请求何时算完成？
- **实现**：线长、缓冲、仲裁和时钟约束需要多少成本？

共享总线、crossbar 和由交换节点构成的网络都能解决其中一部分问题。它们的取舍见[互连比较](./bus-vs-noc-vs-crossbar.md)。

## 一次请求要经过什么

下面以**分包网络**为例。网络接口（Network Interface，NI）也可以集成在端点中，不一定是独立模块。

> **请求路径：** 发送端 → 注入接口 → 交换节点与链路 → 接收接口 → 目的端。

发送端先产生请求。注入接口根据目标和实现规则形成网络消息，并等待注入资源。交换节点为消息选择输出并处理竞争；消息可能经过一个或多个节点。接收接口交付给目的端。如果上层事务需要响应，响应还要按该实现的规则返回并与请求匹配。

<span id="noc-要解决的不是能不能通而是通得是否可持续"></span>请求到达网络出口，不一定等于目的端已经消费，更不一定等于软件已经观察到事务完成。这些完成边界要分别定义。AMD Versal 的一个具体实现中，网络接口会将 AXI 读请求封包，在目的侧恢复请求，再将读响应送回；这是该产品的实现例子，不代表所有 NoC 都采用同一流程。[AMD PG313：Read Transactions](https://docs.amd.com/r/en-US/pg313-network-on-chip/Read-Transactions?contentId=m1XdimEA6OVj8nzhHnt8qw)

## 两个发送方遇到一个慢目的端

<span id="ai-系统里真正关心的是哪几条路径会先塌"></span>假设 A 和 B 各有每拍一个传输单元的发送需求，全部发往 X。X 的接收端口每拍最多消费一个单元。这里的“传输单元”只是计数单位，可以是某个模型中的一个 flit。

在连续 T 拍内，A 和 B 合计提出 2×T 个单元的发送需求，而 X 最多消费 T 个。即使网络内部没有其他瓶颈，差额也不能由 X 在这段时间内完成消费。如果流量持续、缓冲有限且系统不丢弃数据，队列最终会填满，反压使某些上游发送暂停。

这个结果来自**目的端的服务能力**，不是由 mesh 或 crossbar 的名称决定的。拓扑、路由和仲裁仍会影响等待发生的位置以及两个发送方分别等待多久。要判断计算是否断供，还需要看发送方、接收方与计算任务之间的依赖。

## 什么时候考虑分布式网络

<span id="为什么不是把-bus-做宽一点或把-crossbar-做大一点"></span>加宽共享通道可以提高该通道的传输能力；增加 crossbar 端口可以提供更多连接。它们都值得作为候选，但共享端口、仲裁、布线和时序仍要分别核算。分布式网络将部分转发和仲裁放在多个节点，也引入链路、缓冲、路径管理及验证成本。

网络可以让不冲突的流使用不同资源，也可能在共享链路、目的端口或存储控制器处遇到热点。逻辑 hop 少不一定意味着物理线短或端到端延迟低；比较必须包括实际布局和时钟。早期 NoC 研究将规律化的片上布线和资源共享作为设计动机，但其示例参数不能直接当作今天芯片的成本数据。[Dally 与 Towles，2001](https://doi.org/10.1145/378239.379048)

<span id="常见误解"></span>因此，“峰值链路带宽足够”不能单独证明系统不会堵塞；“采用 NoC”也不能单独证明系统更快或延迟有上界。

## 从系统问题开始建模

<span id="建模启示"></span>若目标是估算容量上界，先记录端点、源与目的、数据量、路径和各共享资源的服务能力。这个层次可以暂不表示每个 flit，但不能据此声称已算出排队延迟或反压传播时间。

若要分析等待和反压，再加入需要观察的队列、仲裁、流控与端点消费过程。若要证明完成时间上界，还要给出流量约束、服务和公平性等条件。指标的计量边界见[延迟、吞吐与饱和](../07-evaluation-methodology/metrics-latency-throughput-saturation.md)。

<span id="一句话理解"></span>NoC 把片上通信的路径与共享资源显式组织起来；它的价值和代价必须在具体系统与流量下判断。
