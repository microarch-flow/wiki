# 两笔读能同时通过吗？从共享总线、交叉开关到多跳 NoC

上级：[01 认识 NoC](../SUMMARY.md#01-overview) · 原章节：[01 认识 NoC](./README.md)

<span id="共享总线crossbar-与-noc怎样比较"></span><span id="bus-vs-noc-vs-crossbar"></span><span id="这页在回答什么问题"></span>
桥要读 `0x4000_0120`，取回 SRAM 中的 42。[上一篇](../05-system-integration/ni-network-interface-design.md)跟着这个请求走了一个来回。现在卡内的 DMA 也准备好一笔读。两个发起端各有自己的接口，两笔请求能不能在同一拍通过？

先让桥读第一块 SRAM，DMA 读第二块。然后只改 DMA 地址的高位，把它指向第一块 SRAM 的另一个字。两个发起端始终没有读写冲突。拿这两组流量分别经过三种连接结构，等待会出现在不同的地方。

## “同时通过”要站在哪里看？

<span id="先分清三个问题"></span><span id="先讲结论它们不是同一条坐标轴上的三档性能"></span><span id="bus交易语义优先"></span>
在桥旁和 DMA 旁各放一个有空位的队列，即使后面只有一条共享通道，两个队列也可能**同拍接下**各自的请求。它们稍后只能一个接一个地使用共享通道。如果此时只数入口握手，就会以为互连每拍能送两笔，直到队列填满才发现目标从来没那么快。

所以把计数器放在**目标的读请求入口**。一个目标实际收下一笔地址，就在那一拍加一；有两个目标时把两边的接收数相加。一次孤立读取能告诉我们它走了多久。要知道这套结构能持续送多少，就让两个源都不断有新请求，等路径填起来，再数固定的一段时间。

在下面的教学模型里，称桥为 **A**、DMA 为 **B**，两块 SRAM 的目标端口分别为 **X** 和 **Y**。X 对应 `0x4000_0000` 窗口，Y 对应 `0x5000_0000` 窗口。桥始终向 X 读偏移 `0x120`。DMA 先读 `0x5000_0124`，再改成 `0x4000_0124`；偏移和大小都没变，变的是目的端。

每笔都是独立、对齐的 4 字节读，去程请求抽象为一个传输单元，在网格里就是一个请求 flit。三种结构用同一时钟，各源最多每拍提出一笔，每个目标最多每拍接一笔。假设有足够的在途空间、下游一直愿意接收，返回路径另有容量。本文数的是**去程地址请求**；要回答“桥何时用上 42”，还得加上目标服务和数据回程。[回看读地址与读数据的两个握手](../../BUS/02-fundamentals/transaction-address-data-response.md) · [NoC 需要管理哪些资源？](./problem-statement.md)

## 先让两笔读去不同的 SRAM

<span id="用同一组流量比较"></span>
**共享总线。** 把两个源接到同一组请求线上，再由地址译码决定哪个目标接收。假设某拍轮到 A，线上的地址就是 `0x4000_0120`，X 收下它。Y 即便空着，也不能让同一组线在这拍再表示 B 的另一个地址。下一拍轮到 B，Y 才能收到请求。两边持续提出请求时，公用通道每拍能送一笔；若两边等权轮流用，每两拍各送一笔。

<span id="crossbar用面积换单跳和并发"></span>
**交叉开关（crossbar）。** 现在为 X 和 Y 的每个输出各放一个选择器，让每个选择器都能从输入中挑一路。X 可以选 A，与此同时 Y 可以选 B：两个选择器取的是不同的输入，驱动的也是不同的输出。这一拍，X 和 Y 各收一笔。原例是全连接的 4 输入 × 4 输出交叉开关，另外两路输入、输出空闲。这里还假定请求通路有独立的输出仲裁，没有前置的共享地址通道。单看产品名里的 *crossbar* 无法判断这一点，例如 AMD 的一种 AXI Interconnect 配置采用共享地址仲裁和多条数据通路。[AMD PG059 对地址和数据通路的说明](https://docs.amd.com/r/en-US/pg059-axi-interconnect/N-to-M-Interconnect-Crossbar-Mode)

<span id="noc承认通信是分布式资源问题"></span>
**多跳网格（mesh）。** 把四个路由器排成方格，上排从左到右接 A、B，下排接 X、Y。相邻路由器之间双向相连，每个方向各能每拍传一个单元。本例先走到目标所在的行，再沿该行走到目标所在的列。A→X 走左边向下的链路，B→Y 走右边向下的链路。请求到了目标路由器，再从本地出口交给 SRAM 控制器。两条路线直到交付都没有争用同一项资源，所以第一对请求抵达以后，可以持续每拍交付两笔。沿途的流水级决定第一对何时到达。

## 只把 DMA 的目的端改成 X

A 仍然读 X，B 也改读 X。共享总线仍每拍只能给出一个地址。交叉开关这次遇到了新限制：X 的输出选择器同时看到 A 和 B，而它只有一组输出线。若这一拍选 A，B 就得等下一次机会。Y 的选择器即便闲着，也没有通向 X 的第二个接收口。

网格的情况稍容易看错。A 仍走 A→X；B 按同样的路由规则先走 B→Y，再走 Y→X。**两条请求没有共用任何一条有向链路，却都要从 X 路由器的同一个本地出口交给控制器。** 来自上方和右方的请求可以同时到达 X 路由器的两个输入缓冲；目标端这一拍仍然只能接一笔。图中的 Y 在此只是 B 的途经节点，Y 的 SRAM 不会接下这笔地址。

## 第一对请求恰好没撞上，瓶颈在哪里？

只看两笔孤立请求，可能看不出排队。A 到 X 只有一跳，B 绕经 Y 要两跳。如果 A 先到先走，等 B 到了，出口又空了。现在让每个源在时隙 0、1 各发一笔，按发送顺序记为 A0、A1 和 B0、B1，四笔都读 X。用这段最短的连续流量，看队列第一次在哪里出现。

仍按前面的网格选路。假设开始时网络为空，在一个时隙内可以走一段链路；到达的请求从**下一个**时隙起才能继续。X 路由器经本地口向控制器交付也占一个时隙。X 为两路输入各留有缓冲，两路都在等时轮询；某路独自用过出口后，下次两路同时有请求，另一边优先。表格记录在各时隙内实际发生的事。

<div class="bus-read-trace" markdown="1">

| 时隙 | 链路上正在走什么 | X 经本地口交给控制器 |
| ---: | --- | --- |
| 0 | A0：A→X；B0：B→Y | 空，时隙开始时输入缓冲为空 |
| 1 | A1：A→X；B1：B→Y；B0：Y→X | A0 |
| 2 | B1：Y→X | B0；A1 已到，留在输入缓冲 |
| 3 | 无 | A1；B1 已到，继续等 |
| 4 | 无 | B1 |

</div>

时隙 1 最值得细看。三条不同方向的链路各搬了一个请求单元，但只有 **A0 这一笔**交给了 X 的控制器。把链路上的三次移动算成三笔交付，会重复计算途中经过多跳的请求。到时隙 3，链路甚至全空了，X 门口却仍有两笔合格请求。若把 B 的目标改回 Y，A0、B0 会在时隙 1 分别交给 X、Y，A1、B1 在时隙 2 同样一起交付。这样，第一笔仍在时隙 1 到，四笔全部交付的时刻却从时隙 4 提前到了时隙 2。

换一张更大的网格，同样值得反过来检查：目标不同，就一定能每拍送两笔吗？设两条流分别去右半边不同的 SRAM，但它们的既定路线都必须经过同一条向东的链路。只要这条链路每拍只能过一个请求，两条流的**合计**就至多一笔/拍，哪怕两个目标各有空位。找瓶颈时需要逐段标出每条流的方向和每个端口的服务能力。[拓扑指标与带宽](../03-topology/topology-design-metrics.md) · [网格中的维序路由](../04-routing-and-flow-control/dimension-order-routing.md)

## 既然都能做到两笔一拍，为什么还要区分结构？

<span id="连接规模和物理成本"></span><span id="三者的边界放到-ai-芯片里最清楚"></span><span id="不要把-crossbar-和-noc-看成是否分层的道德判断"></span>
假设在 X、Y 旁边再各加一个端点。全连接交叉开关若有 N 个输入、M 个输出，就要允许 N×M 种输入到输出的连接。4×4 有 16 种连接可能，并不意味着每拍能传 16 笔：每个端口每拍只收发一个单元，即使四个输入去四个不同的输出，最多也只有四对同时工作。增加端口，会增加选择器的输入、仲裁请求和需要跨越芯片的布线。位宽、位置、时钟目标和流水切分都会改变代价，不能拿 16 直接换算硅面积。

网格把选择分散到相邻路由器，可以更多地用局部连接，但一笔远距离请求会占用多段链路，还可能在每一跳等缓冲或出口。集中在一小片区域的端点可能适合局部交叉开关；相距较远的几个计算簇可以在簇间用多跳网络。规模很小、很少同时发请求的一组控制寄存器，单一共享通道也可能足够。控制、启动和调试路径是否另设通路，还取决于主网络尚未初始化时哪些端点必须可达。[固定专线与共享事务的工程边界](../../BUS/02-fundamentals/bus-vs-noc-vs-point-to-point.md) · [交叉开关与集中式网格](../03-topology/crossbar-and-concentrated-mesh.md)

<span id="常见误解"></span>
在这三种方案里，桥仍然可以通过 AXI4 发读地址、等待相应 ID 的读返回。**端点怎么交接**与**去程经过哪些资源**是两个层面。交叉开关甚至可以装在网格路由器里面，负责从几个输入中为每个输出选一路，选完才把包送上下一段链路。AMD Versal 就把边缘的 AXI 转换和内部的 NoC 包交换节点分开描述，其 NPS 使用交叉开关。算例中的交付率来自前面给出的结构与流量；实际产品的吞吐和延迟还要按它自己的仲裁、内部流水与时钟计算。[Arm AXI4 规范 IHI 0022H](https://developer.arm.com/-/media/Arm%20Developer%20Community/PDF/IHI0022H_amba_axi_protocol_spec.pdf) · [AMD UG909 的 NPS 结构](https://docs.amd.com/r/2024.1-English/ug909-vivado-partial-reconfiguration/Network-on-Chip) · [AMD PG313 的读请求路径](https://docs.amd.com/r/en-US/pg313-network-on-chip/Read-Transactions)

## 建模启示

<span id="比较时依次确定什么"></span><span id="一个实用的选择顺序"></span><span id="一句话理解"></span>
拿到一个写着“2 笔/拍”的规格时，先问它在哪一处计数。复现上面两张表，可以给每条流列出它实际占用的资源：共享段、交叉开关输入和输出、网格有向链路、目的端本地口。逐项检查所有经过它的流加起来是否超过其容量。这个检查能给出吞吐上界；能否达到上界，还要看路由、仲裁和缓冲能否给出像时隙表那样可执行的安排。

需要计算某笔读的延迟时，再为每一跳加入流水时间、队列深度、下游是否就绪和仲裁状态，单独记录“请求注入、目标收下、数据返回、发起者接走”。即便两个方案的目标接收率相同，第一笔延迟、最后一笔等待和物理实现的时钟频率都可能不同。还想追到路由器内部哪一拍挑输出、哪一拍过交换开关，可以接着读[路由器流水线](../02-router-microarchitecture/router-pipeline-stages.md)或对照 [gem5 Garnet 的周期模型](https://www.gem5.org/documentation/general_docs/ruby/garnet-2/)。

桥发出的片内地址还有一个上游来源。刚上电时，主机甚至还不知道这张卡在哪个总线上，它后来怎样给卡分到一个能读的地址？下一篇沿着同一张加速卡追到主机一侧。[《主机第一次读卡上的寄存器，地址是怎么来的？》](../../PCIE/03-configuration-enumeration-addressing/config-space-bar-capability.md)
