# 事务拆分、顺序与完成：网络怎样保持接口语义？

上级：[05 端点与系统集成](../SUMMARY.md#05-system-integration)；原章节：[05 端点与系统集成](./README.md)

相关：[网络接口 NI](./ni-network-interface-design.md)、[地址映射与路由表](./address-map-and-routing-table.md)、[死锁、活锁与饥饿](../04-routing-and-flow-control/deadlock-livelock-starvation.md)

一次端点事务可能变成多个网络消息，也可能与其他事务同时在途。网络把消息送到目的地后，端点仍要匹配数据、维持接口要求的顺序并处理状态。**包到达、事务响应和软件看到完成是不同事件。**

## 一次跨端口读取

下面是构造例：内存区域以 64 B 为单位交替映射到四个端口，地址从 0 开始。发起者提交读取 T0：地址 32 B、长度 96 B；接口和目的端都允许此读取拆分。假设每拍的接口传输单位为 32 B，且事务不跨越该接口的其他边界。

| 片段 → 端口 | 地址范围 | 数据偏移 |
| --- | --- | --- |
| F0 → 0 | 32–63 B | 0 B |
| F1 → 1 | 64–127 B | 32 B |

地址范围包含两端，F0 为 32 B，F1 为 64 B。

源端为 T0 分配内部状态，记录原接口 ID、两个片段的范围和状态。若 F1 先返回，接收逻辑可以暂存它；F0 到达后，再按上层接口要求交付数据和状态。若接口允许逐段交付，实现也可以在满足顺序和错误规则时提前交付，而不必等待所有片段。

## ID 不一定是唯一事务号

假设上面的接口是 AXI4，同一个发起端先后发出读事务 T0 和 T1，二者的读 ID 都是 7，且都允许在途。NI 可以分别分配内部 tag 51、52，并在 ID 7 的队列里记录 T0 在 T1 之前。即使 T1 的数据先在内部到达，也必须按 AXI4 的同读 ID 响应顺序向该发起端返回。

因此，`(source, ID)` 本身不一定唯一标识一笔在途事务；还需要内部 tag、序号或队列位置。不同读 ID 在规则允许时可以不同顺序返回；读 ID 与写 ID 数值相同也不自动建立读写之间的顺序。[Arm AXI4 规范，Issue H](https://developer.arm.com/-/media/Arm%20Developer%20Community/PDF/IHI0022H_amba_axi_protocol_spec.pdf)

这些规则属于所选接口，而不是所有 NoC 的通用顺序。片段是否允许拆分、如何传递字节使能、属性和错误，也必须按目标协议与实现确定；不能把普通内存读取的拆分套用到任意 MMIO 或原子访问。

## 缓冲和前进条件

乱序返回需要可用的接收状态。设计可以在接纳请求前预留所需空间，也可以使用其他已验证的流控方案。关键是：不能接收超过自身契约能处理的返回，也不能形成请求占着资源等待响应、响应又无法取得资源的循环。

例如 AMD Versal NMU 使用读重排缓冲，并在接收读请求时按该实现的规则预留空间。[AMD Read Reorder Buffer](https://docs.amd.com/r/en-US/pg313-network-on-chip/Read-Reorder-Buffer) 中的容量和释放细节是产品特定的。仅有 credit 或路由依赖无环，不足以证明端点协议也能前进；[第四章的端点等待例](../04-routing-and-flow-control/deadlock-livelock-starvation.md#协议和端点也可能形成等待环)说明了原因。

## 哪个事件表示完成

| 事件 | 它说明什么 |
| --- | --- |
| 消息到达 NI | 网络已把该消息交给接收边界。 |
| 接口响应被接纳 | 事务在该接口达到协议规定的响应边界。 |
| 设备报告 completion | 达到设备文档规定的任务完成条件。 |
| 软件读取结果 | 还需满足该平台的所有权、顺序和可见性规则。 |

这些事件未必一一对应。比如，某些允许缓冲的 AXI 写响应可以由中间组件给出；该组件仍需遵守后续传播与可观察性规则。响应不能被笼统解释为数据已经写入 DRAM，或 CPU 缓存已经看到结果。

错误、超时和复位同样需要契约：哪些片段已执行，如何向上回报，何时释放 tag，以及迟到响应是否还可能出现。超时本身不证明请求已被取消；在途状态未处理完时复用标识可能错配新旧事务。
