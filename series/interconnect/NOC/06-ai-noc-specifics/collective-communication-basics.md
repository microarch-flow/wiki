# 集体通信基础：参与者交换什么，何时完成？

上级：[06 多端通信与调度](../SUMMARY.md#06-ai-noc-specifics)

相关：[广播、多播与复制](./broadcast-multicast-tree.md)、[归约与 AllReduce](./reduction-and-collective-networks.md)、[All-to-All 与通信矩阵](./all-to-all-and-traffic-matrix.md)

一次集体通信涉及一组参与者。要理解它，先回答三个问题：**谁提供数据，谁得到什么结果，以及哪个事件表示完成。**这些是通信语义；它们并不规定数据必须怎样经过 NoC。

## 常见通信形状

下面用一组端点说明数据的逻辑效果。一个操作是否包含源端自身、数据如何排列，以及允许哪些大小和类型，要以具体接口的契约为准。

| 操作 | 输入 | 结果 |
| --- | --- | --- |
| 广播 Broadcast | 一个源的数据 | 组内所有指定参与者得到相同数据。 |
| 多播 Multicast | 一个源的数据和目的集合 | 集合中的目的端得到相同数据；集合不必是全网。 |
| Scatter | 一个源提供的不同数据块 | 各目的端得到各自指定的数据块。 |
| Gather | 多个参与者各提供数据 | 一个目的端收集这些数据，通常按约定次序排列。 |
| Reduce | 多个参与者各提供输入和归约算子 | 一个目的端得到合并后的结果。 |
| AllReduce | 多个参与者各提供输入和归约算子 | 所有参与者得到归约结果。 |
| Reduce-Scatter | 多个参与者提供输入和归约算子 | 数据先按语义归约，结果的不同部分交给不同参与者。 |
| AllGather | 多个参与者各提供数据 | 每个参与者得到按约定排列的全部数据。 |
| All-to-All | 每个源为各目的端提供数据 | 每个目的端得到各源发给自己的数据。 |
| Barrier | 一组参与者的到达事件 | 按接口定义的条件完成同步；它本身不定义上述数据运算。 |

这些名称描述“结果是什么”。实现可以将一个操作分解为多个点对点消息，也可以使用网络内复制或归约。[MPI 4.1 集体通信概述](https://www.mpi-forum.org/docs/mpi-4.1/mpi41-report/node114.htm)给出了进程组上的定义；这里借用其通信形状，不要求 NoC 实现 MPI 接口。

## 一个四端点例子

端点 0、1、2、3 分别持有数值 1、2、3、4。假设所有端点都属于同一组，算子为精确整数加法：

- Gather 到端点 0，可以得到按端点顺序排列的 [1, 2, 3, 4]。
- Reduce 到端点 0 得到 10；AllReduce 则让四个端点都得到 10。
- Broadcast 将源端的**同一份**数据发给组内目的端。Scatter 可以给每个目的端不同的数据块。
- All-to-All 中，源 i 可以为目的 j 准备不同的块 x[i,j]；目的 j 最终取得各源发给它的块。若允许本地交付，x[j,j] 不必经过网络。

通信组、数据分块和顺序不是由拓扑自动决定的。同一个逻辑操作可以有不同的树、环或多份单播实现；比较它们时还要考虑位置、链路与端点容量。

## “完成”指哪个边界

| 事件 | 能说明什么 |
| --- | --- |
| 源端提交或注入 | 请求已交给某个发送边界，不代表所有目的端已收到。 |
| 某个目的端接收 | 该端点收到契约要求的数据；其他目的端可能仍在等待。 |
| 组操作完成 | 只有接口定义了该事件，才能判断哪些参与者已完成以及缓冲何时可复用。 |
| 消费者完成 | 数据已达到上层指定的使用边界；它可能晚于网络交付。 |

例如，MPI 非阻塞集体操作的局部完成允许调用方按该接口规则使用缓冲，但一般不表示其他进程已经完成，甚至不一定表示它们已经开始。[MPI 4.1 非阻塞集体操作](https://www.mpi-forum.org/docs/mpi-4.1/mpi41-report/node145.htm) 其他系统可以约定更强或不同的完成条件。

设计 NoC 接口或工作负载模型时，应记录参与组、数据范围、顺序、局部交付规则和依赖的完成事件。还要说明错误、取消和超时如何报告；超时本身不证明在途数据已消失。逐 flit 交付与上层事务完成的边界可参见[事务拆分、顺序与完成](../05-system-integration/transaction-ordering-and-completion.md)。
