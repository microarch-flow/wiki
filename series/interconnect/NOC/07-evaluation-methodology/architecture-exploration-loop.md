# 架构探索与实验设计：怎样比较候选？

<span id="architecture-exploration-loop"></span>

上级：[08 性能评估与架构探索](../SUMMARY.md#07-evaluation-methodology)；原章节：[07 Evaluation Methodology](./README.md)

相关：[性能界与瓶颈分析](./performance-bounds-and-bottlenecks.md)、[Stall 分类与归因](./stall-taxonomy-and-attribution.md)、[实验与案例记录](./case-card-template.md)

<span id="这页在回答什么问题"></span><span id="目标不是找最优参数"></span>架构探索把一个设计问题转成可比较的候选、实验和证据。结果可以排除某些方案，也可以指出下一步需要什么模型；有限扫描不自动找到全局最优。

## 先固定比较问题

<span id="推荐闭环"></span><span id="baseline-应该怎么选"></span>先写出目标、约束和对照方案，再固定任务、端点位置、完成边界和模型版本。明确哪些资源预算相同，哪些随方案改变。例如固定端点注入能力与固定总布线预算回答不同问题，两者不一定能同时满足。

一轮实验可以按以下顺序进行：

1. 定义工作负载、目标指标、约束和可解释的 baseline。
2. 列出要改变的变量、固定项和可行参数范围。
3. 先用必要条件或简化模型筛选，再设计需要的仿真或测量。
4. 比较完成时间、各资源负载、等待及成本，并保存未完成任务。
5. 把观察、原因假设和已验证结论分开；决定保留、淘汰或继续验证。

## 用小范围组合检查交互

<span id="sweep-不要所有变量一起动"></span>延续[两源共享链路](./performance-bounds-and-bottlenecks.md#一个共享链路例子)：两个源各发送 64 B，源链路各为 16 B/cycle，其他假设相同。比较两种共享链路和两种目的端容量，单位均为 B/cycle：

| 候选 | 共享链路 | 目的端 | 已知完成时间下界 |
| --- | ---: | ---: | ---: |
| A：baseline | 16 | 16 | 8 cycle |
| B | 32 | 16 | 8 cycle |
| C | 16 | 32 | 8 cycle |
| D | 32 | 32 | 4 cycle |

表中只有容量下界，**没有实际仿真结果**。它说明两个资源的限制可能相互作用：只改变一项不会降低这里的最大下界，两项都改变后才降低。实际完成时间仍可能因流水、竞争或其他资源而不同；B 或 C 的下界不变，也不能证明它们没有收益。

初筛时一次改变一个参数，容易解释局部差异。若参数之间存在耦合，再用小型组合实验检查交互。对 VC 数、buffer 和链路宽度也要说明固定的是总存储、每 VC 深度还是面积预算。

## 结果需要什么证据

<span id="结果不只看更快了多少"></span>对每个候选记录实际测得的释放、注入、完成和未完成数量；按需要增加尾延迟、链路与端点负载、stall 分类和能量／面积。相同的局部变化不一定改变任务完成时间；观察与推断需要分别记录。

随机工作负载应记录随机种子及独立运行次数。若比较成对运行，需保证两侧使用可比较的输入；只使用同一个 seed，不保证不同程序消耗随机数的顺序相同。选择适合样本和目标的统计方法，并报告波动或不确定性。packet 延迟可能在同一拥塞阶段相关，不能简单把所有 packet 当作独立重复实验。[NIST 的自相关说明](https://www.itl.nist.gov/div898/handbook/eda/section2/eda251.htm)

有限任务要保留启动与结束阶段；连续稳态实验应说明预热、测量和排空方式。固定时间重放与依赖驱动工作负载可能产生不同反馈，比较时必须声明。

## 形成下一步决策

<span id="什么时候该停止当前层探索"></span>当现有模型可以排除某个候选，或决定结果的现象不在模型范围内，就记录结论并决定是否更换输入、补充模型或检查实现。成本和物理约束同样可能改变排序。

<span id="常见误区"></span><span id="一句话理解"></span><span id="建模启示"></span>案例记录应同时保存候选、输入、统计边界、证据、未验证假设和下一步。一个下界、一次仿真和真实硬件测量具有不同的证明范围。
