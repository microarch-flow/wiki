# UALink 规范组件：Common、DL/PL 与系统管理怎样分工

上级：[协议与系统案例](README.md)

UALink 已发展为多个规范组件。比较设备时，需要列出组件与版本，不能只写“支持 UALink 2.0”。下表按 2026-11-17 的[联盟公开目录](https://ualinkconsortium.org/specification/)整理；它描述规范发布状态，不证明某款器件已实现全部功能。

| --- | --- | --- |
| UALink 200G | 1.0 | 理解最初公开的分层与事务体系 |
| Common | 2.0 | 查看公共协议能力及新增网络内计算 |
| 200G Data Link and Physical Layers | 2.0 | 查看与 Common 拆分后的链路和物理承载 |
| 128G Data Link and Physical Layers | 1.0 | 查看另一组链路和物理层定义 |
| Chiplet | 1.01 | 查看芯粒集成接口、流控与管理边界 |

Common 与 DL/PL 拆分，使物理承载可以独立演进。“2.0”是版本号，不表示速率翻倍。Chiplet 的集成职责也不等于网络交换协议；其封装内承载背景见[D2D](../../D2D/README.md)。

## 网络内计算改变了哪一段工作

以归约为例：传统点对点方案先把输入传给其他端点，再由端点计算；支持相应算子的网络组件可以在传输途中合并部分数据。这样可能减少后续路径上的数据量或端点计算负担。

这个收益有条件：参与组、算子、数据类型、分块和执行次序必须匹配接口能力。多个源发往不同目的地的独立数据，不能仅因为网络支持归约就被合并。浮点加法的顺序改变还可能改变舍入结果。

因此，规范介绍网络内计算，不等于任意 AllReduce 都自动卸载。还需确认设备实现、软件选择、支持范围和回退路径。

## 版本表怎样转成兼容性检查

采购或集成时，应让双方提供同一份能力记录：公共协议版本、DL/PL 组合、lane 配置、可选操作、管理接口及软件版本。然后核对规范中的允许组合和产品认证，最后用对应配置进行互操作测试。

例如，两个端点都声称支持 Common 2.0，但若它们没有共同的物理承载或中间交换组件不支持所需操作，就不能直接构成目标通信路径。这个例子只说明检查方法，不指定未经核实的版本兼容矩阵。

详细时序、网络内计算字段及错误行为应以目标组件正文为准。本文不把公开目录未说明的细节补成事实；可追溯资料入口集中在[术语与资料](../06-modeling-and-reference/glossary-and-sources.md)。
