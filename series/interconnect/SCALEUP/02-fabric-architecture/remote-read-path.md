# 一次远端读取：请求、返回和在途状态怎样配合

上级：[交换结构](README.md)

远端读取包含去程请求与回程数据。能够连续发出请求，还不足以保证持续返回数据；请求状态、返回通道和目标内存都必须跟得上。

## 请求怎样走完路径

以下是构造模型：A 已有 B 的有效映射，每个读请求返回 256 B，传输不会跨越映射边界。

| 步骤 | 输入与处理 | 产生的输出或状态 |
| --- | --- | --- |
| A 接受读取 | 检查地址与操作，分配事务标识和返回位置 | 一个未完成请求条目 |
| A 注入请求 | 等待发送资源，编码目标和长度 | 发往交换结构的请求 |
| 交换结构转发 | 按目标选择出口，等待缓冲与链路 | 到达 B 的请求 |
| B 服务读取 | 检查授权，取得目标数据 | 带关联信息的返回 |
| A 接收返回 | 匹配请求、汇集数据、处理错误状态 | 完成事件，释放请求条目 |

这个过程只描述职责。实际协议可以拆分数据、乱序返回或使用多级事务标识。UALink 1.0 的公开分层说明包含分离请求／响应和端口标识机制；不能据此推断其他互连使用相同字段。[UALink 官方概览](https://ualinkconsortium.org/blog/ualink-200g-1-0-specification-overview-802/)

## 并发深度为什么影响带宽

若每个条目只能承载一个大小为 q 的读取，最多有 K 个请求在途，且稳态平均条目占用时间为 R，则这个窗口对应的理想吞吐上限为：

> B<sub>window</sub> ≤ K × q / R

R 从分配条目算到条目可复用，包括排队和返回。示例取 K = 64、q = 256 B、R = 1 μs，得到 16.384 GB/s。即使链路允许 100 GB/s，这个窗口也可能先限制吞吐。

反过来，目标为 B 时，需要至少覆盖 B × R 的在途数据。对 100 GB/s 和 1 μs，这相当于 100,000 B，按 256 B 请求向上取整为 391 个条目。这是必要的窗口预算，不是达到目标带宽的保证。

## 请求小，不代表请求通道可以忽略

小粒度读取会增加每秒请求数，压满发起端、目标端或交换处理能力。返回数据还要竞争反向链路；双向应用中，正反方向可能同时承载请求和数据。

因此诊断时要分别记录请求速率、返回字节、条目占用、目标服务时间和端口排队。仅统计应用取得的总字节，会隐藏控制消息及协议开销。下一篇用[拓扑预算](topology-and-bandwidth.md)把这些限制放到整个系统中。
