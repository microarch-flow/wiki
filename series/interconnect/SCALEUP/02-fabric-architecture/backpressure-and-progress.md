# 背压与拥塞：缓冲不溢出以后，请求能否继续前进

上级：[交换结构](README.md)

流控解决接收资源是否足够。拥塞分析解决多个流如何争用有限容量。前进性则要求请求最终能完成所需的后续步骤。这三个问题不能互相替代。

## 从一个被堵住的出口开始

假设 A、B 同时向 C 发送，C 的出口已满。交换组件必须暂停相关输入，或按协议处理无法接收的数据。采用信用流控时，发送端只能消耗已经获准使用的接收资源；资源释放后再恢复信用。

背压会沿路径传播。如果不同目的地的数据共享同一个队头，被阻塞的 C 流量还可能挡住去 D 的流量。这是队头阻塞。分队列或虚通道可以隔离部分依赖，但增加队列并不会增加物理出口容量。

## 为什么响应需要自己的前进条件

构造反例：A 发出读请求后占住所有可接收缓冲，同时等待 B 的返回；B 的返回又需要 A 释放缓冲才能发送。若系统没有其他逃离路径，双方都可能无法前进。

解决方式取决于协议和实现，可以包括独立响应资源、受控注入、明确的缓冲预留或无环资源依赖。不能只写“使用虚通道，所以没有死锁”。还要证明请求需要的返回资源不会被同一依赖链永久占用。

| 检查对象 | 要记录的问题 |
| --- | --- |
| 接收资源 | 信用按什么单位计数，归还事件是什么？ |
| 队列与仲裁 | 哪些流共享队头，是否可能长期饥饿？ |
| 请求与响应 | 是否共享资源，依赖关系是否成环？ |
| 目标端 | 何时停止接收，如何让已接收操作完成？ |

## 增加缓冲能解决什么

缓冲可以吸收有限突发，或覆盖信用往返期间的数据量。若平均到达率持续大于服务率，增加缓冲只会推迟背压，并增加排队时间，不能提高持续服务能力。

评估时应同时看吞吐、尾延迟、队列占用和停顿原因。平均吞吐相同的两个方案，可能具有完全不同的长尾行为。
