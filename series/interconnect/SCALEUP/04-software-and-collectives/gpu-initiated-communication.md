# GPU 发起通信：数据传输、通知和等待怎样配合

上级：[软件与集体通信](README.md)

GPU 内核可以通过通信接口直接发起远端操作。这能减少某些主机提交环节，但不会消除地址授权、完成检测或执行资源限制。本文用 NVSHMEM 说明接口边界，不假设所有 GPU 通信库采用相同语义。

## 从 PE 与对称对象开始

NVSHMEM 使用 PE 表示参与处理实体，并用对称对象表达可由其他 PE 访问的数据。远端操作通常通过对象的本地地址表达和目标 PE 标识定位远端对象；不能随意传入另一个进程中的普通指针。

初始化、对称分配、参与者一致的调用要求，应按[官方 API 概览](https://docs.nvidia.com/nvshmem/api/latest/api/overview.html)执行。数据对象可访问之后，put、get 和原子接口才有有效目标。

## 用带通知传输交付一轮数据

假设 A 是唯一生产者，B 是唯一消费者，双方已为数据和通知分配有效对象。本例每轮使用递增编号 e，避免把上一轮的通知误认为本轮完成。

1. A 完成本轮源数据生产。
2. A 使用支持的 put-with-signal 操作，把数据交给 B，并发布 e。
3. B 使用对应的信号等待接口观察 e，再消费本轮数据。
4. B 通过另外的确认协议允许 A 重用目标槽位；若使用多个槽位，则分别管理其生命周期。

NVSHMEM 的[通知操作契约](https://docs.nvidia.com/nvshmem/api/latest/gen/api/signal.html)规定数据交付与信号更新之间的关系。普通 put 后紧跟普通远端写标志，不能未经证明就替代该契约。多生产者、通知计数回绕和缓冲环复用需要额外设计。

## 源缓冲复用与远端消费是两件事

阻塞、非阻塞和流式接口具有不同完成边界。非阻塞传输后，源缓冲是否可重用应按该接口要求等待；目标消费者则要通过规定同步观察数据。`quiet` 和 `fence` 的作用见[排序与完成](../01-access-semantics/operations-ordering-and-completion.md)。

CPU 上调用的排序操作不能直接当作 GPU 发起通信已经完成。主机等待 GPU 工作时，需要建立 GPU 侧通信完成与内核／流完成之间的关系。

## 忙等也需要执行资源

构造反例：消费者内核占满设备可驻留资源并等待生产者，而生产者内核尚未获得执行机会。这是执行调度依赖，不是增加链路带宽就能解决的问题。应使用库支持的启动、同步和进度机制，并检查执行模型。

GPU 发起通信的收益最终取决于减少了多少提交开销，以及新增的通信内核、HBM 访问和等待消耗。下一章的[重叠分析](../05-workloads-and-performance/overlap-and-critical-path.md)处理这些成本。
