# 多卡通信怎样测试：正确性、路径和计时边界一起记录

上级：[负载与性能](README.md)

测试首先要证明操作得到正确结果，再说明测量覆盖了哪条路径。单个大消息带宽值不能代表小消息同步、非均匀流量或真实任务。

## 分四步建立证据

1. **记录配置。** 保存设备型号、物理拓扑、分区、驱动与库版本、rank 映射、NUMA 位置和环境变量。
2. **验证点对点。** 按设备对与方向检查可达性，分开测试内核访问、显式复制及通信库发送／接收。
3. **扫描集体操作。** 改变消息大小、参与者子集和数据类型，先用默认配置，再开展有控制的算法对照。
4. **加入任务条件。** 测量计算并发、非均匀流量和多任务竞争，同时检查结果及尾延迟。

## NCCL Tests 命令示例

以下命令假设已经按项目说明编译 NCCL Tests，当前分配了八个可用 GPU，并具备足够内存。以下仅为命令示例，不附硬件实测结果。

```sh
./build/all_reduce_perf -b 8 -e 128M -f 2 -g 8 -w 5 -n 20 -c 1
```

它从小消息扫描到 128 MiB，每次翻倍，进行预热、重复测量和正确性检查。具体参数定义与默认数据类型应以所用提交的[官方 README](https://github.com/NVIDIA/nccl-tests/blob/master/README.md)为准。多进程、多节点需要相应构建和启动方式，不能只把 `-g` 改成集群 GPU 总数。

AMD 平台应使用对应版本的 [RCCL Tests](https://github.com/ROCm/rccl-tests)，不要直接假设二进制或构建环境通用。

## 避免测到错误的时间

GPU 工作异步执行，主机函数返回通常只说明提交边界。微基准应使用工具定义的设备计时方式；任务测试则应覆盖输入就绪到所有必要结果可消费的边界。跨设备事件不能未经验证就放到一个时间轴相减。

预热用于减少初始化等干扰，但冷启动本身可能是产品需求，应单列测试。重复试验应报告统计方法，不要只挑最大带宽。正确性失败的样本不能作为有效性能结果。

| 记录字段 | 最少内容 |
| --- | --- |
| 操作 | 算子、数量、数据类型、原地或非原地 |
| 配置 | 软件版本、设备集合、rank 映射、调优选项 |
| 时间 | 计时边界、预热、重复数、统计量 |
| 流量 | 应用大小、algbw、busbw 及解释 |
| 验证 | 错误计数、数值容差、异常与重试 |

浮点归约需要事先定义误差标准。发现结果错误、卡住或异常降速时，保留原始日志并按[诊断流程](../06-modeling-and-reference/diagnosis-and-recovery.md)缩小范围。
