# 停顿、丢包与性能下降：怎样沿证据定位故障？

上级：[性能、诊断与查阅](README.md)

先固定失败的操作和时间区间，再沿路径缩小范围。低吞吐是一种结果，不是故障位置；单个非零计数器也不一定与本次任务有关。

## 从可达性到完成逐层排查

| 现象 | 优先核对 | 对照方法 |
| --- | --- | --- |
| 链路未建立或降速 | 端口模式、介质、训练及错误状态 | 比较两端报告和链路健康 |
| IP 通而 RDMA 失败 | GID、QP、权限、MTU、接收资源 | 最小端点测试与错误完成 |
| 吞吐低且暂停多 | 热点、队列映射、PFC 与 ECN | 降低并发或改变路径，观察增量 |
| RC 报 RNR 相关错误 | 接收请求供给和软件推进 | 检查 RQ 补充、CQ 消费及重试配置 |
| 主机内存快、GPU 内存慢 | 注册、设备拓扑、库选路、GPU 同步 | 固定网络，仅改变内存位置 |
| 微基准正常而应用停顿 | 调用匹配、依赖、工作分配 | 应用日志与各 rank 阶段时间 |

RNR 表示接收资源相关条件，不等于交换机缓冲溢出；PFC 暂停也不能证明本端应用正确补充了 RQ。不要把不同层次的背压合成同一个原因。

## 取得有时间边界的统计

以下是只读工具示例，需安装相应软件并替换设备名。具体输出字段与权限由平台决定。

```sh
rdma link show
rdma statistic show
ibv_devinfo
ip -s link show dev eth0
ethtool -S eth0
```

测试前后分别采样并求增量，同时保存运行时长。累计计数包含其他任务和历史事件；设备复位或计数回绕还会破坏简单相减。硬件卸载流量应查看相应 RDMA 与端口计数，不能只看 netdev 字节数。[NCCL 网络排查文档](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/troubleshooting/networking_troubleshooting.html)

## 从一条假设推进

若怀疑共享出口拥塞，固定消息和端点，只减少发送者数量；若怀疑主机瓶颈，固定网络，只改变 NUMA 或 CPU 放置。每次改变一个主要条件，并保留失败样本。一次恢复正常不足以证明因果，尤其要排除后台流量变化。

## 恢复网络后仍需恢复应用状态

链路恢复、QP 重建与应用重试是不同动作。传输失败可能留下已部分更新的目标缓冲，非幂等操作也可能已执行而响应丢失。恢复时需要确定旧操作是否仍会到达、目标数据是否可用，以及新的连接能否复用旧授权。

不要通过盲目增加重试次数掩盖永久不可达，也不要在未确认状态时重新执行整批原子更新。使用请求标识、幂等协议或应用事务处理不确定结果，相关完成边界见[排序与生命周期](../03-rdma-endpoints/completion-ordering-and-lifetime.md)。
