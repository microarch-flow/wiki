# RPC、存储与集群通信：怎样把业务变成网络需求？

上级：[性能、诊断与查阅](README.md)

网络负载不是一个带宽数。至少需要描述发送方与接收方、消息大小、到达时刻、依赖关系和完成目标。同样的总字节数，可以产生完全不同的排队与任务时间。

## 三类负载的关注点

| 场景 | 常见结构 | 主要观察量 |
| --- | --- | --- |
| RPC | 小请求、响应、扇出与汇聚 | 完整请求时间、尾延迟、并发及服务端处理 |
| 远端存储 | 命令与数据方向不同，存在队列深度 | 吞吐、IOPS、完成语义及后端服务 |
| 集群通信 | 多参与者分阶段交换或归约 | 阶段完成时间、同步等待和流量放置 |

这些是分析入口，不是业务必然属性。RPC 也可能传送大对象，存储可能以小随机请求为主，集体通信可能只处理少量数据。应从实际日志或明确的构造参数出发。

## 一个 RPC 汇聚案例

假设一次查询向 16 个工作节点发出请求，每个节点返回 64 KiB，总响应为 1 MiB。如果响应在很短窗口集中到单个 NIC，接收端将出现 incast。即使请求发送量很小，响应方向仍可能饱和。

应用完成时间还包含最慢工作节点的处理与调度。把网络传输下界从端到端时间中直接相减，不能唯一得到计算时间，因为两个阶段可能重叠，也可能相互影响。排队模型见[Incast](../02-ethernet-and-ip/queues-incast-and-tail-latency.md)。

## 存储需要额外的完成定义

远端内存写入完成，不等于数据已经持久化到目标介质。远端存储协议还要定义命令完成、缓存策略和持久性保证。RDMAP 中数据放置与交付本身也有不同定义，见 [RFC 5040](https://www.rfc-editor.org/rfc/rfc5040.html)。本专题不把普通 RDMA Write 当作存储事务提交。

## 集群流量从已有模型取得

先根据并行切分得到参与者、方向和字节数，再映射到 NIC 与路径。TP／PP／DP 的推导见[并行方式与流量](../../SCALEUP/05-workloads-and-performance/parallelism-traffic.md)，MoE 见[分发与合并](../../SCALEUP/05-workloads-and-performance/moe-dispatch-and-combine.md)。这里关注这些流量是否集中到某条轨道或共享出口。

建议每个案例都保留一张流量表：源、目标、每轮字节、并发、轮次依赖、截止时间及证据来源。没有测量时标为教学假设，不能把行业常见描述代替本任务的输入。
