# 丢包、重传与拥塞控制：可靠交付怎样与有限带宽配合？

上级：[Ethernet 与 IP 网络](README.md)

可靠传输需要发现缺失并恢复数据；拥塞控制需要约束网络中的发送量；接收端流控需要避免超过接收能力。三种职责可以同时出现，但不能用一个“流控”概念替代。

## 以 TCP 说明两种窗口

TCP 用序号、确认及重传等机制提供有序字节流。发送端受接收窗口和拥塞窗口等约束：前者反映接收方可接受的数据范围，后者约束发送方在网络中的未确认数据量。接收方内存充足，并不意味着中间链路没有拥塞。

丢包也不一定来自拥塞，可能是链路错误、策略丢弃或接收资源耗尽。TCP 根据可观察的信号恢复并调整发送行为，不能仅凭应用吞吐下降推断物理链路故障。[TCP 基础规范](https://www.rfc-editor.org/rfc/rfc9293.html)

## ECN 提供信号，不自行决定调速

在支持并正确配置 ECN 的路径上，设备可以标记拥塞而不立即丢弃该包。接收端反馈信息，发送端按选定算法调整发送。交换机阈值、反馈时延与发送端响应共同形成控制环。[RFC 3168](https://www.rfc-editor.org/rfc/rfc3168.html)

DCTCP 根据被标记数据的比例调整 TCP 拥塞窗口，适用于受控的数据中心部署。它不是“开启 ECN”后的唯一算法，也不能未经额外措施直接套到公网。[RFC 8257](https://www.rfc-editor.org/rfc/rfc8257.html)

## UDP 外层不取消内层可靠性

RoCEv2 用 UDP/IP 承载 RDMA 传输。采用 RC 服务时，可靠性由相应 RDMA 传输机制承担，不是由 UDP 提供。反过来，不能因为 RDMA 名称相同，就把 RC 的保证套到 UD 等其他服务。

丢失一个包后重传多少、是否容忍乱序、何时超时，必须查具体协议与实现。不要把经典重传策略写成所有新 NIC 的固定行为。

## 传输完成也不是业务提交

连接失败时，上层可能不知道某个业务请求是否已经执行。重发非幂等请求可能产生重复扣款、重复更新或重复原子操作。应用应通过请求编号、幂等处理或事务协议解决这种不确定性；网络重传机制本身不能提供任意业务的恰好一次执行。

RoCE 的具体调速环见 [ECN、CNP 与 DCQCN](../04-roce/ecn-cnp-and-dcqcn.md)，应用恢复边界见[故障诊断](../07-performance-and-reference/diagnosis-and-recovery.md)。
