# QP、工作队列与 CQ：RDMA 请求怎样进入设备？

上级：[RDMA 端点](README.md)

RDMA 应用向设备提交工作请求，设备执行并生成相应状态。QP、工作队列和完成队列保存的是不同阶段的信息。它们不是线上每个包都一一对应的三个队列。

## 先建立对象关系

| 对象 | 职责 | 典型关联 |
| --- | --- | --- |
| PD：保护域 | 组织可相互使用的设备资源 | MR、QP 等关联到保护域 |
| QP：队列对 | 保存传输状态和工作队列关系 | 发送队列及接收侧资源 |
| SQ：发送队列 | 接收发送、读、写等工作请求 | 一个请求可能生成多个网络包 |
| RQ／SRQ | 提供接收工作请求 | 私有接收队列或共享接收队列 |
| CQ：完成队列 | 供软件取得工作完成状态 | 多个队列可以共享一个 CQ |

WR 是应用描述的工作请求，WQE 是设备可消费的队列元素表示，CQE 是完成记录。不能假设任意实现的内部格式相同。CQ 轮询读取完成，中断或事件通知帮助软件发现需要处理的状态；事件本身不能替代检查完成状态。

## 以 RC 连接为例

应用选择设备与端口，创建 PD、CQ 和 QP，准备合法内存。RC QP 需要配置对端及路径、序号和重试等属性，经过规定状态后才可发送。可使用 RDMA CM 管理连接流程，也可由应用交换参数并显式配置；这些步骤不能仅靠连接一根线完成。

接收 Send 前，对端应发布接收资源。设备执行请求后，软件从 CQ 取得状态、操作类型与工作标识，判断后续能否继续。详见 [RDMA 编程手册](https://docs.nvidia.com/rdma-aware-networks-programming-user-manual-1-7.pdf)。本文以 RC 建立主线，UD 等服务的连接与可靠性要求不同。

## 队列深度不是无限并发

SQ 满时不能继续无条件提交；CQ 消费不及时也可能产生错误。增加深度可以覆盖延迟，却占用设备与软件状态，还可能使拥塞时的积压更大。性能测试应记录并发、QP 数和 CQ 消费方式。

可以只给部分发送请求设置完成通知，以降低 CQE 处理量。此时必须按所用队列与操作的排序规则跟踪已回收区间，并保留排空和错误处理路径；不能简单把未产生 CQE 的请求当作永不需要管理。

提交接口还可能接受请求链的前部，再在某个请求处失败。[ibv_post_send](https://github.com/linux-rdma/rdma-core/blob/master/libibverbs/man/ibv_post_send.3)通过 bad_wr 标出失败位置。重试整条链前应先确认哪些请求已经提交，避免重复操作。
