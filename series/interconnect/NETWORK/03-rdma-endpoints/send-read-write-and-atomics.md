# Send、Write、Read 与原子操作：双方分别需要准备什么？

上级：[RDMA 端点](README.md)

以下以支持相应操作的 RC QP 为主线。操作是否可用，还取决于设备能力、QP 类型、内存权限和长度限制。接口中出现一个操作码，不表示每种传输服务都支持它。

## 四种基本操作

| 操作 | 发起端指定什么 | 目标端需要什么 |
| --- | --- | --- |
| Send | 本地数据和连接 | 提前发布可匹配的接收缓冲 |
| RDMA Write | 本地数据、远端地址与 rkey | 有效且允许写入的目标 MR |
| RDMA Read | 本地目标、远端源地址与 rkey | 有效且允许读取的源 MR |
| 原子操作 | 远端位置、操作数、本地返回位置 | 支持该操作且满足对齐和权限要求的 MR |

Send 的目标缓冲由接收端预先发布的接收请求决定。Write 的目标位置由发送方在授权范围内指定。Read 有请求与数据返回两个方向，不能只按请求头大小预算通信。典型原子操作返回旧值并更新指定位置，但不自动提供任意大小数据结构的事务性。

支持矩阵和 API 参数见 [ibv_post_send](https://github.com/linux-rdma/rdma-core/blob/master/libibverbs/man/ibv_post_send.3)。设备原子与 CPU/GPU 原子是否具有所需的共同原子性范围，必须查对应平台保证。

## Write with Immediate 为什么需要接收资源

普通 Write 放置数据后，不为接收方生成一个与 Send 相同的接收完成。Write with Immediate 则同时交付一个立即数通知，并消耗接收端发布的接收工作请求。大块载荷仍写入指定远端 MR，不是写入该接收请求的普通数据缓冲。

因此，“单边写不需要接收请求”不能扩展到 Write with Immediate。接收资源不足时，RC 可能遇到 RNR 及相应重试，耗尽重试后出错。接收请求供给与网络交换机缓冲是两种不同资源。[RDMA 编程手册](https://docs.nvidia.com/rdma-aware-networks-programming-user-manual-1-7.pdf)

## 怎样选择操作

目标端希望自己分配每条消息位置时，Send 更容易表达这种控制；发送端已知道目标布局时，Write 可直接放置；数据需求由读取者决定时，Read 可减少不必要的推送。选择时还要考虑通知、权限交换、并发窗口和应用所有权。

例如 A 写入 B 的数据区后，B 仍需要知道哪一轮数据已就绪。可使用符合接口规则的带通知写入，或另行建立经过验证的通知协议。不能只因为内存中出现了几个新字节就开始读取整条消息。具体时序见[排序与完成](completion-ordering-and-lifetime.md)。
