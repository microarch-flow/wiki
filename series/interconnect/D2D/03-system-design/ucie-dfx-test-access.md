# UCIe 2.0 DFx：封装后怎样访问与管理芯粒测试逻辑？

上级：[03 系统集成与验证](../SUMMARY.md#system-integration)

多颗芯粒装进同一封装后，测试设备或系统管理软件未必能从封装引脚直接访问每颗芯粒的内部测试电路。系统需要事先设计访问路径，才能发现能力、发出操作并取得结果。

本文以 **UCIe 2.0 的可选管理能力和 UCIe DFx Architecture（UDA）**为例。它关注怎样访问测试和管理逻辑，不把某次测试通过等同于整颗芯粒或封装没有缺陷。[UCIe 2.0 白皮书](https://www.uciexpress.org/_files/ugd/0c1418_b6481ec611e24c6e91f1beb743b0c860.pdf)

## 管理端怎样到达目标

假设封装中有芯粒 A 和 B。A 可通过一个封装外接口连接测试或管理端；A、B 都实现了本例所需的管理能力，且已建立可用、允许访问的路径。B 内有可被管理路径访问的内存自测试模块。

一次访问可以沿下面的**构造路径**进行：

> 管理端 → A 的外部桥接入口 → 管理网络 → B 的 DFx Management Hub → B 的内存自测试模块

状态再经可用的管理路径返回。箭头表示职责关系，不规定芯粒的实际布线或一定使用哪一组引脚。不同产品可能选择不同的外部接口、管理端和封装内路径。

联盟白皮书描述了管理网络与 hub/spoke 结构：每个 UDA 芯粒中的 **DFx Management Hub（DMH）**提供访问入口并转发管理信息；连接的 **DFx Management Spoke（DMS）**提供具体功能，例如扫描控制、内存自测试或遥测。外部桥接和管理传输为访问这些能力提供路径；各 spoke 的实际功能和配置仍要按实现检查。[UCIe 2.0 白皮书，第 2–3 页](https://www.uciexpress.org/_files/ugd/0c1418_b6481ec611e24c6e91f1beb743b0c860.pdf)

## 沿一次内存自测试看分工

继续使用上面的假设，并假设管理端拥有执行测试所需的权限，B 的内存和测试模块处于允许测试的状态。

1. **发现能力。** 管理端经可用管理路径发现 B 的 DMH，以及 B 提供的内存自测试 spoke。
2. **配置并启动。** 管理端按该模块支持的接口选择测试对象和模式，再发出启动操作。具体寄存器和测试算法取决于实现。
3. **B 执行测试。** 自测试模块驱动其能够覆盖的本地内存，并检查结果；DMH 提供访问与转发，不代替测试模块执行测试。
4. **读取结果。** 管理端按模块定义观察进行中、通过或失败等状态，记录对象、模式和条件。

这只是说明职责的例子，不规定 UCIe 2.0 的完整寄存器序列。若结果显示通过，它只能说明该模块覆盖的内存在所用测试和条件下通过。它不自动证明 A 与 B 之间的所有数据线、B 的其他逻辑或业务访问都正确。

## 访问路径与测试路径是两个问题

**管理访问路径**决定命令和结果能否到达测试模块；**被测路径**决定测试实际检查了哪些电路。两者可能使用不同资源。

例如，本例如果能访问 B 的自测试模块，测试仍可能只覆盖 B 的内部存储，而不覆盖 A、B 之间的全部主带数据线。相反，链路回环测试可以覆盖一条指定的芯粒间路径，却不一定检查 B 的内存。需要同时记录测试入口、实际经过的电路、测试模式和结果观察点。[链路测试与故障定位](./link-testing-and-diagnosis.md)

UCIe 2.0 支持将管理传输封装在边带或主带中，也允许设计使用专门的管理端口。具体路径由系统实现决定：如果测试访问依赖的连接本身不可用，就不能假定管理命令仍能到达 B；是否存在备用入口需要检查设计。[UCIe 2.0 白皮书，第 2–3 页](https://www.uciexpress.org/_files/ugd/0c1418_b6481ec611e24c6e91f1beb743b0c860.pdf)

## 封装前后还要分别检查什么

| 阶段 | 主要问题 |
| --- | --- |
| 装配前 | 当前筛选能覆盖哪些 die 内部逻辑和可触达接口？哪些条件要留到装配后检查？ |
| 装配后 | 实际芯粒间连接和已装配对象能否访问并通过所需测试？ |
| 使用中 | 系统提供哪些状态、计数器或诊断能力？触发测试是否会影响正在运行的业务？ |

通过封装前筛选的 KGD 有明确测试边界，不表示装配后的连接一定正确。[FAB：KGD](../../../chip-development/FAB/wiki/03-wafer-test-and-cp/kgd-known-good-die.md)；[OCP 芯粒集成测试流程](https://www.opencompute.org/news/addressing-the-colossal-challenge-of-system-co-optimization-with-a-holistic-chiplet-design-methodology/)

UDA 是一种架构选择，不是所有 UCIe 芯粒都必然实现的功能。能够访问测试逻辑，也不能单独证明访问方身份、权限或消息完整性；防护和开放时机需要按所用规范版本及产品设计确认。

[IEEE 1838](https://standards.ieee.org/ieee/1838/5073/)定义了面向三维堆叠集成电路的测试访问架构，覆盖堆叠前后对 die 内部及 die 间连接的测试访问。它和本文的 UDA 是不同的标准架构，不应把任一方案当作所有多芯粒封装的必选实现。
