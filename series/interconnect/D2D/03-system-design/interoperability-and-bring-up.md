# 芯粒互操作与启动：连接接通后怎样让系统可用？

上级：[03 系统集成与验证](../SUMMARY.md#system-integration)

两颗芯粒即使都声明支持同一种接口，也不一定能直接组成可用系统。封装连接、电气条件、承载格式和上层功能都要匹配；上电后，链路与目标资源还要完成各自的准备。

本文用一个构造案例区分三个问题：**设计是否匹配、链路是否就绪、目标功能是否可用**。具体启动状态和检查顺序取决于所选接口与实现。

## 先检查设计能否配合

假设系统要把芯粒 A 的访问送往芯粒 B 的寄存器。两颗芯粒都提供相同名称的 PHY，本地逻辑也都使用 AXI。但这些名称还不能证明它们能交换同一笔事务。

| 要检查的边界 | 需要双方或系统共同满足的条件 |
| --- | --- |
| 封装与连接 | 芯粒方向、凸点映射、数据与时钟连接，以及通道条件符合双方接口要求。 |
| 电气与时序 | 信号电平、供电、时钟方式和速率范围相容；所选通道满足相应约束。 |
| 接口与承载 | 版本、方向、数据宽度、传输格式、可选功能以及所需的初始化方式相容。 |
| 事务与系统 | 双方对请求、响应、地址和错误的解释一致；地址映射和目标资源支持预期访问。 |

例如，A 和 B 都在片内使用 AXI、跨芯粒也都使用同一种 PHY，但 A 用格式 P 封装请求，B 只识别不兼容的格式 Q。即使物理连接能够传位，B 也不能按 A 的预期解析访问。P 和 Q 是为说明边界而假设的格式。

这些检查应在选择芯粒和设计封装时完成。接口名称和规范的版本兼容声明很有用，但不能代替对具体配置和可选能力的核对。[UCIe 联盟对初始化与配置的说明](https://www.uciexpress.org/post/introduction-to-ucie-webinar-q-a-recap)；[OCP FCSA 1.1.0](https://www.opencompute.org/wp-content/uploads/2026/10/FCSA-1.1.0.pdf)

## 从上电到第一次访问

继续假设设计检查已经通过，且本系统具有执行下列检查所需的控制和观测手段。这里是**排查思路**，不是所有接口通用的状态机：

1. **准备供电、时钟与复位。** 按芯粒和封装的要求建立工作条件，释放相关复位。
2. **准备物理接口。** 按所选接口完成必要的配置、初始化和对齐；如果该接口要求训练或校准，也要完成相应步骤。
3. **建立共同承载方式。** 两端采用相容的数据宽度、格式和上层协议；需要协商的能力按所用规范协商。
4. **准备系统资源。** 配置访问所需的地址映射和目标资源，并确认访问方具有所需权限。
5. **执行受控访问。** 发起一笔预期结果已知的访问，检查请求、返回数据和状态。

接口的步骤并不完全相同。UCIe 联盟的问答将宽度、频率和协议支持列为其链路初始化涉及的参数；而现有 [BoW.Flexi 1.0.0 案例](../bow-flexi.md)说明该版本没有定义 PHY training，仍有复位和配置要求。不能把某一接口的训练流程推广到所有芯粒连接。

## 链路就绪不等于访问成功

假设步骤 1–3 已完成，A 和 B 的链路已经就绪。A 仍可能因为地址映射不正确、目标尚未退出复位，或 B 不支持预期事务而无法读到寄存器。

反过来，读取失败也不能直接证明 PHY 有问题。应先看系统实际能观察到什么，再缩小范围：

| 现象 | 下一步可以检查的方向 |
| --- | --- |
| 链路始终不能就绪 | 供电、复位、时钟、物理连接和两端要求的初始化条件。 |
| 链路就绪，但远端不能解析消息 | 双方选择的格式、协议、宽度和相关配置。 |
| 消息送达，但访问返回错误或超时 | 地址映射、权限、目标状态和事务响应；超时本身不能证明请求已取消。 |

表中的方向只是排查入口，不是故障与原因的一一对应。能否区分这些情况，还取决于芯粒提供的状态、计数器和调试接口。封装后部分内部节点难以直接探测，因此可测试性和可观测性需要在设计阶段考虑。[UCIe 2.0 可管理性白皮书](https://www.uciexpress.org/_files/ugd/0c1418_b6481ec611e24c6e91f1beb743b0c860.pdf)
