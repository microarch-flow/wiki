# 多颗芯粒怎样连接？从数据放置看跨芯粒流量

上级：[03 系统集成与验证](../SUMMARY.md#system-integration)

两颗芯粒之间有一条高带宽链路，并不表示多芯粒系统中的每次访问都能使用这条带宽。多个计算和存储位置会共享不同的接口；数据可能需要经过中间芯粒，才到达目的地。

本文用一个构造案例，把**连接关系、数据放置和每段链路上的流量**放在一起看。它不是某个产品的内部拓扑或性能测量。

## 先画连接，再确定路径

假设同一封装内有四颗芯粒，连接关系为 **B ↔ A ↔ C ↔ D**。A、C 执行计算，也具备转发经过本芯粒的数据所需的接口和逻辑；B、D 各提供存储服务。图中每一段都代表两端兼容的 D2D 接口及封装连接，不只是一条抽象的线。

例如，B 的数据可以直接送到 A；要按本例路径送到 C，则先经过 B → A，再经过 A → C。A 能否转发、数据怎样选路，以及转发是否与本地访问共享缓冲和带宽，都由系统设计决定。

逻辑连接图也不能单独证明封装能够实现它。设计时还要检查每颗芯粒的接口数量、位置、数据方向、可用边缘及封装布线。增加一条直连可以改变路径，也会占用两端 PHY 和封装资源；是否值得，需要结合流量和具体实现比较。

## 固定连接，改变数据放置

下面只统计**存储服务返回的数据**，不统计请求、响应头、重传或其他流量。GB 按十进制计算。假设：

- 每段链路全双工，每个方向都能持续承载 **16 GB/s 有效数据**；两个方向的容量分别统计。
- B、D 各能持续提供 16 GB/s；A、C 的计算逻辑各能持续接收 16 GB/s。A、C 的转发和内部资源也足以承担示例中的中转。
- 路径按上面的连接关系选择；数据不从缓存直接命中，不经多播复制、压缩或合并，系统处于稳定工作状态。

**第一种放置：就近读取。** A 从 B 接收 16 GB/s，C 从 D 接收 16 GB/s。最终交给两个计算芯粒的数据合计是 32 GB/s。B → A 和 D → C 各承载 16 GB/s；两个计算芯粒之间没有本例数据流量。

**第二种放置：两侧各取一半。** B、D 各向 A 和 C 发送 8 GB/s。指定两条远端路径分别为 B → A → C 和 D → C → A：

| 数据来源 | 给 A 的数据 | 给 C 的数据 |
| --- | --- | --- |
| B | 8 GB/s，经 B → A | 8 GB/s，经 B → A → C |
| D | 8 GB/s，经 D → C → A | 8 GB/s，经 D → C |

此时 B → A 承载 16 GB/s，D → C 承载 16 GB/s；A → C 和 C → A 各承载 8 GB/s。A、C 最终仍各收到 16 GB/s，总共收到 **32 GB/s**。

但如果数据每跨一段芯粒间链路就计一次，第二种放置的链路累计流量为 **16 + 16 + 8 + 8 = 48 GB/s**。第一种是 16 + 16 = **32 GB/s**。同样的最终交付量，在第二种放置下消耗了更多跨芯粒传输资源。

这里的 48 GB/s 是各有向链路负载之和，不是单条链路带宽，也不表示应用吞吐必然下降。具体结果还取决于中转、排队和端点服务；本例假设这些资源足够，才可以持续完成所述流量。

## 设计时怎样使用这个结果

先列出实际需要交换的数据、来源和目的，再为每条允许的路径统计逐段流量。检查每段的方向容量，以及中间芯粒的转发、缓冲和其他共享资源。数据放回本地可能减少跨芯粒流量，但也可能增加复制或占用本地存储；代价取决于工作负载。

增加直连、改用集中式中转，或提供多条可选路径，会改变端口数、封装布线和流量分布。图上存在一条备选路径，不代表接口和路由一定支持使用它。链路容量是必要条件，也不足以单独证明请求延迟、持续吞吐或无死锁。

[MCM-GPU 原始论文](https://research.nvidia.com/sites/default/files/publications/ISCA_2017_MCMGPU.pdf)研究了多芯粒 GPU 中的存储分布、数据局部性和封装内带宽。它的结构与结果属于论文模型，不是本文 B—A—C—D 例子，也不能直接当作量产产品的内部参数。
