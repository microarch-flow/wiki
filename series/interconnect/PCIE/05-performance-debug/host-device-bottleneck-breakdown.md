# 主机与设备数据路径：如何定位吞吐瓶颈？

上级：[性能与调试](README.md)

链路利用率低只是一项观察。上游没有工作、读窗口太小、目标内存慢和设备正在计算，都可能让链路空闲。有效诊断需要同时看到任务供给、在途状态和服务结果。

## 一条完整路径可以拆成

| 路径段 | 输入与输出 | 可用观测 |
| --- | --- | --- |
| CPU / 驱动 | 任务 → 已发布描述符 | 提交率、批大小、Doorbell 时间 |
| 设备队列与 DMA | 描述符 → 内存请求 | 待发队列、Tag 占用、请求大小 |
| PCIe 层次 | 请求/数据 → 下一跳 | 每跳速率、宽度、方向吞吐、信用阻塞 |
| 主机翻译与内存 | 地址请求 → 数据或状态 | IOMMU fault、可用翻译及内存计数 |
| 完成处理 | CQE → 软件消费 | CQ 占用、中断率、消费延迟 |

计数器不一定全部由通用软件暴露。缺少 Tag 或信用计数时，应结合设备遥测、受控负载和协议分析工具，不编造统一寄存器名。

## 用不同证据区分竞争假设

| 同一时间窗的观察 | 候选解释 | 反例或下一项证据 |
| --- | --- | --- |
| 待发队列常空、链路空闲 | 软件供给不足 | 设备也可能在执行长计算；查执行状态 |
| 有工作、Tag 满、RTT 稳定 | 请求窗口限制 | 同时检查完成缓冲和请求供给 |
| 有工作、Tag 满、RTT 随负载上升 | 返回或目标服务排队 | 用每跳和主机内存计数定位，不能只怪 RC |
| 有待发写、PD 信用等待增加 | 下游接收或更新路径限制 | 查看接收消费率，ACK 不等于信用归还 |
| CQ 已有条目、应用仍等待 | 软件回收或通知延迟 | 检查命令标识、有效位与所有权 |

## 一个受控对照实验

固定设备、NUMA 位置、传输方向、缓冲区和映射方式，只逐步增加队列深度。每档记录有效吞吐、实际请求长度、完整 RTT 和 Tag 平均占用。

若吞吐先随占用增加而上升，之后在 Tag 满时平台化，而 RTT 基本稳定，窗口容量是候选限制。若增加深度主要让 RTT 增长而吞吐不再增长，应寻找服务能力上限。两种结论都需要排除完成处理和设备内部工作变化。

随后可以独立改变请求大小、批大小或 NUMA 放置，每次只改变可解释的一组因素。不要同时关闭 IOMMU、换插槽、改包长，再把结果归因于某一个参数。

## 结果怎样报告

报告方向、有效字节口径、运行窗口、配置与实际状态，给出平均值及适用的延迟分布，并记录反例检查。不同硬件的 IOMMU、RC 和 Switch 延迟应实测标定。
