# CPU 与设备如何协作执行一次迭代

上级：[本专题导读](README.md)

主机提交一个 GPU 调用，并不代表设备已经完成该调用。推理运行时必须区分“工作已提交”“结果已就绪”和“资源可复用”三个时刻。

## 一次迭代的交接

CPU 侧通常负责接收请求、选择本轮工作、准备输入和状态映射。设备侧执行算子、通信和必要的采样。随后结果回到请求状态机，触发输出和下一轮工作。

<ol class="inference-flow">
<li><strong>准备。</strong>调度器给出请求标识、token 范围和已分配状态；执行器生成设备输入。</li>
<li><strong>提交。</strong>搬运与内核进入相应队列；提交返回只表示排队成功。</li>
<li><strong>完成。</strong>事件或其他同步机制确认依赖已完成，结果可被后继操作使用。</li>
<li><strong>更新。</strong>推进请求状态，输出 token；释放或复用不再被访问的缓冲区。</li>
</ol>

CPU 可以为下一轮准备不依赖当前结果的元数据。若下一轮需要刚采样的 token，则必须等待其可用；不能因为接口异步就省略数据依赖。

## Stream 与 event 表达什么

在 CUDA 的同一 stream 中，操作通常按队列顺序执行；不同 stream 之间需要显式依赖，或者由有明确语义的同步机制建立依赖。

例如传输 stream 在输入复制之后记录事件，计算 stream 等待该事件后启动内核。若主机还需把结果读回，要等设备到主机的复制完成才能读取。要复用输入缓冲区，则需确认所有引用它的内核和传输都已完成。记录事件时应明确它证明了哪一次访问结束。

不同 stream 允许表达并发，但不保证物理重叠。复制引擎、HBM、执行单元、固定页主机内存和依赖关系都会影响实际结果。多卡通信同样需要与生产和消费张量的操作建立正确顺序。

## 启动开销与 Graph replay

很多短内核可能让主机启动和设备间隙占据明显比例。算子融合减少内核数，Graph replay 则减少重复提交一组操作的控制开销。两者作用位置不同。

构造一轮含 100 个短内核的例子，假设每次主机提交开销为 3 μs，累计提交工作为 300 μs。这不等于关键路径一定增加 300 μs：主机提交与设备执行可能重叠。应观察设备空隙和主机队列，而不是机械相加。

捕获图需要准备符合要求的操作、缓冲区和形状。动态路径或不支持捕获的操作可能需要局部捕获、更新或回退，详见[动态形状](dynamic-shapes.md)。

## 取消与异步执行怎样相遇

取消在主机侧生效后，已提交的设备工作仍可能访问旧 KV。执行器需要把最后一次设备访问的完成信号交给状态管理器。请求如何停调度、怎样处理晚到的结果以及何时归还 KV 块，见[取消、故障与资源回收](../08-serving-lifecycle/request-resource-lifecycle.md#一次取消发生在提交之后)。

## 如何测量这条路径

主机计时器测得异步调用返回时间，通常不能代表设备执行时间。设备事件适合测量指定流中的设备区间；客户端时间适合测量用户体验；跨设备或跨主机的 Trace 需要同步时钟或明确因果关联。

定位时同时观察 CPU 输入准备、GPU 执行、通信、等待和输出处理。异步调度的收益是缩小关键路径上的空隙，不是让 CPU 工作“没有成本”。
