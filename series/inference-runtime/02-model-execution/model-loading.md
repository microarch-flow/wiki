# 从模型文件到可执行后端

上级：[本专题导读](README.md)

模型文件保存参数与结构信息，执行后端提供可用的算子实现。运行时需要把两者匹配，才能得到可提交到设备的工作。加载成功只说明实例已经建立，不说明所有输入形状都可执行，也不说明服务已经预热完成。

## 加载路径的输入与输出

输入至少包括模型配置、权重、分词器或其他预处理规则、精度要求、设备与并行配置。输出包括设备上的参数、可执行的算子或子图、内存池，以及支持的输入形状和功能范围。

典型过程如下：

1. 解析模型结构与参数命名，校验权重形状、数据类型和版本。
2. 按并行布局切分或复制参数，完成必要的解包、重排与设备搬运。
3. 为算子选择后端和内核；可以即时执行，也可以编译部分图。
4. 分配工作区、KV 池及通信资源；准备常用输入形状。
5. 预热并验证输出，最后把副本标为可接收请求。

具体顺序可交错。例如某些权重转换在 CPU 完成，另一些在设备上完成。文件中的低比特编码也不一定等于内核直接读取的布局。

## 图划分与执行后端

ONNX Runtime 的 Execution Provider 通过能力查询报告可处理的节点或子图，再由运行时进行分配。TensorRT 则可以构建针对特定模型、精度和形状范围优化的执行引擎。LLM 框架还常使用手写模型执行器，选择 Attention、矩阵乘和通信实现。

因此，“模型已经导出为图”与“模型能在某设备高效执行”之间，还隔着支持范围、布局转换和执行计划。

假设一个图含 A、B、C 三段，设备后端只支持 A、C。若 B 回退到 CPU，可能出现设备到主机、主机到设备的搬运和同步。即使 B 的 FLOP 很少，边界成本也可能显著。分析时应画出数据所在位置，而不是只数不支持的算子个数。

## 模型实例与请求实例分开

权重和只读常量可以在多个请求间复用。请求各自的 KV、输出长度、随机数状态和约束状态不能随意合并。

LoRA 等适配器又增加一层身份：同一基础模型可以搭配不同适配器。批执行是否支持多个适配器、如何切换内核参数、适配器是否常驻，都取决于实现。前缀缓存也需要包含对应身份，不能只按输入 token 匹配。

模型升级宜采用明确的版本选择。已经进入执行的请求应继续使用其确定的版本，或通过显式的失败／重试规则迁移。不能在同一请求中途无条件替换权重并沿用旧 KV。

## 冷启动由哪些成本组成

启动时间可拆成文件读取、反序列化、参数转换、设备搬运、编译／捕获、分配和预热。可并行的阶段不能简单全部相加；有依赖的阶段也不能假设完全重叠。

启动峰值内存可能同时包含旧权重、转换中间结果和新布局。稳态容量估算不能代替加载峰值检查。构建产物缓存能减少重复编译，但缓存键需要覆盖影响代码或布局的条件。

对外服务的“就绪”应包含一条可完成的代表性执行，而不只检查进程和端口。扩缩容时，还需考虑模型加载期间占用的资源，见[副本管理](../08-serving-lifecycle/routing-and-scaling.md)。
