# 长上下文执行与上下文并行

上级：[本专题导读](README.md)

长上下文会增加状态容量与 Attention 工作，但增加设备数不自动解决问题。首先要确认状态沿哪个维度分布，以及每个查询还需读取哪些位置。

## 先区分三种改变

KV 头切分沿头维分配状态，适合有足够 KV 头的布局。上下文并行沿序列或状态位置维分配工作和存储。滑动窗口则改变每个查询允许访问的历史范围，是模型语义的一部分。

滑动窗口不能直接当作全注意力的无损替代。Prefill 分块也只是改变执行时间划分，未必减少需要保留的历史。

## Prefill 上下文并行

对很长的输入，可以将查询位置分配到多个 rank，并通过交换或轮转所需 K/V 完成注意力。每个查询仍需看到语义规定的全部位置。

收益来自分担计算或状态；成本来自 KV 交换、同步和工作分配。因果掩码会使不同查询区段的有效工作量不同，平均切 token 数不一定等于平均计算量。

环式、分块交换及其他实现使用不同通信计划，不能仅按“序列除以设备数”估算时间。

## Decode 上下文并行

单个新查询可能需要读取整个历史。若 KV 沿历史位置分片，各 rank 计算局部分数和局部输出，再合并归一化结果。

合并不能直接平均各分片已经归一化的输出。设分片 r 保存最大值 $m_r$、指数和 $\ell_r$ 和未归一化加权和 $z_r$，需以全局最大值 M 重标度：

$$M=\max_r m_r,\qquad
o=\frac{\sum_r e^{m_r-M}z_r}{\sum_r e^{m_r-M}\ell_r}$$

空分片需明确处理。这个关系与[在线 Attention](../03-kernels-and-precision/05-attention-kernels.md)相同，但跨设备合并还增加通信与同步。

## 为什么 TP 增大后 KV 可能没有继续下降

若模型只有少量 KV 头，头维切分很快达到粒度限制。继续增加 TP 可能导致 KV 复制。上下文维切分可以提供另一种分担方式，但它的通信模式与头维切分不同。

MLA 的压缩缓存布局还需单独建模，不能用“KV 头数少”就直接套标准 GQA 的容量与内核公式。[vLLM 上下文并行文档](https://docs.vllm.ai/en/stable/serving/context_parallel_deployment/)给出相关部署条件。

## 何时值得采用

如果瓶颈是单设备状态容量，上下文切分可能使任务可执行；如果关键路径受 KV 读取限制，也可能减少每设备读取。短上下文、小状态或高通信启动成本下，新增同步可能抵消收益。

应检查每 rank 状态峰值、位置分配、实际通信字节、局部工作量与最慢 rank。最大输入长度、模型位置编码支持和运行时支持范围也必须满足；不能把运行时能分配空间当作模型长上下文质量已验证。
