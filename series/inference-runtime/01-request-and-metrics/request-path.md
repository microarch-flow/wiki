# 一次推理请求的完整路径

上级：[本专题导读](README.md)

推理运行时把模型计算变成一个可持续服务请求的系统。模型给出“输入张量如何变成输出张量”；运行时还要决定何时执行、使用哪些资源、状态保存在哪里，以及何时可以释放资源。

本文以自回归文本模型为例。图中的模块是职责划分，不要求每个模块都独立成一个进程。离线推理也需要模型执行和状态管理，但可以没有 HTTP 接口、在线路由和流式输出。

## 先分清四层职责

| 层次 | 输入 | 输出 | 主要职责 |
|---|---|---|---|
| 服务入口与副本路由 | 请求、模型名、生成参数、截止时间 | 带请求标识的引擎任务 | 校验、选择副本、背压、取消传播 |
| 请求引擎 | 等待队列、运行中请求、资源余量 | 本轮执行计划 | 准入、批组成、token 配额、KV 生命周期 |
| 执行器与后端 | token、位置、状态映射、算子计划 | logits、更新后的状态、完成事件 | 加载权重、准备输入、启动内核、执行通信 |
| 采样与输出 | logits、采样状态、语法状态 | token、文本片段、结束原因 | 采样、停止判定、增量解码、返回结果 |

“推理引擎”“运行时”“服务框架”在产品命名中可能重叠。阅读具体实现时，应按输入、输出和状态归属识别职责，而不是仅按产品名分类。

## 一个请求怎样走完系统

<ol class="inference-flow">
<li><strong>接收与准备。</strong>选择模型版本，校验参数，应用聊天模板并分词。多模态请求还需准备对应的输入特征。</li>
<li><strong>排队与准入。</strong>检查执行和内存预算。前缀命中可以减少待计算工作，但仍需验证缓存身份。</li>
<li><strong>Prefill。</strong>计算未复用的输入位置，建立 KV。最后一个输入位置的 logits 通常用于选择第一个输出 token。</li>
<li><strong>迭代执行。</strong>把已选 token 作为下一步输入，读取历史 KV，产生新的 logits；调度器可以在迭代边界调整批组成。</li>
<li><strong>停止与回收。</strong>达到停止条件或收到取消后，停止新增工作。等待相关设备操作完成，再释放状态并返回结束原因。</li>
</ol>

这是一条逻辑路径。CPU 输入准备可以与设备执行重叠，输出传输也可以与下一轮计算重叠。重叠必须服从数据依赖；取消到达并不代表已经提交的设备工作立即停止。

## 贯穿系列的三个请求

后续批处理示例使用三个构造请求：A、B、C 的输入长度分别为 8、3、6 个 token；输出上限分别为 4、2、3。假设它们使用相同模型和生成策略，暂不启用前缀缓存或推测解码。

运行时同时维护三种“数量”：

- 活跃请求数：已经进入执行但尚未结束的请求数。
- 本轮输入 token 数：本轮真正交给模型的 token 总数，Prefill 可以一次贡献多个。
- 已保存状态量：已经计算并保留的 KV 或其他模型状态。

三者不能用一个 batch size 代替。一个长 Prefill 请求可以占用很多本轮 token，却只对应一个请求；多个 Decode 请求则可能每个只贡献一个 token。

## 哪些状态不能混在一起

权重主要属于模型实例。KV、随机数状态和已输出位置属于请求；缓存中的可复用前缀还带有共享引用。语法解析器与流式文本缓冲属于生成控制。调度队列、设备流和临时工作区属于执行系统。

例如请求 A 完成后，调度器可以移除 A，但执行器可能仍在读取它的 KV。只有最后一个使用者完成，且共享引用也已解除，块才能重新分配。这个边界是后续[资源回收](../08-serving-lifecycle/request-resource-lifecycle.md)的核心。
