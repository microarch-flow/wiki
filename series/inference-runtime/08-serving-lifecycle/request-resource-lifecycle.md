# 取消、超时、故障与资源回收

上级：[本专题导读](README.md)

请求结束不等于所有资源立即可释放。运行时需要让入口、调度器、执行器、传输任务和缓存管理器对“结束”达成一致。

## 请求状态与资源状态分开

请求可以经历：接收、等待、执行、终止待清理、完成。终止原因可以是正常停止、输出上限、取消、超时或错误。资源则可能仍处于设备使用中、传输中、共享引用中或可回收。

以下是一个可实现的职责分工，具体状态名可不同：

| 模块 | 结束时的责任 |
|---|---|
| 入口与路由 | 识别请求标识，传播取消或截止时间，返回终止原因 |
| 调度器 | 不再安排后续工作，处理已提交计划的结果 |
| 执行器 | 报告最后使用完成，避免提交失效输出 |
| 状态管理器 | 解除请求引用，等待在途使用结束后回收 |
| 输出通道 | 处理已发送与未发送内容，关闭流并释放缓冲 |

## 一次取消发生在提交之后

假设 GPU 正在执行请求 A，CPU 收到取消。正确处理不是立即把 A 的 KV 块分给 B，而是先将 A 标记为不再调度，等待最后使用该块的操作完成，再解除引用。

如果 A 的前缀与其他请求共享，解除 A 的引用后，块仍可能保留。若存在 KV 复制，传输任务也可能持有引用。重复收到取消应保持幂等，不能重复释放。

取消确认的语义应明确：已接受取消、已停止新增工作、所有资源已清理，是三个不同里程碑。

## 超时与背压

截止时间可以影响准入和排序。发现任务已经无法在剩余时间内完成时，服务可按策略拒绝或结束，但预测存在误差，不能把估计称为硬实时证明。

慢客户端会让输出缓冲增长。可以限制缓冲、暂停生成或终止连接；不同策略对 KV 占用和其他请求公平性不同。无界缓存会把网络慢变成内存问题。

服务端超时与客户端断开也可能不同步。需要主动传播结束信号，而不是一直计算到输出上限。

## 失败恢复是否能继续原请求

恢复至少要考虑模型版本、已计算状态、已提交 token、采样随机数状态和语法状态。只有 KV 存在，并不代表可以完全恢复同一生成过程。

若无法保证继续执行的语义，可返回明确错误，让调用者选择重试。已经输出的部分文本不能在未知边界下与一次新生成拼接。

对于跨节点传输，应区分“发送成功”“接收完整”“已安装可用”“所有权已移交”。中途失败时，各方按请求和传输标识清理，而不是仅依赖连接关闭。

## 模型和适配器也有生命周期

模型实例退出前需停止新请求并处理在途工作。适配器缓存、编译图和 KV 前缀都可能依赖其身份；卸载时要么保留可恢复的版本关系，要么使相关条目失效。

滚动升级可让旧请求在旧实例完成，新请求进入新实例。是否保留旧缓存应由兼容条件决定，不能仅按模型显示名称匹配。

## 用故障注入验证不变量

适合验证的事件包括：排队时取消、执行中取消、传输中断、重复取消、客户端停止读取、模型退出与请求完成同时发生。

检查结果应包括无重复输出、无越界读写、无引用泄漏、无已释放状态被复用，以及明确的结束原因。性能测试之外，这些条件决定服务是否可靠。
