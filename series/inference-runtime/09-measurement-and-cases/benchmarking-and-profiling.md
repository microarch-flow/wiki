# 压测、统计与性能定位

上级：[本专题导读](README.md)

压测回答“在指定负载与服务规则下，系统表现怎样”。Profiling 回答“时间和资源花在哪里”。两者需要互相校验，单个内核峰值不能替代服务验收。

## 先固定可复现的工作点

记录模型与分词器修订、量化产物、软件与驱动、硬件拓扑、并行布局、内核后端、调度预算、缓存与解码功能。生成参数和输出长度规则也属于配置。

负载至少包含输入长度、输出长度、到达过程、共享前缀、模型／适配器分布，以及取消或失败处理。只保留平均长度会丢失长尾和相关性。

质量检查与性能配置应对应。例如更短输出、更强截断或改变接受策略可能提高 token/s，却改变任务本身。

## 闭环与开环压测回答不同问题

闭环保持固定并发：一个请求结束后才补下一个。服务变慢时，到达速率会随之降低，适合观察指定并发下的稳定工作点。

开环按预定到达时间发送请求，例如回放 Trace 或生成随机到达。即使前一个请求未完成，下一个也按计划到达，更适合观察过载与排队。

压测客户端自身也可能排队。应记录计划发送时间、实际发送时间和完成时间；否则客户端被阻塞后减少施压，可能掩盖系统本应出现的等待。

## 冷启动、热缓存与稳态分开

模型首次加载、首次编译／捕获、冷前缀和热前缀对应不同条件。预热可以排除启动成本，但报告必须说明排除了什么。

缓存实验需控制输入顺序和复用范围。比较两种实现时，不能让一侧热缓存、另一侧冷缓存，除非这正是要比较的部署场景。

固定测量窗口、预热期、结束排空规则，并记录窗口外请求如何处理。稳态指标与整场作业指标可以同时报告，但不能混合分母。

## 统计结果要能解释失败

至少报告完成、拒绝、超时、取消和错误数，以及输入／输出 token 数。延迟使用[统一指标边界](../01-request-and-metrics/02-metrics-slo.md)，给出分布、样本量和百分位计算方法。

少量样本的 p99 不稳定。可以增加独立重复试验、给出不确定性，并按输入长度或请求类别分组检查。不要只删除最慢请求后报告成功样本均值。

吞吐平台、队列增长与失败率一起观察，才有助于定位可持续负载。一次短暂的峰值输出速率不等于持续可服务能力。

## 从服务问题下钻到执行时间线

| 观察 | 首先核对 | 可能的后续定位 |
|---|---|---|
| TTFT 增大 | 排队与输入处理 | Prefill 形状、缓存命中、接收端等待 |
| ITL 尾部增大 | 请求是否每轮执行、输出是否缓冲 | 分块 Prefill、抢占、通信、主机空隙 |
| 内存峰值增大 | 活跃状态与工作区 | 图池、复制、缓存尾块、适配器 |
| 吞吐不再增长 | 实际完成率与资源忙碌 | 计算、带宽、通信、入口或输出瓶颈 |

这些是排查顺序，不是一一对应的诊断结论。用 Trace 关联请求、批、内核与传输事件，再改变一个因素验证假设。

Profiling 本身会扰动执行，应先获得不启用 profiler 的服务基线，再采集代表性短窗口。

## 最小报告内容与来源

报告应给出配置、输入来源与到达规则、测量边界、错误处理、样本量、资源和请求指标、原始记录位置，以及可复现命令。无法实际运行的配置应标为分析案例。

[NVIDIA AIPerf 指标](https://docs.nvidia.com/aiperf/dev/reference/ai-perf-metrics-reference)用于对照工具口径；[Nsight Systems 文档](https://docs.nvidia.com/nsight-systems/UserGuide/index.html)用于主机、设备和通信时间线。把这些测量接入预测模型的方法见[下一篇](trace-and-event-model.md)。
