# 从 HBM 到计算阵列，一块数据什么时候才算就绪？

<span class="micro-legacy-anchor" id="hbm-到-tile-的数据供给链"></span>

上级：[工作负载与案例](./README.md)

<span class="micro-legacy-anchor" id="这页在回答什么问题"></span>

HBM 控制器已经返回一整块数据，阵列却还没开始算。到底少了哪一步？取一个可以一路认出来的数 **37**：它在 HBM 里属于输入块 0 的行号 3、列号 2。我们让阵列把每个数加 1，再将结果写回 HBM。看见 37 从控制器出来、看见阵列能读 37、看见目标端能读 38，是三个不同的时刻。

## 描述符写的是一块矩阵，控制器收到的是哪些地址？ {#一条典型供给链长什么样}

给这次计算两个彼此独立的分块（tile）。每块是 5 行 × 5 列的 32 位整数，每行有 20 B 有效数据，每块共 100 B，运算不会溢出。运行时选好源和结果地址，给搬入引擎准备一个二维描述符。块 0 的源基址是 `0x1000`，相邻两行的起点相隔 64 B；搬到片上以后，每行紧接前一行，行距只有 20 B。结果也按 20 B 行距紧密写到另一段 HBM，块 0 的结果基址取 `0x8000`。块 1 使用各自独立的地址。行、列都从 0 编号。

只跟踪 37。DMA 从源行首再加两个元素的偏移，算出 **0x1000 + 3 × 64 + 2 × 4 = 0x10C8**。片上应当写入的偏移却是 **3 × 20 + 2 × 4 = 68 B**。这两个数一个用来找源，另一个要和读请求一起记下来，以便数据回来时写对位置。真正发出的请求可能按对齐、突发长度或地址边界进一步拆开。先回来的片段仍按自己的目标偏移落位。[按行生成地址](../03-dma-microarchitecture/multidimensional-stride-dma.md) · [后发的读请求先返回时怎样落位](../03-dma-microarchitecture/scheduling-outstanding.md)

## 同一个 37，在 HBM 和片上 SRAM 各要等谁？ {#为什么这条链常常是哪里都像瓶颈}

先把这组地址投到一个**教学用的 DRAM 映射**上。假设这里的源地址都落在同一 bank，行宽取 256 B，`0x1000` 对齐行首。控制器开始前该 bank 没有打开行，按源行顺序服务，并保持刚打开的行。前四行有效字节的起点相对基址为 0、64、128、192，都在同一个 DRAM 行。等读到偏移 200 的 37，控制器可以沿用已打开的行发列读；第五行从偏移 256 开始，会切到下一行。这里的矩阵行由软件布局决定，DRAM 行由地址映射决定。具体 HBM 的行宽、通道交错、调度和时序要按目标器件确定。[存储系列的源端行状态与目的 bank 对照](../../../storage/01-memory-hierarchy/02-access-paths/sram-vs-dram-access-pattern.md#dma-source-row-destination-bank) · [AMD HBM 控制器的开页与关页读延迟](https://docs.amd.com/r/en-US/pg276-axi-hbm/Performance)

再跟着 37 离开 HBM。假定这台机器先通过片上网络（NoC）把返回片段送到计算簇共享 SRAM 的槽 S0，本地搬运单元再从 S0 送进阵列输入槽 I0。若 S0 基址按 16 B 对齐、SRAM 有四个按 4 B 字交错的 bank，偏移 68 的这个字属于 bank 1，因为 (68 ÷ 4) mod 4 = 1。哪怕 37 已到网络出口，它和另一个请求同时申请 bank 1 唯一的读写端口，也只能先接纳一个。HBM 的行命中可以省一次重新开行，不能替目的端腾出这个端口。[DMA 与本地 SRAM、DDR 和 HBM 的接口](../05-system-integration/dma-and-memory-system.md) · [DMA 与 NoC](../05-system-integration/dma-and-noc.md)

链路会随产品改变。有的加速器让内存读取单元直接填计算缓冲，就少一次簇内搬运。比如 NVDLA v1 的卷积路径里，CDMA 把输入装入卷积缓冲 CBUF，CSC 再组织数据送往乘加单元。下面特意选用 S、I 两层来观察两次交接。[NVDLA v1 卷积流水线](https://nvdla.org/hw/v1/ias/unit_description.html#convolution-buffer) · [AI 加速器里的 DMA](./ai-accelerator-dma.md)

## 37 已经到片上，为什么阵列还要再等一拍？ {#when-input-is-ready}

<span class="micro-legacy-anchor" id="这条链最容易出问题的地方"></span>

把上述路径放在一张时间表里。两个块分别使用簇内中转槽 **S0、S1**，阵列输入槽 **I0、I1** 和结果槽 **O0、O1**。每个槽能放一块。此例约定整块收齐且可见才允许交给下一段；计算等到能独占阵列并获得结果槽才开始。为便于手算，规定传输段各服务一块用 1 拍，计算一块用 2 拍。不同段具有足够的独立端口，HBM 读和写共用的端口单列在首尾。这里从**首个 HBM 读数据服务开始**计时，请求已准备好，假设没有额外开行、方向切换、仲裁或通知等待。表里的 1 拍是整块的服务时间单位。举例说，若仍用上节地址映射，且每个 SRAM bank 每个硬件时钟只写一个 4 B 字，那么四个 bank 每时钟合计最多写 16 B，连续 25 个字即使没有读者争用，也至少需要 7 个硬件时钟。要用下面的表描述这套窄端口实现，可以把服务时间单位选得足够长，并为 S0 的读取和 S1 的写入留足端口时隙；若一拍就是一个硬件时钟，则要用更宽的端口，或重排时间表。

| 观察哪里 | 块 0 | 块 1 |
| --- | --- | --- |
| HBM 控制器服务输入读取 | [0,1) | [1,2) |
| 经过 NoC，整块进入簇 SRAM | [1,2)，到 S0 | [2,3)，到 S1 |
| 本地搬运，整块进入阵列输入槽 | [2,3)，S0 → I0 | [3,4)，S1 → I1 |
| 阵列读取输入，并把结果存入结果槽 | [3,5)，I0 → O0 | [5,7)，I1 → O1 |
| 写回通路把结果送入控制器待写队列 | [5,6)，从 O0 读取 | [7,8)，从 O1 读取 |
| HBM 控制器服务结果写入 | [6,7) | [8,9) |

表中区间左闭右开。**t = 1** 时块 0 的读数据已经离开控制器，37 还要经过 NoC。**t = 2** 时 37 已经在 S0。本设计的阵列从 I0 取数，本地搬运单元此时才开始从 S0 读取。假设它在最后一段才把 37 写到 I0 的偏移 68，早一拍启动阵列就可能读到上一次留下的数。直到 **t = 3**，这一块所有必要字节都已在 I0 对阵列可见，控制器才发出“块 0 输入就绪”。在这之后才允许翻转输入槽的选择。若设计允许阵列按行先行消费，则需要为每一行记录就绪与覆盖条件。

沿块 1 再看一次。**t = 4** 时它已在 I1 完整就绪，但块 0 还占着阵列。它只能到 t = 5 才开始。这里等的是计算资源；这一个空等周期不能记到 HBM 返回延迟上。[搬入、计算、写回如何共用两组缓冲](../../06-task-control/dma-compute-writeback.md)

## 算出了 38，可以立刻覆盖哪些位置？ {#一个系统判断框架}

块 0 在 t = 3 完成本地搬运。本例约定它是 S0 的最后一个读者，此后 S0 就能归还。阵列还要继续读 I0，到 **t = 5** 才读完并释放 I0。此刻 37 已变成 38，保存在 O0 的偏移 68。若此时让后续块覆盖 O0，写回单元接下来可能读到后续块的数。

在表中，写回通路到 **t = 6** 才把 O0 的结果完整复制进能够独立保存它们的待写队列。若接口明确确认所有对 O0 的读取均已结束，t = 6 可释放源槽 O0。队列里的写入还要等待 HBM 服务。这里另行约定写服务在 **t = 7** 完成时，指定的目标消费者才可从 `0x8000 + 68 = 0x8044` 读到 38。若设备只报告整笔写回完成，就等到该通知再归还 O0。若目标消费者是主机 CPU，能否经其缓存读到新值，还应遵从平台的映射和同步约定。[描述符、数据可见与软件回收](../04-programming-model/queues-doorbells-completions.md)

## 每块读写各用一拍，两块为什么到第 9 拍才交完？ {#hbm-shared-service}

<span class="micro-legacy-anchor" id="常见误解"></span>

只盯表中第一行和最后一行。假设同一 HBM 控制器的数据路径**读写合计最多服务 100 B/拍**。本例把每块计算所需的 100 B 输入和产生的 100 B 输出都计在这条路径；忽略突发取整导致的额外传输。单块在这个资源上至少要获得 **(100 + 100) ÷ 100 = 2 拍**的等效服务。两块要经过 400 B，因而至少需要 **4 拍**服务。一个把读和写当独立端口的估算会得到 max(1,1) = 1 拍/块，与这里共享的硬件不符。[存储系列的共享读写带宽预算](../../../storage/01-memory-hierarchy/04-npu-case/on-chip-bandwidth-budget.md#hbm-shared-read-write-budget)

在表里实际找到这四拍：前两拍分别读两块，[6,7) 和 [8,9) 分别写两块。中间 HBM 数据路径有空余，但结果还在计算或去往写队列的路上；只有在合法依赖、空间和发射时序允许时，其他工作才有机会用上这些空档。因此这份日程从首块读数据服务开始到末块结果按约定可用是 **9 拍**。4 拍只约束这个控制器。反过来，若再来一笔输入补货请求也想占用 [6,7)，它就要同块 0 的结果写入争一次服务，写回压力会影响后续输入。从管脚统计真实 HBM 流量时，还得数实际突发、读写转向和其他流量，并使用对应时钟或时间单位。这里的 100 B/拍是教学预算。

## 阵列没开工，先从哪项记录查起？ {#建模启示}

<span class="micro-legacy-anchor" id="一句话理解"></span>

固定那块尚未开工的数据，从阵列往回查。如果阵列尚未获准读 I0，先看三种记录：完整输入有没有到达 I0，结果槽是否仍归上一块，阵列本身有没有空出来。若数据确实没到，沿 I0 的生产者回查。簇 SRAM 的写请求仍在排队，可以查 [bank 和端口争用](../../../storage/01-memory-hierarchy/02-access-paths/sram-vs-dram-access-pattern.md)；回包在 NoC 里等，可以查返回通路是否被大流量占满；若内存端口有空闲，DMA 却等上一笔读返回才发下一笔，则要查发射节奏和在途名额。若所有名额都已用满且老请求长期不返回，就继续查 HBM 的通道映射、行状态和控制器服务。这样可以区分单个慢块的尾延迟、持续断供和计算映射本身造成的空闲。

在事件模型中保留每个块自己的进度，同一时刻可能一块正计算、另一块正补数。保存以下字段时，给 `hbm_fetch` 区分发起与返回，给 `writeback` 区分源读取结束与目标可见。只有看到 `consumer_ready` 才让指定消费者使用数据。

```text
HBMToTilePipeline {
  per_tile_events: hbm_fetch, noc_transit, sram_fill, tile_ready, compute, writeback
  buffer_owner[tile]; dependencies[tile]; resource_queues
}
```

最后回到 37。若只记录一次 `transfer_done`，通常分不出它指 t = 1、2 还是 3，也难以解释阵列为何还在等。[估算长期带宽](../../../storage/01-memory-hierarchy/04-npu-case/on-chip-bandwidth-budget.md)时，每个共享资源要把同一块对它的多次服务需求加起来。只有各段用独立资源、工作能充分重叠且没有重复占用时，才可以用最慢一段的服务时间近似稳态间隔。
