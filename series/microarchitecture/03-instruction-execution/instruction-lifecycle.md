# 一条指令如何从取指走到提交

上级：[指令执行与处理器控制](./README.md)

指令执行不是“译码后算出结果”这一个动作。处理器还要找到操作数、处理等待，并决定结果何时成为程序的正式状态。**执行完成、写回和提交是不同的事件**，即使某个简单实现把它们放在同一拍。

## 从接口职责看流水线

以下按职责划分。它不是所有 CPU 通用的级数，也不规定每项职责耗时一拍。

| 职责 | 输入与状态 | 输出或动作 |
| --- | --- | --- |
| 取指 | 下一条 PC、取指请求及返回状态 | 指令字节与对应 PC；可能含预测路径信息 |
| 译码 | 指令编码 | 操作类型、源与目标标识、立即数、异常信息 |
| 分配与派发 | 队列容量、寄存器映射等 | 为在途操作分配位置；复杂实现可先重命名 |
| 发射与读操作数 | 操作数就绪状态、执行端口能力 | 获准开始的操作及操作数 |
| 执行或访存 | 运算输入、地址、访存权限与响应 | 结果、分支方向或错误状态 |
| 写回 | 已产生的结果 | 更新内部结果存储，并使相关消费者就绪 |
| 提交（retire/commit） | 程序顺序及完成、异常状态 | 确认软件可见状态的更新，允许必要的后续副作用 |

流水寄存器保存阶段之间的状态。队列则容纳可以等待不同时间的操作。一个 cache miss 可以比许多整数操作慢，因此不能把上表机械画成等长的七拍通道。

## 结果已经算出，为什么还不能提交

考虑这段示意指令，寄存器互不依赖：

```text
I0: load r1, [p]
I1: add  r2, r3, r4
```

假设处理器允许乱序执行，并要求精确异常。I0 等待地址翻译或存储响应时，I1 可能先算完并把结果写入物理寄存器。此时内部已经存在 I1 的结果，但 I1 尚不能越过未解决的 I0 提交。

如果 I0 最后报告异常，处理器应暴露对应异常边界的程序状态：更老的指令已完成，I0 及更年轻指令的架构状态修改尚未生效。I1 的投机结果必须被丢弃或变为不可见。否则，异常处理程序看到的状态就无法对应顺序执行到 I0 的位置。

重排序缓冲区（ROB）是一种实现办法：记录在途指令的顺序、完成状态和异常，在队首满足条件时提交。它不是所有处理器必须具备的结构。简单顺序核可用更少状态实现其异常契约。

## Store 的几个“完成”也不能混用

Store 的地址已算出，不等于数据已写进 cache；获准提交，也不等于其他观察者已经看到新值。实现可能在提交后把写入留在 store buffer，再按内存系统规则排出。

例如，[BOOM 的 ROB 文档](https://docs.boom-core.org/en/latest/sections/reorder-buffer.html)说明提交会授权 store 队列把相应写入发送给内存系统。跨核可见顺序、屏障和设备访问仍由 ISA、内存模型与互连契约共同决定。不要把“提交”解释为 DRAM 已更新。

## 错误路径如何退出

分支预测可让处理器在真实方向确定前继续取指。若预测错误，错误路径上尚未提交的操作需要清除；重命名映射、资源占用和下一条取指位置也要恢复。

恢复的目标是软件语义正确。投机执行可能留下 cache 等微架构状态变化，不能据此推断系统没有侧信道。本文只讨论正常执行与精确状态边界，不展开预测器或安全机制设计。

## 一个可观测的检查方法

追踪一条指令时，至少分别记录进入队列、发射、结果就绪、写回和提交。遇到慢指令，再记录阻塞原因：操作数未就绪、单元繁忙、队列满、访存未返回，还是更老指令尚未提交。

要把“何时可以开始执行”落实到具体拍号，可以回看[三条指令的发射日程](./dependencies-bypass-issue.md)。[BOOM 流水线文档](https://docs.boom-core.org/en/latest/sections/intro-overview/boom-pipeline.html)提供一个具体乱序实现的职责划分；本文的 I0/I1 例子用于解释机制，不规定产品时序。
