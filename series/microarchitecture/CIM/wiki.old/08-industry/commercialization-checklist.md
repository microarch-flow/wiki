# 商业化评估清单

## 为什么需要单独一页

CIM 很容易出现“论文指标亮眼，但商业路径不成立”的情况。原因通常不是单一技术点，而是技术、工程、生态和客户需求之间没有闭环。

因此，本页的作用不是判断技术有没有意思，而是判断一条路线有没有机会走到产品和收入。

## 技术维度

- 使用什么 memory technology
- 是 macro、chip、card 还是 system
- 支持什么精度和模型
- 指标是 macro 级还是 system 级

## 工程维度

- 是否需要特殊工艺
- 软件栈是否成熟
- 是否容易接入现有系统
- 良率、可靠性、验证难点是什么

## 商业维度

- 客户是谁
- 场景是否足够刚需
- 相比 GPU / NPU / HBM 的替代优势是什么

## 一套更实用的尽调顺序

### 1. 先判断产品形态

先确认它到底卖什么：

- 一个研究宏
- 一颗芯片
- 一张加速卡
- 一个 memory module
- 一套完整系统

产品形态不同，商业壁垒和集成难度完全不同。

### 2. 再判断它减少了什么成本

不要只看峰值 TOPS/W，而要问：

- 减少的是算力成本还是带宽成本
- 节省的是功耗、面积、带宽，还是 BOM
- 对客户来说，这个节省是否足够痛

### 3. 再判断它是否能接入客户现有栈

需要明确：

- 是否兼容现有模型格式
- 是否需要新的编译器或 runtime
- 是否要求客户改软件、改主板或改内存系统

### 4. 最后判断量产约束

需要看：

- 工艺是否特殊
- 测试校准是否复杂
- 良率与可靠性是否可控
- 客户验证周期是否过长

## 典型高风险信号

- 只展示 `macro-level` 指标，没有 chip 或 system 解释
- 宣称覆盖通用 AI，但没有明确 workload 边界
- 需要复杂工艺，却没有清晰供应链支撑
- 软件栈薄弱，必须人工映射
- 客户价值主张不清楚，只停留在“更省电”

## 典型正面信号

- 明确聚焦一个高痛点场景
- 指标口径清晰，能说明是否包含外围与系统成本
- 有清晰的 host 协同和软件接口
- 技术路线与目标客户需求强匹配
- 已经能从 demo 过渡到可部署产品形态
