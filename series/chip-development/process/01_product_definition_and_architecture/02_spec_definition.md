# 怎样把产品目标写成可验收规格

<span class="micro-legacy-anchor" id="规格定义"></span>

## 前置知识

先明确[工作负载和目标场景](01_market_and_workload_analysis.md)。

## 规格的本质

规格给下游提供同一套边界。设计用它确定功能和接口。验证用它生成判据。软件用它理解可观察行为。硅后团队用它决定怎么测量以及什么结果算通过。

## 规格层次

| 层次 | 要写清楚的内容 |
| --- | --- |
| 产品 | 目标负载、允许输入、性能与功耗测量边界、环境和成本约束 |
| 架构 | 软件可见的能力、地址、数据格式、状态、错误和顺序规则 |
| 微架构 | 接口时序、队列深度、仲裁、背压、资源共享、时钟与复位 |
| 验证与交付 | 判据、覆盖计划、运行条件、版本、负责人和待确认项 |

IEEE、RISC-V、PCI-SIG 或 UCIe 等外部规格有各自的版本与覆盖范围。引用接口标准时，要声明规范版本、启用能力、配置与系统上实际承诺的行为。 [RISC-V 规范](https://riscv.org/specifications/ratified/) · [UCIe 规范](https://www.uciexpress.org/specifications)

## 规格应包含什么

每项要求有可追溯编号，列出触发条件、可接受输入、预期结果和判据。对吞吐或延迟，写明单位、观测区间、负载、并发和时钟。对错误和复位，明确输入是否接收、存量事务如何处理、何时可以重试。未决定的选项记录负责人、依赖和确认期限。

## 关键活动顺序

1. 产品与系统团队固定第一版负载和测量边界。
2. 架构、RTL、软件、验证团队确认接口和无效输入的行为。
3. 物理、封装与测试团队提出可实现的工作条件和可观测限制。
4. 将高风险要求附上一个正常场景和一个边界场景。按版本管理变更。

## 典型场景

**教学假设。** 采用[生命周期的 SRAM＋DMA 算例](../00_overview/01_full_lifecycle.md#典型场景)。本版只支持一个未完成请求。有效事务搬运连续 16 B，目的地址按 4 B 对齐且在指定 SRAM 范围内。

| 要求 | 通过判据 |
| --- | --- |
| DMA-01 接受与写回 | 接收一个合法请求后，目的范围的 16 B 与参考数据一致。检查其他地址保持原值。 |
| DMA-02 完成事件 | 在最后一次成功写响应后产生一次完成事件。控制域确认该事件后，才释放事务槽。检查连续请求和目的时钟异常停顿后的恢复。 |
| DMA-03 复位 | 约定中的复位令在途请求取消，复位期间没有完成事件。重新初始化后软件重新提交。已写入的字节可能保留，软件重新覆盖整个目标范围。 |
| DMA-04 延迟预算 | 若数据源在约定时间响应、SRAM 无背压且两侧时钟处于指定频率范围，按「接收时刻到控制域确认时刻」比较延迟预算。频率、响应上限和预算数值由例题或产品版本给定。 |

带宽、时延的性能预算与功能承诺分别评审。若产品要求任意时长背压，测试不能要求固定完成时限。若要保证最终完成，必须声明下游最终响应等活性前提。

## 角色、时长与交付物

产品或系统负责人维护目标和通过条件。架构、RTL、验证和软件负责人审核各自使用的条款。交付物包括带版本的规格、参考模型、验证映射和未决事项。修改接口、复位或验收条件时，同步更新受影响的实现与测试。
