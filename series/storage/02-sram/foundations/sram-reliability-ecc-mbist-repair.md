# SRAM 可靠性：初始化、ECC、测试与修复

上级：[SRAM 基础](./README.md)

相关：[SRAM 宏接口与读写语义](./sram-macro-interface-and-semantics.md) · [先进工艺与 SRAM](./sram-process-scaling-challenge.md) · [SRAM 漏电与低功耗](./sram-power-leakage-retention.md)

<p class="ram-problem-lede">SRAM 可靠性不仅取决于 cell 是否能保存数据。系统还需要知道数据何时有效、怎样检测和处理错误，以及测试与修复会占用哪些资源。</p>

本文区分数据初始化、运行时纠错、存储测试和冗余修复。各机制覆盖的故障、报告和恢复能力由目标宏及控制器决定；一个机制不能自动替代其他机制。

## 1. 先区分故障与处理机制

| 情况 | 例子 | 可能采用的处理 |
| --- | --- | --- |
| 内容未建立或已丢失 | 上电后的数据与校验位没有形成有效码字，或断电未保持。 | 按设备规定初始化数据和校验位，或重新装载内容。 |
| 内容发生错误 | 某个已保存的 bit 受到扰动而翻转。 | 由受支持的 ECC 检测或纠正，并按规则报告。 |
| 持续性缺陷 | 某单元、地址译码或连线存在持续故障。 | 测试、定位，并在设计支持时使用冗余资源修复。 |
| 工作条件不满足 | 电压、温度或时序超出宏的保证范围。 | 恢复受支持的工作条件；不能只依赖 ECC。 |

同一现象可能有不同原因。ECC 看到错误码字，并不一定能判断故障是瞬态还是永久的；测试结果也有其覆盖范围。

## 2. ECC 能纠正什么？

ECC 将数据与校验位组成受保护的**码字**。读取时，控制器依据码字计算并解释校验结果；具体编码、检查范围和响应取决于实现。例如，支持 SECDED 的设计通常承诺对一个码字中的单 bit 错误进行纠正，并检测两个 bit 错误。对于三个或更多错误，不能沿用这个保证；某些模式可能被误判甚至误纠正。

假设一组数据和对应校验位已正确初始化，之后同一受保护码字只有一个物理 bit 翻转，且该实现支持读取时纠正：读取可以返回纠正后的数据，并按设备规则报告错误。但**输出被纠正不等于阵列中的错误位必然已改写**。另一种实现可能提供回写纠正，或由软件处理；应查目标控制器的行为。

如果同一 SECDED 码字中有两个错误，按该编码和设备支持的保证可检测到不可纠正错误。若两个错误分别位于不同码字，则每个码字可能各自满足单 bit 纠正条件。实际处理仍要核对中断、错误地址、返回数据、异常和后续恢复规则。[TI 的 TMSx70 ECC 说明](https://www.ti.com/lit/an/spna126/spna126.pdf)描述了该系列的 SECDED、初始化和错误报告。

Scrubbing 是一种可选的后台检查与修复策略：定期读取受保护区域，检查后在实现允许时将纠正结果写回。它可以缩短错误在阵列中累积的时间，但会消耗端口、带宽和能量，还需处理与正常写入的并发。检查频率和覆盖范围应由可靠性目标与具体实现决定；并非所有 SRAM 都支持硬件 scrub。

## 3. 初始化为什么要覆盖数据与校验位？

上电、未保持的断电或其他使内容失效的操作之后，数据位和校验位可能不匹配。对这样的码字执行 ECC 检查，可能报告错误，即使软件还没有有意写入数据。

一个典型的系统流程是：确认供电和控制器可用；按设备规定的方式初始化受保护区域，使数据和校验位匹配；等待初始化完成；再允许依赖这些内容的访问。ECC 开关与初始化的具体先后顺序依赖设备，不能套用统一流程。[TI 的初始化说明](https://www.ti.com/lit/an/spna126/spna126.pdf)给出了软件与硬件两种设备特定方法。

部分写入还要检查 ECC 粒度。若控制器必须先读取完整码字、合并部分数据并重算校验位，未初始化的旧码字可能在读改写时触发错误。以 [TMS470M eSRAM 手册](https://www.ti.com/lit/ug/spnu495c/spnu495c.pdf)为例，该器件启用 64-bit ECC 时，小于该粒度的写入涉及读改写。并发更新还需要覆盖整个实际读改写粒度的保护，见 [SRAM 宏接口](./sram-macro-interface-and-semantics.md)。

退出保持模式时，也要确认数据和校验位是否均被保持，以及何时允许访问。若只恢复供电而内容没有保证，就需要重新初始化或装载。

## 4. MBIST 与冗余修复

Memory Built-In Self-Test（MBIST）通过控制测试访问并比较结果，检查设计所覆盖的存储故障。可检测的故障类型、测试模式、测试时间以及是否报告失败地址，都由具体实现决定。测试若改写受检区域，会破坏原有内容；运行前需要安排停机、保存和恢复，或在启动时、软件使用该区域之前运行。

[Microchip PIC32CM JH00/JH01 的应用说明](https://ww1.microchip.com/downloads/aemDocuments/documents/MCU32/ApplicationNotes/ApplicationNotes/AN4480-PIC32CM-JH00-JH01-High-Level-Usage-of-MBIST-and-ECC-with-Fault-Injection-DS00004480.pdf)给出了设备实例：其 SRAM 自测试会清除内容，应在启动时、变量和栈进入受测 SRAM 之前执行，而且不提供失败 bit 的数量和位置。测试通过说明所执行测试没有发现其覆盖范围内的故障，不等于证明所有工作条件下永不出错。

若设计提供备用行或列，制造测试或其他受支持的修复流程可以使用冗余资源替代部分有缺陷的位置。可修复的数量、位置组合和映射方式受电路限制；没有足够冗余或超出可修复范围时仍可能失败。MBIST、故障定位和修复可以配合，但具备其中一项不自动意味着具备另外两项。

## 5. 从机制到系统契约

一次设计检查可以按下面顺序进行：

1. 确认保护对象、码字大小、可纠正和可检测的错误范围，以及数据与校验位的开销。
2. 确认上电、复位和低功耗退出后的内容有效性与初始化顺序。
3. 确认单错和多错的返回值、错误报告、异常与恢复；核实纠正是否写回。
4. 确认测试和修复的触发条件、覆盖范围、时间、内容破坏及可用冗余。
5. 确认 ECC、读改写、scrub 和测试对正常访问的仲裁、等待和能耗影响。

## 一句话理解

初始化建立有效内容；ECC 在其保证范围内检查和处理码字错误；MBIST 与冗余修复针对受覆盖的故障提供测试和处理手段。

## 建模启示

只研究无错误时的吞吐，可以在声明已初始化且无故障后省略错误事件。研究可靠性、启动时间或服务干扰时，应记录有效状态、错误粒度、报告与恢复、测试占用，以及 scrub 或读改写对共享端口的影响。故障率和覆盖率必须来自目标条件下的证据，不能从容量或 ECC 名称直接推断。
