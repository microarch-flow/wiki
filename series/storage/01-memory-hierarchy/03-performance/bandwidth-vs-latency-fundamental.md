# 带宽与延迟：从单次响应到持续吞吐

<span id="带宽与延迟两个不同的目标"></span>

上级：[存储层级与数据路径](../README.md)

相关：[峰值与有效带宽](./effective-bandwidth-vs-peak.md) · [速度·容量·成本·功耗](../01-system-basics/memory-hierarchy-tension.md) · [Cache miss 的处理](../02-access-paths/cache-dram-coordination.md)

## 这页在回答什么问题

一条路径的带宽提高后，单次读取一定更快吗？一次读取延迟很低，是否意味着它能持续提供足够的数据？

本文区分请求的响应时间和指定接口上的字节率，再看请求并发、排队和传输粒度如何影响两者。它们可以同时改善，也可能在给定资源预算下形成取舍。

## 带宽、单次延迟与排队

### 延迟要从哪里量到哪里？

**延迟**是指定起点到指定终点的时间。描述一次读取时，常见的事件有：

| 事件 | 含义 |
| --- | --- |
| 请求发出 | 发起方提出读取；请求可能还在等待接纳。 |
| 请求接纳 | 被观察的接口接受该请求。 |
| 所需的第一部分数据可用 | 消费者取得继续执行所需的第一部分数据。 |
| 请求的数据全部返回 | 该请求所需的最后一部分数据到达所选观察点。 |
| 消费者可以继续 | 数据、权限或同步条件按系统约定满足后，消费者开始下一步。 |

例如，从**请求发出到第一部分数据可用**，与从**请求发出到全部数据返回**，是两个不同的延迟。某些处理器可以在所需字返回后继续执行，即使一整条 cache line 尚未填充完成；另一些路径可能要求等待更多数据或同步事件。

起点也很重要。从发出开始计时会包含接纳前等待；从接纳开始计时则不会。比较结果时，还要统一时钟单位、请求大小、地址和负载条件。

### 带宽要在哪个接口、哪个窗口统计？

**窗口平均带宽**是指定接口上，在指定时间窗口内传输的字节数除以窗口长度。例如，一个接口在 100 ns 内传了 1,000 B，该窗口的平均传输带宽是 10 GB/s。这里 1 GB = 10⁹ B。

传输方向和字节口径同样重要。读取与写入可以分别统计；若要合计，必须说明共享或独立接口。被传输的 payload、任务实际使用的数据，以及处理器发出的逻辑读取量，也未必相同。如何比较接口峰值、实际传输与有用字节，见[峰值与有效带宽](./effective-bandwidth-vs-peak.md)。

短窗口内的平均值可以高低波动；**持续带宽**通常指在所说明的负载和较长稳定窗口下得到的字节率。接口峰值是能力上界，不等于任意工作负载都能达到的持续带宽。

### 首次返回与全部完成

假设一次 8 B 读取在时刻 0 发出；在所选接口上，第一组 4 B 在时刻 10 返回，第二组 4 B 在时刻 11 返回。两组数据连续传输，时刻单位是同一个时钟周期：

| 观察终点 | 从发出到该终点 |
| --- | ---: |
| 第一组 4 B 返回 | 10 cycle |
| 全部 8 B 返回 | 11 cycle |

在这个例子中，第一组数据到达时，部分传输已经完成。若把“启动延迟”定义为发出到第一组返回的 10 cycle，再加上完整 8 B 的传输时间 2 cycle，就把第一组的传输重复计入了。

另一种简单模型把启动时间定义为**请求发出到数据开始传输**的时间。假设随后以固定速率连续传输，没有排队、中断或额外尾部开销，且数据量可以整除每周期传输量：

<div class="ram-calculation">
  <span>全部数据完成时间 = 传输开始前的时间 + 数据量 / 传输速率</span>
</div>

这只是定义清楚边界后的理想模型。实际请求还可能等待仲裁，传输也可能被切分、暂停或与其他工作重叠；不能把公式直接当作所有请求的端到端时间。

### 请求并发为什么会影响带宽？

如果下一笔读取的地址依赖上一笔返回，发起方可能只有很少的请求在途。即使接口很宽，它也可能因缺少可服务请求而空闲。相反，多笔独立请求可以在满足端口、bank 和下游资源约束时部分重叠。

在稳定状态下，若在途数量、完成率和延迟使用**同一请求边界**，平均在途请求数等于平均完成率乘以平均请求停留时间。这是 [Little 定律](https://pubsonline.informs.org/doi/10.1287/opre.9.3.383)在该边界上的应用。

若每笔请求都返回相同的 q 字节，且平均停留时间为 W，达到目标字节率所需的平均在途数量可按下面的关系估计：

<div class="ram-calculation">
  <span>平均在途请求数 = 请求完成率 × 平均停留时间</span>
  <span>平均字节率 = 请求完成率 × q</span>
</div>

这不是性能保证。可用跟踪项、请求依赖、地址分布和共享路径都可能限制并发；增加并发也可能增加排队，使 W 改变。完整的 64 B 请求、100 cycle 延迟算例见[存储系统为何难设计](../01-system-basics/problem-statement.md#请求并发如何影响带宽)。

## 两种指标怎样同时变化？

考虑一个构造比较：两条路径使用相同的时钟周期和观察边界。近端多 bank scratchpad 的首组数据延迟为 1 cycle，持续服务能力为 64 B/cycle；远端路径分别为 50 cycle 和 16 B/cycle。假设请求足够独立、地址分布均匀，没有端口和返回通路冲突，且两条路径都能在测试窗口达到各自的持续能力。

在这些条件下，近端路径的首组延迟和持续带宽都更好。它仍可能有更严格的容量、面积或功率约束。数值只是教学假设，不是 SRAM 或 DRAM 的通用参数。

增加并行资源可能提高吞吐，也可能在共享仲裁、布线或功率预算上引入代价。例如，控制器集中服务一批写请求可能减少读写方向切换；但某些写可能先等待积累，某些读也可能在写排空期间等待。实际影响取决于请求流和调度策略。

同一路径的延迟也会随负载变化。排队增加时，带宽可能先上升，而请求响应时间同时变长；在其他条件下，两者也可能一起改善。[Intel Memory Latency Checker](https://www.intel.com/content/www/us/en/download/736633/intel-memory-latency-checker-intel-mlc.html)提供了观察不同负载下内存延迟和带宽的具体工具。它的结果适用于所测系统和配置。

## 一句话理解

延迟描述一次请求在指定起点和终点之间经历的时间；带宽描述指定边界和窗口内的字节率。请求依赖、并发、排队和传输粒度会影响两者，不能只用其中一个推断另一个。

## 建模启示

先确定要解释的现象，再选择需要保留的信息：

| 问题 | 需要定义或观察什么 |
| --- | --- |
| 单次读取何时能继续？ | 请求发出、接纳、所需数据可用和消费者可继续的事件。 |
| 持续吞吐为何不足？ | 请求大小、在途数量、完成率、服务能力及共享资源。 |
| 高负载时为何变慢？ | 同一边界的延迟分布、队列占用、完成率和负载条件。 |
| 大块传输耗时如何估算？ | 数据何时开始传输、速率是否持续、是否有尾部和未重叠阶段。 |

如果只需要固定条件下的粗略估算，可以使用经过校准且注明边界的延迟和带宽。若要比较并发上限、排队或 bank 映射，模型还需要保留对应状态。观察尾延迟时，应同时记录窗口末尚未完成的请求，避免漏掉仍在等待的长请求。
