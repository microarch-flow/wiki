# 带宽与延迟：两个不同的目标

上级：[存储层级与数据路径](../README.md)
相关：[峰值带宽 vs 有效带宽：损失发生在哪里](./effective-bandwidth-vs-peak.md), [速度、容量、成本、功耗四角矛盾的根源](../01-system-basics/memory-hierarchy-tension.md)

## 这页在回答什么问题

为什么高带宽和低延迟是不同指标；在什么资源与工作负载条件下，两者可以同时改善，或需要权衡。首字延迟、末字延迟和持续字节率需要各自定义端点与统计窗口。

## 带宽、单次延迟与排队

“带宽”和“延迟”几乎是所有存储讨论里最常被同时提到的两个词，但它们也是最常被混成一个概念的两个词。很多人会自然地觉得：带宽高一点，数据不就更快来了吗；延迟低一点，系统不就更能跑满了吗。这个直觉只在非常浅的层面上部分成立。更准确地说，带宽和延迟虽然都描述“数据到达”的效率，但它们关心的是两种完全不同的系统问题。

`Latency` 回答的是：当我现在发起一次请求，第一份我真正需要的数据要多久才能到。它更像“启动等待时间”或“单次事务首字节时间”。`Bandwidth` 回答的是：在一段足够长的时间窗口里，这条路径平均每秒能稳定搬多少数据。它更像“持续输送能力”或“吞吐上限”。这两者当然有关，但并不等价。一个系统完全可能第一份数据来得很慢，但一旦管道灌满后吞吐极高；也可能首字节来得很快，但总线很窄、并行度很低，长期吞吐并不高。

这组差异在存储层次里尤其尖锐。近端寄存器、L1 或 scratchpad 常具低延迟，实际持续带宽取决于端口、bank、频率与访问模式，而非容量大小。外层 DRAM/HBM 可提供大容量和高带宽，路径及共享状态通常更多。延迟和带宽使用不同单位，也可由同一资源同时提供。

可以用一个直观类比帮助理解：延迟更像“第一桶水多久能从水龙头出来”，带宽更像“水龙头一分钟最多能稳定出多少水”。你可以把阀门开得很大，让一分钟总水量极高，但管路长、预压大时，第一桶水仍然可能要等；也可以把一小截很近的细管放在手边，第一口水来得极快，但长时间总流量远不如大主管。这个类比只适合抓“首字节时间 vs 持续流量”的差别，具体到存储系统还是要回到资源路径和并行度。

两项指标有时受资源预算约束。第一层原因是 `距离`。这就像便利店和大型仓储超市的区别——便利店就在楼下，你一分钟就能拿到一瓶水（低延迟），但它的货架面积决定了它不可能每小时给你供应一吨货物（低带宽）；大型仓储超市有巨大的仓库和多条结算通道（高带宽），但你得开车 20 分钟才能到（高延迟）。低延迟通常要求数据离计算近、路径短、状态简单，最好不跨太多层控制和共享资源；高带宽则往往要求更多并行 lane、更宽总线、更深预取、更多 bank/channel，甚至接受更复杂的分层组织。距离一长、资源一共享，首访问的控制开销和排队概率就会上升，延迟自然更难低。换句话说，把路径做得更“粗”和更“宽”，通常有利于总吞吐；把路径做得更“短”和更“直”，通常有利于首访问时间。

第二层原因是 `并行度与突发性`。高带宽几乎总要借助某种形式的并行：多 bank、多 channel、burst、pipeline、wide I/O。可这些机制真正释放价值时，往往要求访问流本身足够大、足够连续、足够可重排，能把资源灌满。若只有一笔小请求，很多并行结构根本派不上用场，反而只留下前置控制成本。就像一条八车道高速公路——它的设计吞吐量极大，但如果你只有一辆车要上路，这八条车道对你毫无意义，你感受到的只是上高速时漫长的匝道和收费站。也就是说，高带宽资源通常最适合“已经有很多数据要搬”的场景，而不是“只想立刻拿到一点数据”的场景。延迟敏感请求反而更希望看到的是少排队、少分层、少共享，而不是复杂的高吞吐 machinery。

第三层原因是 `资源共享方式`。高带宽层往往是共享资源：多个 core、多条 DMA、多组 NPU tile、多个 GPU 单元都会去抢同一套主存接口。共享能提高整体利用率，却也让单请求更难获得稳定、确定的首访问时间。低延迟层则更倾向于局部专有或小范围共享，虽然总容量小，但资源争用少、行为更可控。因此，减少共享可降低排队；并行资源也可提高吞吐。两者是否冲突要看面积、功率、端口与访问形状。

第四层原因是 `工作粒度`。高带宽往往围绕 cache line、burst、tile 甚至更大块数据来组织，要求一次搬很多，才能把每次 activate、burst、turnaround 或 DMA setup 的固定成本摊掉。低延迟则更在乎单次请求的固定成本能不能被压低，即使搬的数据不多也要尽快开始返回。因此，很多高带宽设计会主动提高一次事务的粒度，而这反过来会让“小而急”的请求显得更不合算。

可以用下表比较可能的设计侧重点；这些代价不是必然结果：

| 目标 | 系统更偏好的东西 | 常见代价 |
| --- | --- | --- |
| 低延迟 | 近距离、低争用、少状态切换 | 若限制端口和面积，容量或带宽可能受限 |
| 高带宽 | 多 bank/端口、宽接口、可重叠服务 | 额外面积和功耗；共享或排队可能增加延迟 |

这里最容易犯的错误，是拿一个 workload 的痛点去误解另一个 workload 的目标。CPU 控制流、指针追踪、锁竞争和中断路径往往更怕延迟，因为它们在等某个很小但关键的数据；GPU 渲染、NPU 张量搬运和大规模流式计算往往更怕带宽不够，因为它们需要稳定喂饱大吞吐阵列。你如果拿 CPU 的眼镜看 HBM，会觉得“首访问还是不够快”；拿 GPU 的眼镜看 TCM，会觉得“容量和持续吞吐太弱”。这并不说明哪一层设计错了，而是说明它们本来就不是为同一类痛点而生。

现代系统常以层次化满足不同容量、成本和访问需求。近端 SRAM/寄存器可同时提供低延迟与高聚合带宽，外层 DRAM/HBM 提供更大容量；各层的实际性能取决于组织及工作负载。固定容量、面积和功率预算后，才可比较哪些实现能同时改善两项指标，哪些存在取舍。

带宽与延迟的张力还会直接决定控制器与协议设计。controller 若为了提高 row-hit-rate 和总线利用率，可能会让某些单请求多等几拍；write drain 为了减少总线方向切换，也是在牺牲部分单写请求延迟来换取整体带宽；多 channel、NUMA 和 HBM 也常常是在换更高总吞吐的同时，把路径拉长或把一致性/拓扑复杂性做大。也就是说，前面所有“为什么这样设计”的答案，很多都能在这里重新汇总成“这是在偏向带宽，还是在偏向延迟”。

所以，这一页真正要建立的结论不是一句抽象口号，而是一种判断方式：当你看到某个内存设计很“强”时，先问它强在首访问时间，还是强在持续吞吐；再问它是通过减少共享、缩短距离做到的，还是通过扩大并行、增加突发和加深流水做到的。只有把这两层区分清楚，你才不会再把“带宽高”误认为“延迟也一定低”，或者把“延迟低”误认为“吞吐自然够大”。

例如近端多 bank scratchpad 同时提供 1 拍首字延迟与每拍 64 B 的聚合服务，而假设远端接口为 50 拍和每拍 16 B；在对应地址均匀且端口无冲突的条件下，近端两项都更好。它仍可能受容量和面积约束。请求完成延迟还包括最后一字节、排队和传输时间；与首字延迟应分别定义端点。

## 一句话理解

延迟描述指定起点到首字或末字的时间，带宽描述指定边界上的持续字节率。两者可以同时改善，也可能在给定资源预算下形成取舍，应分别测量。

## 建模启示

在模型里，带宽和延迟绝不能被压成同一个参数。最少应该把 `startup_latency` 和 `sustained_throughput` 分开表示，并允许同一资源在这两个维度上呈现完全不同的排序。否则模型会天然高估“高带宽资源对延迟敏感流”的价值，或高估“低延迟资源对流式 workload”的价值。

一个最小可用的抽象可以写成：

```text
MemoryPathCapability {
  startup_latency_cycles: int
  sustained_bw_bytes_per_cycle: int
  max_outstanding_reqs: int
  burst_granularity_bytes: int
}
```

然后对同一条访问路径至少区分两类成本：

```text
single_small_req_cost  ~= startup_latency
large_stream_cost      ~= startup_latency + bytes / sustained_bw
```

如果只关心 very-short control accesses，`startup_latency` 的权重远高于 `sustained_bw`；如果关心大张量搬运或大数组扫描，则反过来。把这两个量分开之后，后面很多系统判断就会自动变得更清楚：为什么 HBM 对 GPU/NPU 很值钱，但对某些控制流并不等价于“更快”；为什么 TCM/寄存器对实时路径很关键，却不解决大容量流式搬运问题。
