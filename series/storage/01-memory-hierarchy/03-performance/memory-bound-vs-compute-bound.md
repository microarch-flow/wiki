## 这页在回答什么问题

计算单元没有达到峰值时，限制来自外存、片上数据路径、计算依赖，还是同步？增加一项资源后性能没有变化，又能说明什么？

本文先用工作量和资源能力计算吞吐上界，再说明怎样结合实际流量、等待和对照实验定位瓶颈。方法适用于不同计算系统；NPU 的多层数据路径作为一个案例。

## 计算与数据供应的性能上界

假设观察同一任务的完整执行窗口，窗口长度为 T。任务完成 O 次所定义的操作，并在第 i 个数据边界上传输 Qᵢ 字节。计算资源的能力上界为 P op/cycle，该边界的传输能力上界为 Bᵢ B/cycle。所有上界与统计值都采用同一时间单位，并覆盖窗口内的工作。

每项资源都不能在窗口内完成超过其能力上界的工作，因此：

<div class="ram-calculation">
  <span>T ≥ O / P</span>
  <span>T ≥ Qᵢ / Bᵢ</span>
  <span>吞吐 O / T ≤ min（P，所有 Bᵢ × O / Qᵢ）</span>
</div>

最后一行只对 Qᵢ > 0 的边界计算；Qᵢ = 0 表示此工作量在该边界没有统计到传输，该项不提供带宽约束。这里还假设 T、O、P、Bᵢ 均为正且有定义；若数据在窗口之前已预取，不能把窗口外的传输误计成窗口内完成的流量。

这些不等式给出**上界**。它们不要求计算和传输完全重叠；充分重叠关系到能否接近上界。如果计算、数据准备和同步不能重叠，实际时间可能更长。依赖、排队、启动和其他资源也可能让实际吞吐远低于上界。

P 与 O 的操作口径必须一致。例如，若把一次乘加计为 2 op，计算能力也应使用同一口径；数据类型、精度和所用计算单元也要对应。Qᵢ 与 Bᵢ 同样要对齐接口、方向和统计窗口；共享读写接口与独立读写通路不能无条件使用同一个合计方式。

当 Bᵢ 是协议或实现的绝对能力上限时，上述不等式是该条件下的约束。如果使用某个微基准测得的持续带宽，它只是该测试配置和流量下的参考值，不一定是所有访问模式的严格物理上限。

[Roofline 原始论文](https://www2.eecs.berkeley.edu/Pubs/TechRpts/2008/Archive/EECS-2008-134.pdf)以操作数、经过 cache 层次后的 DRAM 流量和带宽建立上界，并讨论了其他缓存层作为观察边界的情况。[NVIDIA Nsight Compute](https://docs.nvidia.com/nsight-compute/NsightCompute/index.html#rooflines)也提供多层 Roofline 的具体工具实例。

### Memory bound vs compute bound：上界与实测

对某个边界，O / Qᵢ 常称为该边界的操作强度；若统计的是算术操作，也常称为算术强度。换一个边界，字节数可能改变，强度也可能改变。一个 Roofline 图中的较低上界，只说明**在该模型和口径下，哪项能力更先约束理想吞吐**。

看一个构造例子：

- 计算能力上界 P = 100 op/cycle；某接口带宽上界 B = 10 B/cycle。
- 同一任务完成 O = 400 op，在该接口传输 Q = 100 B；窗口包含全部操作和传输。
- 接口对应的吞吐上界为 10 × 400 / 100 = 40 op/cycle，低于计算上界 100 op/cycle。
- 假设某种执行存在一条至少需要 80 cycle 的串行依赖；数据传输和其他工作能够在这段时间内完成。

在这些假设下，任务用 80 cycle 完成，实际吞吐是 5 op/cycle；接口平均流量是 1.25 B/cycle。若接口能力增加到 20 B/cycle，但依赖链和其他条件保持不变，完成时间仍受这条 80 cycle 依赖链约束。

因此，带宽上界较低，不足以证明当前实现已经被该接口的带宽饱和限制。限制也可能是访问延迟、可并发请求数、计算依赖或同步。这个例子只说明一种可能性，不代表所有低利用率任务都有同一原因。

## 怎样定位实际限制？

先固定任务、输入、正确结果、执行范围和时间窗口，再收集证据。下表中的现象是线索，右列是可尝试的检查，不是仅凭一个计数器就能得到的结论。

| 可能的限制 | 可观察的线索与下一步 |
| --- | --- |
| 某边界持续传输能力 | 按相同口径比较实际流量与适用的带宽参考；检查接口忙碌情况，并在可控条件下改变该路径能力或所需流量。 |
| 访问延迟或并发不足 | 检查依赖链、平均在途请求数、完成率和响应时间；尝试增加独立工作，同时记录流量和排队是否改变。 |
| 片上分发、bank 或端口 | 检查各 bank、端口和链路的请求分布、等待及返回路径；比较不同布局或资源配置。 |
| 计算执行或计算依赖 | 检查有效操作、指令发射、计算单元使用和依赖；比较可展开并行度或计算能力变化。 |
| 同步、阶段切换或控制 | 看任务时间线、首尾阶段、屏障与等待条件，判断能否重叠或缩短关键路径。 |

计算单元利用率低并不自动证明数据带宽不足。相反，即使外存平均带宽不高，串行访问仍可能因每次等待数据而受内存访问延迟限制。对于实际 GPU，性能计数器的定义还受架构和工具约束；[NVIDIA 的性能诊断指南](https://docs.nvidia.com/nsight-compute/ComputeTriage/#symptom-dram-throughput-is-below-peak-with-no-other-limiter-saturated)给出了检查在途数据和并行度的具体示例。

### 用 NPU 数据路径进一步定位

以一个 NPU tile 为例，即使外存供数足够，数据仍可能在片上网络、共享 SRAM 的 bank、局部端口或结果回收路径等待。反过来，如果这些路径足够，外存的持续供数或下一 tile 的准备也可能限制执行。

部分和可以留在 PE 寄存器中，也可以经过局部 buffer；只有实际跨越某个边界的流量才计入该边界。不同角色共享同一资源时，还需要考虑同时到达和仲裁。逐边界计算 weight、activation 和 psum 需求的例子见 [NPU 片上带宽预算](../04-npu-case/on-chip-bandwidth-budget.md)；搬运与计算何时能重叠见[激活缓冲与双缓冲](../04-npu-case/activation-buffer-and-double-buffering.md)。

更大的片上 buffer 可能让数据驻留更久，从而减少外存读取；如果当前数据没有可利用的复用，或更大的容量没有改变调度和流量，也可能没有收益。是否有效需要比较同一任务的实际跨边界字节和运行时间。

## 一句话理解

资源能力与逐边界流量给出性能上界；实际瓶颈需要结合执行时间、资源使用、依赖和对照实验定位。瓶颈随工作负载、映射、数据放置和资源配置变化，不是任务永久不变的标签。

## 建模启示

模型可以记录各资源的请求、接纳、完成、占用和等待原因，再按目标问题汇总。但同一周期内，外存未完成、片上网络阻塞和 bank 冲突可能同时存在；不同 PE 也可能处于不同状态。

若要把空闲或 stall 分成互斥类别，应明确观察对象、时间分母和原因优先级。例如，单个 PE 的周期占比与整个阵列的 PE-cycle 占比不是同一口径。保留可重叠的原始状态，有助于解释互斥汇总；无论采用哪种分类，计数本身都不等于消除该原因后可获得的加速。

做敏感性实验时，可分别改变外存能力、片上链路、bank 组织或计算能力，并记录实际运行时间、操作数、各边界字节、等待和频率。改变 bank 数或 tile 也可能改变映射、流量与并行度；若这些量随之改变，应一起解释，不能只把结果归因于参数名称。仿真结果只能支持所建机制和所验证条件下的结论。
