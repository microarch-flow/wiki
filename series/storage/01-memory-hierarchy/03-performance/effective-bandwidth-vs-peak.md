# 峰值、实际与有效带宽：如何定位差距

## 这页在回答什么问题

规格书给出接口峰值带宽。运行任务时，接口实际传输了多少字节，其中多少对任务有用？如果结果低于峰值，应怎样区分接口空闲、无用传输和上游供数不足？

回答这些问题之前，必须统一接口、方向、时间窗口和字节口径。“有效带宽”在不同工具和资料中可能有不同定义，不能只凭名称比较。

## 峰值带宽 vs 有效带宽：先统一口径

| 指标 | 本文采用的含义 | 需要注意 |
| --- | --- | --- |
| 接口峰值带宽 | 选定接口在理想连续数据传输下的 payload 字节率上界。 | 写清通道、方向、位宽、传输速率，以及是否计入校验位。 |
| 接口实际传输带宽 | 该接口在窗口内实际传输的 payload 字节数除以窗口时间。 | 包含实际传出的、但任务可能没有使用的字节。 |
| 接口有用传输带宽 | 上述实际传输字节中，按约定判为任务有用的部分除以窗口时间。 | 有用字节是本次接口传输字节的子集；判定范围和重复传输的口径要写清。 |
| 任务逻辑有效带宽 | 按任务的逻辑读取和写入字节数除以任务时间。 | 它描述任务侧工作量；缓存命中、复用或压缩可能使其不同于外存接口流量。 |

计算接口峰值时，可用每秒传输次数乘以每次传输的 payload 字节数。例如，假设一个接口每秒传输 3.2×10⁹ 次，每次传输 8 B payload，单方向连续传输的峰值为 25.6 GB/s。若规格已经给出每秒传输次数，不应因为 DDR 在双沿传输而再乘一次 2。多通道能否直接相加，还要看通道是否独立、方向及统计边界。

[NVIDIA CUDA Best Practices Guide](https://docs.nvidia.com/cuda/archive/13.2.0/cuda-c-best-practices-guide/index.html#bandwidth)区分了按 kernel 请求计算的有效带宽、实际内存吞吐和 DRAM 吞吐。它是一个具体平台的指标实例；其他工具的计数位置和名称应查看各自定义。

### 同一接口的传输与有用字节

先固定一个数据接口和 100 ns 窗口。假设该接口的 payload 峰值为 100 GB/s；传输期间每个时隙都以该速率传输，窗口内传输时长为 50 ns。其余时间没有 payload 传输。

假设传出的 5,000 B 中，有 4,000 B 按本次任务和观察窗口的规则被判为有用。这里每个有用字节都属于这 5,000 B；不把本地重复使用产生的额外逻辑读取算进去。

| 统计量 | 计算 | 结果 |
| --- | --- | ---: |
| 接口实际传输量 | 100 GB/s × 50 ns | 5,000 B |
| 接口实际传输带宽 | 5,000 B / 100 ns | 50 GB/s |
| 接口有用传输带宽 | 4,000 B / 100 ns | 40 GB/s |
| 已传 payload 中的有用比例 | 4,000 B / 5,000 B | 80% |

因此，在本例的条件下，有用传输带宽与峰值之比为 50% × 80% = 40%。这个乘法依赖两个条件：忙碌时以所定义的峰值传输；有用字节是**同一接口、同一窗口**已传 payload 的子集。若部分 beat 无效、使用写掩码或峰值口径包含额外位，需要按实际有效位和协议重新计算。

窗口内没有 payload 时，有用比例的分母为零，不能计算该比例。若有用性取决于窗口之后是否使用，还要延长观察范围或明确暂未确认的字节如何计数。

### 任务逻辑字节可以大于外存传输字节

假设在 100 ns 内，DRAM 接口传入 1,000 B，数据随后在片上被读取 16 次；片上路径有足够能力完成这些读取。如果任务统计每次逻辑读取，则任务读取量为 16,000 B，对应 160 GB/s；DRAM 实际传入 1,000 B，对应 10 GB/s。

即使 DRAM 的峰值是 100 GB/s，任务侧的 160 GB/s 也不表示 DRAM 超出峰值。两者统计不同边界的字节。反过来，cache line 填充或固定 burst 也可能让外存传输大于任务当前请求的字节。进一步算例见[局部性与数据搬运](../01-system-basics/locality-working-set-data-movement.md)。

## 协议与访问形状造成的带宽损失

下面从 DRAM 数据接口的视角列出可能原因。它们可以同时出现；某一项数值高并不单独证明它决定了任务时间。

| 现象 | 可以进一步检查什么 |
| --- | --- |
| 同 bank 的行切换频繁 | 地址映射、打开行、page policy 与候选请求；其他 bank 能否在切行期间供数。 |
| 小请求导致多余传输 | 请求与 cache line、控制器事务和 DRAM burst 的大小；是否合并、拆分或过取。 |
| 读写切换占用时间 | 读写混合比例、总线 turnaround、写缓冲与排空策略。 |
| 刷新与普通请求竞争 | 器件支持的刷新范围、时序、到达时点，以及是否存在其他可服务资源。 |
| bank 或 channel 热点 | 地址分布、实际并发、共享数据通路和其他瓶颈。 |
| 接口没有足够可服务请求 | 上游依赖、在途上限、DMA 提交、互连背压及下游接收能力。 |

请求大小、片上互连 burst 和 DRAM burst 不一定相同。增加上游请求长度也不意味着可以任意增加 DRAM burst 长度。例如，[AMD Versal 控制器资料](https://docs.amd.com/r/en-US/pg313-network-on-chip/Memory-Controller-Feature-Summary)说明了其 DDR4 配置使用固定 BL8、LPDDR4 配置使用固定 BL16。具体拆分、合并和器件规则应按目标系统检查。

行切换或刷新可能使某个 bank 暂时无法服务，但其他 bank 仍可能传输数据；因此不能把所有 bank 的忙碌时间相加，当成共享数据接口的空闲时间。地址映射和调度的细节见 [DRAM 地址映射](../../04-dram-controller/address-mapping-channel-rank-bank-row-col.md)与[命令调度](../../04-dram-controller/command-scheduling-fr-fcfs.md)。

### 时间记账不是因果证明

继续使用前面的 100 ns 构造窗口。假设 50 ns 有 payload 传输；对于其余 50 ns，观察者预先规定了互斥的分类优先级：

| 数据接口空闲时间的记账类别 | 时间 |
| --- | ---: |
| 行状态相关等待 | 15 ns |
| 读写方向切换 | 10 ns |
| 刷新相关等待 | 5 ns |
| 没有可用请求 | 20 ns |
| 合计 | 50 ns |

这个分区假设每个空闲时间片只记入一个类别，即使多个条件同时成立。它可以避免把 50 ns 空闲时间重复相加，但分类结果依赖所选优先级。例如，一段时间内行等待和刷新条件同时成立时，换一种优先级可能改变两项数字。

因此，记到“行状态相关等待”的 15 ns 不等于消除行等待就一定能节省 15 ns。其他条件可能仍会阻塞服务。应先查看原始状态，再在控制其余条件的前提下比较地址映射、请求流或调度策略的变化。

## 一句话理解

先在同一接口、方向和时间窗口内区分峰值、实际传输字节和有用字节；再结合请求供给、器件状态和共享资源定位差距。跨层的任务逻辑字节不能直接当作该接口的传输字节。

## 建模启示

记录峰值和窗口起止时，还应按问题保留：

1. **数据账**：每个接口、方向的实际 payload 字节，以及有用字节的判定规则；必要时另记任务逻辑字节。
2. **时间账**：数据接口忙闲区间、请求到达与接纳，以及 bank、刷新和方向状态。先允许原始原因重叠，再按所声明的规则做互斥汇总。
3. **验证账**：固定工作量、配置和统计边界，记录修改前后的流量、等待及任务时间。改变映射或分块也可能改变流量，不能只比较一个计数器。

粗粒度模型可以使用在固定条件下测得的带宽，但若要比较行策略、请求粒度或上游并发，就需要保留能区分这些变化的机制。计数与归因的粒度由要回答的问题决定。
