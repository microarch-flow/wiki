# 局部性、工作集与数据搬运：存储层次如何发挥作用

上级：[系统视角](./README.md)

相关：[存储系统为何难设计](./problem-statement.md) · [Cache 与 scratchpad](../02-access-paths/cache-vs-scratchpad.md) · [存储层次与系统角色](memory-hierarchy-as-system.md)

同一套存储系统，面对不同的访问序列，可能产生不同的数据搬运量。原因不仅是存储器的容量和速度不同，还包括数据何时被再次使用、相邻数据是否一起使用，以及数据在使用之间能否留在本地。

本文先比较 cache line 的空间局部性，再用工作集冲突和 scratchpad 数据复用说明数据能否留在本地，以及跨层流量如何变化。

## 1. 什么是局部性？

局部性描述的是一段时间或一串访问中，访问地址之间的关系。它不是某块 SRAM 或 DRAM 固有的性能参数。

- **时间局部性**：访问某个位置后，在相对较近的未来再次访问同一位置。例如，多次读取同一个权重。若数据在这段时间内未改变，后续访问可能复用先前取得的值。
- **空间局部性**：访问某个位置后，在相对较近的未来访问邻近位置。例如，依次读取数组中的相邻元素。如果系统按块搬运数据，后续访问可能使用已经带回的相邻数据。

“相对较近”要结合具体系统理解。如果复用发生前，数据已经被替换或覆盖，本次复用就不能由原来的本地副本满足。同样，地址相邻不保证一定落在同一个 cache line，也不保证一定来自同一个 DRAM bank。

两种局部性可以同时存在，也可以分别存在。例如，一次顺序遍历数组可以利用空间局部性，但如果每个元素只访问一次，就没有对该元素的时间复用。反过来，反复访问一个变量有时间局部性，但不要求访问它的相邻变量。

[MIT 的计算机结构资料](https://ocw.mit.edu/courses/6-004-computation-structures-spring-2009/8aab78cf087999514dd6e0b73c6ab43e_MIT6_004s09_study_digital_guide.pdf)用 cache block 说明空间局部性的收益，也指出较大的 block 可能带来额外数据搬运和冲突。具体收益仍取决于访问序列和 cache 组织。

## 2. Cache line 粒度为什么影响下一级流量？

考虑一组假设的读请求：

- cache 初始为空，每条 cache line 为 64 B；起始地址按 64 B 对齐。
- 处理器依次发出 16 次读取，每次读取 4 B；一笔读取完成后再发下一笔。
- 每次 miss 都从下一级填充完整的 64 B cache line；例子中不发生预取、其他请求干扰或提前替换。
- 只统计**从下一级进入该 cache 的读取数据**，不统计命令、元数据和其他路径上的流量。

在这些条件下，比较两种地址序列：

| 访问方式 | 读取位置 | miss / hit | 下一级填充流量 |
| --- | --- | --- | --- |
| 相邻访问 | 同一条 line 内的 16 个相邻 4 B 数据 | 1 次 miss，15 次 hit | `1 × 64 B = 64 B` |
| 分散访问 | 每次读取都位于不同的 line | 16 次 miss，0 次 hit | `16 × 64 B = 1,024 B` |

两组请求都向处理器提供了 64 B 请求数据。在相邻访问中，第一次 miss 带回的相邻数据被后续请求使用。在分散访问中，每条 line 只使用了 4 B，其余字节没有被这组请求使用。

因此，**请求的数据量相同，不代表跨越 cache 与下一级之间的流量相同**。这也是为什么比较流量时，要同时说明请求大小和传输粒度。

这个例子不能推导出两组请求的执行时间相差 16 倍。实际结果还受并发、排队、下一级命中、数据通道和具体填充机制影响。真实系统也可能有预取、请求合并或不同的填充粒度，需要按目标实现重新统计。

## 3. 工作集与容量有什么关系？

工作集用于描述一个观察区间内涉及的数据集合。这里采用一个便于手算的口径：**在指定的连续访问区间内，统计访问过的不同 cache line**。如果改用字节、对象或其他时间窗口，得到的工作集可能不同。

工作集与容量的关系可以帮助判断数据是否有机会留在某一层，但仅比较总大小还不够。数据能否保留，也取决于映射、相联度、替换策略和其他访问。

例如，假设 cache 容量为 4 条 line，采用直接映射；line 编号对 4 取余，结果相同的 line 映射到同一个位置。cache 初始为空，不考虑预取和其他访问。依次读取 line `0、4、0、4`：

| 访问 | 映射位置 | 结果 |
| --- | --- | --- |
| line 0 | 位置 0 | miss，装入 line 0 |
| line 4 | 位置 0 | miss，替换 line 0 |
| line 0 | 位置 0 | miss，替换 line 4 |
| line 4 | 位置 0 | miss，替换 line 0 |

这段序列的工作集只有 2 条 line，小于 4 条 line 的总容量，但四次访问仍全部 miss。前两次是首次装入；后两次在这个例子中由映射冲突导致。若改成可同时容纳这两条 line 的全相联 cache，并保持其他假设不变，则前两次 miss、后两次 hit。

因此，“工作集放得下”是有利于复用的条件，不是命中率保证。反过来，某个长时间窗口内的工作集大于容量，也不代表所有访问都会 miss；其中一部分数据仍可能在被替换前得到复用。

[AMD 的系统性能分析文档](https://docs.amd.com/r/2024.2-English/ug1145-sdk-system-performance/Evaluating-Memory-Hierarchy-and-the-ACP)在特定 Zynq 系统上改变工作集大小和访问方式，观察到不同的延迟和带宽。其数值只适用于文档中的测试配置，不能作为其他系统的通用参数。

## 4. Scratchpad 如何通过显式安排复用数据？

Cache 通常由硬件判断是否命中，并管理填充和替换。Scratchpad 则通常需要软件、编译器或硬件调度机制明确安排数据何时进入、何时被使用，以及何时可以覆盖。两者都可以利用复用，但管理责任不同。

假设一个 NPU 需要顺序执行 8 次计算，每次都要读取相同的 1,024 B 权重。权重在这 8 次计算期间不变；scratchpad 有足够的可用空间保留权重和同时需要驻留的其他数据。比较两种调度：

1. **重复搬运**：每次计算前，都把这 1,024 B 从外存搬入 scratchpad；计算读取完成后，允许下一次搬运覆盖该区域。
2. **保留并复用**：先搬入一次；确认数据可供计算使用后，让 8 次计算都读取该副本；全部消费完成后才允许覆盖。

假设每次搬运都实际跨越所观察的外存读取边界，且没有压缩、其他 cache 命中或额外传输。只统计这块权重的有效数据：

| 统计对象 | 重复搬运 | 保留并复用 |
| --- | ---: | ---: |
| 外存向片上读取的权重 | `8 × 1,024 B = 8,192 B` | `1 × 1,024 B = 1,024 B` |
| 写入 scratchpad 的权重 | 8,192 B | 1,024 B |
| 计算从 scratchpad 读取的权重 | 8,192 B | 8,192 B |

保留副本减少了例子中的外存读取和 scratchpad 写入，但没有减少计算侧读取权重的字节数。activation、输出、命令和同步流量不在表中。即使外存流量减少，也不能单凭这些数值断言计算时间会缩短 8 倍：计算、片上端口、bank 冲突或其他共享资源可能成为限制。

正确性有两个必要条件：**搬运完成并满足可见性要求后才能消费；所有相关消费者使用完毕后才能覆盖**。具体事件和同步机制由目标系统定义。[NVIDIA 的 CUDA 编程指南](https://docs.nvidia.com/cuda/archive/13.1.0/cuda-programming-guide/02-basics/writing-cuda-kernels.html)将 GPU shared memory 描述为一种由使用者管理的 scratchpad，并说明线程之间需要按实际数据依赖同步；这只是一个具体平台的例子，不代表所有 NPU 使用相同接口。

Scratchpad 的价值也不只来自重复使用。即使数据只使用一次，先搬入本地仍可能用于满足接口、布局或调度要求；是否值得这样做，要同时计算搬运代价和可实现的重叠。

## 5. 局部性好，为什么仍可能没有加速？

局部性描述观察范围内的访问序列。数据布局会影响地址序列；映射、可用容量和保留时间决定系统能否利用这些访问关系。最终性能还取决于资源和执行过程。

| 情况 | 需要进一步检查什么 |
| --- | --- |
| 数据在复用前被替换或覆盖 | 有效容量、映射、替换策略，以及其他数据的驻留时间。 |
| 搬回了很多没有使用的数据 | cache line、burst 或 tile 的大小，以及请求对齐和实际使用范围。 |
| 外存流量减少，但本地访问仍排队 | scratchpad 的端口数、bank 映射、仲裁和其他请求。 |
| 数据搬运减少，但可并行工作也减少 | 计算并行度、可同时发出的请求数，以及不同资源之间的依赖。 |
| 搬运和计算理论上可以重叠 | 是否有独立资源、足够的缓冲空间，以及正确的完成和覆盖顺序。 |

例如，两个 tile 复用同一块权重，可能减少外存读取；但如果它们同时争用同一个 SRAM bank，计算仍可能等待。是否加速，要看整条路径和观察窗口，不能只看一个计数器。

## 6. 对建模和测量有什么启示？

先确定问题，再选择要保留的信息。若要比较两种数据放置或调度，至少应明确检查以下内容是否会改变结论：

| 项目 | 需要定义的内容 |
| --- | --- |
| 请求序列 | 地址或数据块、大小、读写类型、发起者、到达时间，以及必要的数据依赖。 |
| 本地存储 | 有效容量、数据放置或替换规则、传输粒度；研究冲突时还需要端口和 bank 规则。 |
| 搬运与同步 | 源、目的地、搬运完成和可见时点，以及数据何时允许被覆盖。 |
| 流量与时间 | 在哪个接口、哪个方向、哪个时间窗口计数字节；请求何时接纳、响应何时可见。 |

例如，在某一接口观察到 `B` 字节有效数据，并且观察窗口为 `T` 秒，则该窗口的平均有效带宽是 `B / T`。比较两个方案时，应对齐接口、方向、计数内容和窗口。跨不同层次的流量应分别记录；不能把同一笔数据在不同接口的计数直接当成同一接口上的流量。

Cache miss 次数也不自动等于 DRAM 请求数。其他 cache 可能满足请求，多个请求可能被合并，预取或写回也可能增加流量。如果模型只保留固定命中率，它可以用于特定条件下的粗略估算，但不能独立预测访问顺序、映射或替换策略变化后的命中行为。
