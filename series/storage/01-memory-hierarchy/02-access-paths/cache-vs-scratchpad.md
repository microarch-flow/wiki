# Cache 与 scratchpad：数据放置、访问路径与管理代价

<span id="cache-与-scratchpad数据放置和访问时间"></span>

上级：[存储层级与数据路径](../README.md)

相关：[存储层次与系统角色](../01-system-basics/memory-hierarchy-as-system.md) · [Cache 与 DRAM 协同](./cache-dram-coordination.md) · [Cache 的 tag 与 data](../../02-sram/applications/cache-sram-tag-data-arrays.md)

计算单元需要的数据，可能先从较远的存储搬到本地。Cache 和 scratchpad 都能提供本地数据，但它们采用不同的放置和访问方式：前者通常由硬件管理副本，后者通常由软件、编译器或显式调度机制安排数据。

本文比较数据怎样进入本地、何时能被使用，以及各自需要处理哪些代价。它们是系统角色，不规定唯一的存储技术；cache 数据阵列和片上 scratchpad 都常用 SRAM 实现。

## 两种数据管理方式

| 问题 | Cache 与 scratchpad 的常见做法 |
| --- | --- |
| 谁决定放什么？ | Cache 按硬件策略填充和替换；scratchpad 的使用方安排本地数据的位置和生命周期。 |
| 怎样访问？ | Cache 根据请求地址及状态查找；scratchpad 按分配好的本地地址或区域访问。 |
| 数据不在本地时怎么办？ | Cache miss 可触发向下一级的请求；scratchpad 需要由软件或其他调度机制安排写入或搬运。 |
| 什么时候可以覆盖？ | Cache 按替换和写入策略处理；scratchpad 需要在相关消费者使用完成后才能安全复用区域。 |
| 有什么额外责任？ | Cache 需要命中判断和副本管理；scratchpad 的使用方需要管理容量、搬运和同步。 |

Cache 的按需填充由实际请求触发。预取可以预测未来访问，但不是每次填充都依赖预测。Scratchpad 的显式放置也不要求一定使用 DMA：计算线程、复制指令或其他硬件机制都可能参与，具体方式由系统定义。

[NVIDIA 的 CUDA 编程指南](https://docs.nvidia.com/cuda/archive/13.2.1/cuda-programming-guide/02-basics/writing-cuda-kernels.html)把其 GPU 的 shared memory 描述为使用者管理的 scratchpad，并介绍了线程间同步与 bank 冲突。它说明了一种具体的编程和硬件组织方式。

## 一次读取如何发生？

**Cache 路径：**请求到达后，cache 用地址和当前状态判断是否能服务。命中时，按接口规则返回数据；未命中时，可能登记缺失请求并向下一级请求数据。若需要替换已有的脏数据，某些实现还要安排写回。下一级可以是另一层 cache 或内存，具体填充和响应顺序取决于实现。完整的 miss、请求合并和写回过程见 [Cache 与 DRAM 协同](./cache-dram-coordination.md)。

**Scratchpad 路径：**使用方先为数据安排本地区域，再通过适用的写入或搬运方式准备数据。搬运完成并满足可见性要求后，计算单元按本地地址读取。所有相关消费者使用完毕后，该区域才能按系统约定被覆盖；如果结果需要交给其他参与方，还要安排写出及同步。

两条路径的关键区别是**管理责任**。Cache 的使用方通常不需要为每条 line 安排填充；scratchpad 的使用方可以控制放置和复用，但也要保证容量、搬运和数据依赖都安排正确。

## 同一份数据，等待为什么可能不同？

假设计算单元将在周期 10 请求一份 4 B 数据。它位于一个 64 B 数据块中，开始时本地没有该数据。源数据从周期 6 起保持不变，scratchpad 已有足够的可用空间。

假设从下一级搬运完整的 64 B 需要 4 个周期，数据到达后本地读取再用 1 个周期。比较两种安排：

- **按需 cache 填充**：周期 10 请求 miss，立即启动填充；周期 14 完整数据块到达，周期 15 返回本次读取。这里假设 miss 判断不额外占用时间，且完整填充后才开始本地读取。
- **提前放入 scratchpad**：周期 6 启动搬运；周期 10 数据到达并满足可见性条件，随后开始本地读取，周期 11 返回。

两种安排都在所观察的下一级到本地边界上传输 **64 B**。第二种安排把搬运放在了计算请求之前，因此减少了本次请求发出后的等待。它需要提前知道数据需求、预留空间，并保证搬运与消费的先后关系。

这不是 scratchpad 固有的延迟优势：如果 cache 的预取在周期 6 启动并在周期 10 前完成，也可能达到类似结果；如果 scratchpad 到周期 10 才开始搬运，也需要等待。是否能重叠还取决于请求依赖、共享带宽和同步开销。

## 同时访问的反例

位置已知不等于整笔访问的耗时固定。假设 scratchpad 的一个 bank 只有一个读端口，每周期接纳一笔请求，接纳后一周期返回。请求 A 和 B 在周期 0 同时到达该 bank；仲裁选择 A：

1. 周期 0 接纳 A，B 等待。
2. 周期 1 返回 A，同时接纳 B。
3. 周期 2 返回 B。

即使两个地址和数据位置都已知，B 仍会等待。若它们分别落到能够独立服务的 bank，且返回通路也支持并行，结果可能不同。

Cache 也不是本质随机。若初始状态、地址序列、替换与仲裁规则和事件顺序均已知，确定性的实现可以被确定性地复现。两者的实际响应时间都可能受端口、bank、仲裁和其他请求影响。

## 写入与数据生命周期

Cache 写入可以采用不同策略。例如，write-through 会按实现策略将写入传播到下一级；write-back cache 可以先更新本地副本，并在需要时写回脏数据。写入何时对其他参与方可见，还取决于系统的一致性与同步约定。[MIT 的计算机结构课程](https://ocw.mit.edu/courses/6-004/computation-structures-spring-2017/pages/c14/c14s1/)介绍了 cache 命中、替换及 write-back 的基本过程。

Scratchpad 的本地写入不会自动等同于更新外部副本。若后续消费者在本地之外，使用方需要按系统接口安排结果写出，并确认对方何时可以看到它。若多个参与方共享同一块数据，还要明确使用权和同步顺序；具体例子见 [DMA 同步与一致性](../../../microarchitecture/DMA/wiki/04-programming-model/synchronization-errors.md)。

## 硬件、软件与性能代价

Cache 需要用于查找和管理副本的结构，例如 tag、命中判断和替换状态。具体写入策略、一致性机制、端口和阵列组织由实现决定。Scratchpad 通常不需要同样的自动替换路径，但仍需要地址译码、访问控制和资源仲裁等结构。面积和能耗要在相同容量、端口、工艺及工作条件下比较，不能只凭角色名称下结论。

在访问模式难以提前确定的场合，cache 可以透明地响应按需访问；scratchpad 则要求使用方规划数据何时进入、保留和离开。当数据依赖和复用方式可提前安排时，显式管理有助于控制搬运和数据生命周期，但软件或调度机制也要承担这些工作。

比较性能时，应分别观察本地命中或读取时间、跨层流量、搬运完成时间和共享资源等待。以 cache 的平均访问时间为例：若 `H` 是命中访问的平均完整延迟，`M` 是未命中访问的平均完整延迟，`m` 是 miss 比例，且它们采用相同的请求与响应边界，则平均访问延迟为 `(1 − m) × H + m × M`。令增量 miss penalty `P = M − H`，也可以写成 `H + m × P`。

这个平均值描述单次访问的平均响应时间，不能反映完整的延迟分布，也不能直接相加为程序停顿时间：多笔请求及计算可能重叠。跨层流量、工作集和复用的计数方法见[局部性与数据搬运](../01-system-basics/locality-working-set-data-movement.md)。

## 建模启示

先确定要解释的问题，再选择模型需要保留的状态：

- **Cache**：研究命中和替换时，记录地址流、初始状态、映射及替换规则；研究 miss 并发时，还需考虑缺失请求的跟踪和共享路径。
- **Scratchpad**：记录有效容量、数据放置、搬运发起与完成、可见性和可覆盖时间；研究冲突时，还需保留 bank、端口与仲裁规则。
- **共同资源**：按需要表示请求的到达、接纳与完成时间，以及两者与其他请求共享的链路、端口或下一级存储。

若只在固定条件下做粗略估算，可以使用有适用范围的平均参数；若问题是改变地址映射、调度或数据放置后的影响，就需要保留能区分这些变化的状态和规则。
