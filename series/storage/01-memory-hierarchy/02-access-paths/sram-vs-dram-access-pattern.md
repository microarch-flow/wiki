相关：[SRAM 与 DRAM 的分化](../01-system-basics/sram-dram-divergence.md) · [局部性与数据搬运](../01-system-basics/locality-working-set-data-movement.md) · [地址映射](../../04-dram-controller/address-mapping-channel-rank-bank-row-col.md)

一段程序读取了多少字节，并不能说明这些请求能多快完成。同一组地址可能分散到多个 bank，也可能集中争用一个端口；在 DRAM 中，它们还可能反复切换同一个 bank 的打开行。这些 SRAM 与 DRAM 访问模式的差异，需要结合请求到达时间、映射和资源状态来分析。

本文不再比较两种存储单元的电路。我们从**请求流经过地址映射之后，需要哪些资源和状态**出发，解释访问模式怎样影响服务过程。以下 SRAM 指常见片上分 bank 存储，DRAM 指具有行状态和命令时序约束的常见组织；具体规则由目标实现决定。

## 1. 先看请求到达哪一层

程序中的一次读取，不一定在每一层都产生一笔同样大小的读取。Cache 可以满足、合并或扩大请求；DMA 可以把一个大块传输拆成多笔事务。因此，讨论访问模式时，先确定观察边界：是计算单元到本地 SRAM，还是内存控制器到 DRAM？

在选定边界后，至少需要知道请求的地址、大小、读写方向、到达时间和依赖。只保留地址顺序，会丢失“同时争用”与“先后访问”的区别。

| 同一请求需要回答的问题 | 常见 SRAM 组织 | 常见 DRAM 组织 |
| --- | --- | --- |
| 地址落在哪里？ | bank、bank 内位置及所需端口。 | channel、rank、bank、row、column。 |
| 何时可以开始？ | 目标 bank、兼容端口及必要共享通路允许接纳时。 | 行状态允许，并满足相关命令时序及共享通道条件时。 |
| 前面的访问留下什么？ | 未完成请求、资源占用和队列状态。 | 除资源占用外，还有打开行及命令历史约束。 |

SRAM 并非没有历史影响：前面的请求可以占用端口、堵住返回路径，或使资源处于唤醒过程。关键区别是，常见 SRAM 接口不需要按 DRAM 的开行、关行协议组织下一次访问。

## 2. SRAM：地址步长怎样变成 bank 冲突？

考虑一个**用于手算的假设模型**：4 个独立 bank，每个 bank 每周期最多接纳一笔 4 B 读请求；4 笔读取同时到达，访问不同的字，无合并或广播。字编号为 w，按 **bank = w mod 4** 映射。各 bank 和返回通路都能独立工作，没有其他请求。

若字编号为 0、1、2、3，四笔请求分别落到四个 bank，可以在一个周期内全部接纳。若字编号为 0、4、8、12，四笔都落到 bank 0，需要四个接纳时间槽。两组都读取 16 B，但第二组无法使用另外三个空闲 bank。地址到 bank 的完整推导见 [SRAM bank 地址映射与冲突](../../02-sram/foundations/sram-bank-address-mapping-conflicts.md)。

**接纳时间槽不是完整读取延迟。**继续看第二组，假设 bank 0 每周期都能接纳一笔，按 A、B、C、D 的顺序仲裁；每笔读取在接纳后恰好两个周期返回。返回通路有足够能力，没有其他阻塞。下表中的时间是时钟边沿编号：

| 请求 | 到达 → 接纳 → 返回 | 从到达到返回 |
| --- | --- | ---: |
| A | 0 → 0 → 2 | 2 个周期 |
| B | 0 → 1 → 3 | 3 个周期 |
| C | 0 → 2 → 4 | 4 个周期 |
| D | 0 → 3 → 5 | 5 个周期 |

四笔请求分别在时刻 0、1、2、3 接纳；最后一笔在时刻 5 返回。请求 D 的等待包括接纳前的 3 个周期和接纳后的 2 个周期。若请求分时到达、bank 接纳间隔不同，或返回通路受阻，结果也会改变。

[NVIDIA CUDA 13.1 编程指南](https://docs.nvidia.com/cuda/archive/13.1.0/cuda-programming-guide/02-basics/writing-cuda-kernels.html#shared-memory-bank-conflicts)给出了具体 shared memory 的矩阵转置例子：行列访问的步长不同，可以产生不同的 bank 冲突；填充布局可以改变这种映射。该平台的 bank 数量和广播规则不能直接套到任意 SRAM 宏。

## 3. DRAM：同一组请求，为什么顺序也重要？

DRAM 地址映射决定请求落在哪个 bank 和哪一行。控制器处理请求时，还要看该 bank 当前打开哪一行。打开行的后续列访问可以复用已有状态；若需要同一 bank 的另一行，则必须满足关闭旧行、打开新行的条件。[CMU 的 DRAM 延迟研究](https://users.ece.cmu.edu/~omutlu/pub/understanding-latency-variation-in-DRAM-chips_sigmetrics16.pdf)说明了激活、感测恢复与预充过程；器件原理见[SRAM 与 DRAM 的分化](../01-system-basics/sram-dram-divergence.md)。

以下名称描述请求目标与当前 bank 状态的关系。“row miss”在不同资料中有时也包括行冲突；本表将两种未命中状态分开：

| bank 当前状态 | 本文名称 | 为本次读取准备行状态的主要动作 |
| --- | --- | --- |
| 目标行已打开 | row hit | 不需要为该次访问另开行，可在满足条件后发列读取。 |
| 没有打开的行 | row miss（关闭行） | 激活目标行，再在满足条件后发列读取。 |
| 打开了其他行 | row conflict（行冲突） | 关闭并预充旧行，激活目标行，再在满足条件后发列读取。 |

表中概括的是常见命令路径，不表示列命令可以立即发出。具体命令还受先前操作、自动预充、刷新和器件时序约束。

再用一个**构造例子**比较顺序，不给出周期数：

- 4 个独立读取均落在同一 bank。A、B 位于行 R0；C、D 位于行 R1。
- bank 初始已预充。访问后保留打开行，直到需要切换到另一行。
- 不考虑其他请求、刷新、自动预充和返回通路冲突；所有操作仍须满足目标器件时序。
- 只统计这 4 笔读取所需的开行和中途关行，不计最后一次访问后的关行。

| 服务顺序 | 依次需要的行 | ACT 次数 | 中途 PRE 次数 |
| --- | --- | ---: | ---: |
| A → C → B → D | R0 → R1 → R0 → R1 | 4 | 3 |
| A → B → C → D | R0 → R0 → R1 → R1 | 2 | 1 |

两种顺序都执行 4 次列读取，但第二种减少了行切换。这说明“读同样的数据”不保证“执行同样的命令”。如果 C、D 改映射到另一个 bank，则两个 bank 可以分别保持自己的打开行，竞争关系又会改变。

减少命令不等于执行时间按相同比例缩短。不同 bank 可以部分重叠工作，但仍可能共享命令或数据通道；行命中也可能在队列中等待。实际控制器是否可以重排请求，还受请求是否已到达、数据依赖、顺序要求、公平性和 QoS 约束。不能为了提高行命中率就任意改变程序语义。

若要给这个 DRAM 例子计算时间，还必须指定到达时点、控制器调度、器件模式和时序。例如，ACT 到列命令、PRE 到下一次 ACT 都可能有最短间隔；ACT 和先前的读取也会分别约束 PRE 的最早时点。列命令之后不等于数据立即返回。这些约束可能重叠。不能只把 ACT 和 PRE 的数量乘以固定时间，就当成请求延迟。具体参考边沿及模式条件见 [DRAM 时序参数](../../03-dram/protocols/timing-parameters-trcd-trp-tras.md)。

行策略会改变这个例子的条件。例如，关闭页策略可能在访问后关闭行，不能直接沿用表中的计数。具体策略见 [Open、close、adaptive page policy](../../04-dram-controller/page-policy-open-close-adaptive.md)。

## 4. 连续地址不等于连续使用同一资源

“顺序访问更好”只是待验证的假设。连续地址经过映射后，可能依次占用同一行的不同列，也可能交错分布到不同 bank 或 channel。哪种方式有利，取决于请求并发、行复用、共享总线和调度。

反过来，不连续地址也不必然低效。它们可能分散到可并行的 bank；多笔独立请求也可能隐藏一部分等待。若程序存在指针依赖，下一笔请求必须等上一笔返回，则相同的地址集合可能无法形成这种并发。

调整布局或调度时，应同时检查两端：

- **在本地 SRAM 端**：计算侧并发访问是否集中到同一 bank？填充或分块是否减少冲突，却增加了容量占用？
- **在外层 DRAM 端**：搬运请求的对齐、粒度和映射是否合理？是否形成热点，或者在同一 bank 的不同行间来回切换？
- **在两端之间**：减少某端的冲突，是否增加了传输字节、重排缓冲或同步等待？

Cache、scratchpad 和 DMA 可以改变下游请求的粒度或到达时间，但不能保证所有访问都变得有利。先统计它们实际产生的请求，再评价存储层的行为。数据放置责任见 [Cache 与 scratchpad](./cache-vs-scratchpad.md)，而不是在这里再次比较两者优劣。

## 一句话理解

先把地址映射到资源，再看请求何时到达、能否并行。常见 SRAM 需要重点检查 bank 与端口竞争；常见 DRAM 还需要保留行状态和命令时序。不能只按“连续”或“随机”给请求贴上快慢标签。

## 建模启示

为了比较访问模式变化，模型至少要能区分导致差异的状态：

| 要回答的问题 | 需要保留的信息 |
| --- | --- |
| 改步长是否造成 SRAM 冲突？ | 字节地址与请求大小、bank 映射、每周期接纳能力、并发到达及仲裁规则。 |
| 重排是否减少 DRAM 行切换？ | 地址映射、初始行状态、请求依赖、调度和行策略，以及命令时序。 |
| 吞吐改善是否缩短程序时间？ | 返回时点、消费者依赖、共享资源及计算与访存的重叠。 |

固定延迟模型可以用于不研究这些变化的粗略估算，但不能自行预测新的映射或调度带来的收益。统计时分别记录请求到达、接纳、相关操作发出和响应可见的时点；bank、端口和通道阻塞可能重叠，不能直接把各类等待相加。
