# 多通道与 NUMA：地址分布、线程与数据放置

## 这页在回答什么问题

给系统增加内存通道或处理器后，总带宽和容量可以增加。但一个线程访问某个地址时，不会自动同时用到所有新增资源。请求要先找到数据所属的节点和通道，再沿实际路径到达那里。

本文回答两个问题：**地址怎样分散到不同资源？线程与数据的位置怎样改变访问路径？**具体 DRAM 地址映射算法和性能计量分别交给相邻文章，不在这里重复展开。

## 先分清通道、socket 和 NUMA 节点

| 名称 | 描述什么 | 不能据此推断什么 |
| --- | --- | --- |
| 内存通道（channel） | 一组内存接口及其连接的存储资源，可与其他通道提供一定程度的并行服务。 | 多个通道不一定各有完整独立的控制器，也不必形成 NUMA。 |
| 处理器插槽（socket） | 系统中一个处理器封装的安装与连接位置。 | 一个 socket 不一定只对应一个 NUMA 节点。 |
| NUMA 节点（node） | 操作系统用于描述 CPU、内存及其访问亲近关系的拓扑单位。 | 节点不一定同时包含 CPU 和内存，也不是 cache 一致性域的同义词。 |

NUMA 是 Non-Uniform Memory Access，即非均匀内存访问。它关心的是：**同一份内存由不同位置的请求者访问时，代价是否不同。**对称多通道可以保持均匀访问；单 socket 也可以划分多个 NUMA 域。

一个具体例子是 Skylake-SP 的 Sub-NUMA Clustering（SNC）：它可在一个 socket 内形成两个局部域，把核心、LLC 分片和相邻内存控制器的亲近关系暴露给操作系统。这是特定处理器的配置，不是所有 CPU 都有两个节点。[Intel 技术概览](https://www.intel.com/content/www/us/en/developer/articles/technical/xeon-processor-scalable-family-technical-overview.html)同时说明了跨 socket 的一致性互连，因此“不同 NUMA 节点”也不等于“互不一致”。

## 通道扩展与远端访问代价

### 多通道：请求必须分散，资源才能并行

在目标节点内，物理地址映射决定请求落到哪个 channel、bank 和 row。增加通道提供了更多可并行的接口，但请求是否分散，取决于映射和地址流。

考虑一个**仅用于说明映射的假设系统**：两个通道按 64 B 地址块交错，偶数块进入通道 0，奇数块进入通道 1。假设没有额外哈希或重映射：

- 请求依次访问块 0、1、2、3，会交替使用两个通道。
- 请求依次访问块 0、2、4、6，仍全部进入通道 0。

第二种情况即使有多个未完成请求，也没有利用另一个通道。改变步长或数据布局可能改变分布；实际硬件应使用其真实映射分析，不能把这个简化规则套到所有处理器上。

通道交错和 NUMA 页放置处于不同层次。在这个假设系统中，一个物理页可以包含许多 64 B 块，这些块交错到同一节点内的两个通道；操作系统选择该页的节点，并不等于它分别选择页内每个块的通道。实际交错粒度和节点、通道之间的关系取决于系统配置。

还要有足够多可同时推进的请求。如果每次读取都依赖上一次返回的地址，多通道通常不能把这条串行依赖链变成并行。共享互连、控制器前端或请求源也可能先达到上限。因此，独立通道的峰值之和只是有条件的聚合上界，不是单线程可获得的带宽。

### NUMA：请求者和内存位置共同决定路径

以两个节点各有本地 DRAM 的 ccNUMA 系统为例。假设读取未被各级 cache 满足，最终需要访问 DRAM，且页归属在本次访问期间不变：

| 请求 | 简化后的去程 | 返回数据 |
| --- | --- | --- |
| 节点 0 的 CPU 读节点 0 的页 | 本地互连 → 节点 0 的内存控制器 → DRAM | 沿对应本地响应路径返回。 |
| 节点 0 的 CPU 读节点 1 的页 | 节点间互连 → 节点 1 的内存控制器 → DRAM | 还要占用节点间返回路径。 |

表中省略了地址翻译、一致性查询等细节。如果数据由另一颗 CPU 的 cache 提供，实际路径又会不同；不能把所有远端访问都画成“远端 DRAM 读取”。

远端路径增加了要经过的资源，并可能与其他流量争用。但不能据此断言每一笔远端请求都比每一笔本地请求慢：本地队列拥塞程度、cache 状态和目标内存类型也会影响结果。应比较同样边界、相近负载下的路径。

[Linux 的 NUMA 说明](https://docs.kernel.org/mm/numa.html)从硬件位置与软件节点两个角度描述了这种差异。这里的重点不是插槽数量，而是实际拓扑。

## 页放在哪里，与线程跑在哪里是两件事

操作系统通过页表将虚拟地址映射到物理页。物理页所在的内存节点决定数据位置；线程当前运行的 CPU 决定请求发起位置。线程换核，不意味着它使用的页会立即跟着移动。

在 Linux 中，节点选择还受内存策略与允许节点集合约束。默认本地分配、指定节点集合和跨节点交错分配具有不同效果；改变策略通常不会自动搬走已分配的页。[NUMA Memory Policy](https://docs.kernel.org/admin-guide/mm/numa_memory_policy.html)给出了这些规则及例外。

### first-touch 为什么会影响后续访问？

下面是一个**教学案例**，不是所有分配器和映射类型的固定行为。假设使用尚未实际分配物理页的匿名内存，采用本地分配策略，节点内存充足，线程位置固定，期间没有页迁移：

1. 线程 A 在节点 0 上申请一块数组。取得虚拟地址还不代表每一页已有物理存储。
2. A 写入整个数组。首次触发实际物理页分配的访问，使这些页按当时策略分配在节点 0。
3. 工作线程 B 在节点 1 上反复处理数组后半段。这部分页仍在节点 0，因此 B 可能持续产生远端流量。

这就是常说的 first-touch（首次触碰）影响。关键不是源代码中第一次出现变量，也不是固定由 `malloc` 的调用者决定，而是**实际分配发生时的访问位置与策略**。

一种调整方法是先划分各工作线程负责的页范围，再由固定在相应节点的线程初始化并处理自己的范围。例子中可让 B 初始化后半段，使其页有机会本地分配。分块边界应考虑页粒度，否则一个页仍可能由另一线程先触发分配。

这个办法有明确边界：已有页面、显式交错策略、文件映射、可用内存不足或迁移机制，都可能改变结果。分配粒度也不一定是普通基础页大小；透明大页等机制可能改变一次分配覆盖的范围。[Linux 的透明大页文档](https://docs.kernel.org/admin-guide/mm/transhuge.html)说明了不同大小的透明大页。优化后应检查实际页分布，而不只看初始化代码。

### 本地优先，不等于所有数据都放一个节点

如果许多节点共同读取一个大数组，把全部页固定在一个节点可能压满该节点的通道或跨节点链路。按页交错分配能分散服务压力，却也可能增加某个线程的远端访问比例。

因此，选择应从访问关系出发：能按工作分区的数据尽量靠近其主要消费者；广泛共享的数据则比较分区、交错或只读副本的成本。频繁跨节点写同一 cache line 时，还要考虑一致性流量，不能仅靠重新摆放物理页解决。

## 怎样检查实际位置与访问？

分析一个 Linux 程序时，可以按以下顺序收集证据：

1. 查看操作系统报告的节点、CPU、内存和距离；记录实际启用的硬件拓扑，而不只依据 socket 数量。
2. 检查工作线程的 CPU 亲和性和实际运行位置，以及内存策略和允许分配的节点。亲和性表示允许在哪里运行，本身不证明线程在整个观察窗口始终位于某一个 CPU。
3. 查看进程页面的节点分布和页大小，确认初始化、交错或迁移是否得到预期结果。Linux 的 `/proc/<pid>/numa_maps` 可以提供进程内存区域的分布信息；具体输出和可见范围以系统为准。
4. 在相同工作负载和观察窗口下测量响应时间、吞吐及可用的本地／远端流量计数，再检查 cache、互连和控制器是否受到争用。

页面分布只说明某时刻数据的物理放置，不能单独说明每次访问实际从哪里取得数据。读取可能由 cache 满足；线程或页面也可能在采样之间移动。Linux 对 `numa_maps` 的字段和页面分布说明见 [proc 文件系统文档](https://docs.kernel.org/filesystems/proc.html)。

## 一句话理解

多通道增加可并行的服务资源；NUMA 让资源位置进入访问代价。要把新增资源变成性能，必须同时考虑地址分布、线程位置和共享路径，而不是只相加容量与峰值带宽。

## 建模启示

先保留与问题有关的拓扑和放置信息，再决定是否需要细化 DRAM 时序：

| 模型信息 | 用来区分什么 |
| --- | --- |
| 请求发起节点与页所在节点 | 同一个地址由不同线程访问时，路径可能不同。 |
| 地址到通道的映射 | 请求是否集中在热点通道，还是能够并行。 |
| 请求与响应路径 | 请求控制消息和返回数据分别占用哪些链路。 |
| 共享队列与服务资源 | 增加通道后，是否仍受同一前端或互连限制。 |
| 页迁移、线程迁移与一致性路径 | 位置是否随时间改变，数据是否实际来自 DRAM。 |

不要直接把“远端延迟”作为固定罚时叠加到所有请求上。若它已是端到端测量值，再加链路和队列延迟会重复计时。若使用分段服务模型，则按实际依赖与重叠关系推进事件，分别记录路径、排队与服务时间。
